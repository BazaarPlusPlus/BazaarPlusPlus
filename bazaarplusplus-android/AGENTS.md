# AGENTS.md

The BazaarPlusPlus Android App (`com.bazaarplusplus.android`) loads the installed official The Bazaar in its own process and starts LemonLoader and the mod in it. Read root `docs/adr/0012-android-app.md` before changing how the App loads the game, what it carries, or what it writes for the mod. Name things with the terms in `GLOSSARY.md` and the root `GLOSSARY.md`.

## Where a change goes

- Mod features and the Android Host belong in `bazaarplusplus-mod/`. This project only finds, loads and launches the game, and stages what LemonLoader reads.
- Tool versions live in `toolchain.lock.json`; Gradle's own version lives in `gradle/wrapper/gradle-wrapper.properties`. The build scripts read the lock, so a version change is one edit there.
- What the App carries (the Loader Release, native libraries, the Updater) is staged by `release/android-app.mjs`, not by Gradle. Gradle only packages `-Pbpp.runtimeDir`.
- `res/values/bpp_tokens.xml` and `res/drawable/bpp_mark.xml` are generated by `design/build.mjs` (`just design::build`). Change `design/tokens.json` or `design/bpp-mark.svg`, never the generated files.
- The bridge Activity (`src/bridge/`) is compiled into `bridge.dex`, which the game class loader defines next to the game's APKs. It must stay out of `classes.dex` and reach App code only by reflection on `GameSession.wrap`. A restored game Activity in an unprepared process never reaches it: `GameComponentFactory` returns `launch/RestoreActivity` instead.
- The launch rules live in the pure `launch/LaunchGate`; `launch/LaunchCheck` only gathers its inputs. Keep the decision there, with a JVM test per tier.
- The Launch Record is a contract with the mod: `launch/LaunchRecord.toJson` and the golden `contracts/launch-record.v1.json` own it. Change both, and the mod's reader, in one pull request, and bump `SCHEMA_VERSION` for a new field.
- Every development hook goes in `src/debug/.../DevOverrides`, with a twin in `src/release/` that answers "none", so a release build cannot read `files/dev/`.

## Verification

`just android::check` and `just android::test` gate every change (JDK and Android SDK per `toolchain.lock.json`). A change to loading, the runtime or `LoaderDeployment` is done when the debug App launches the installed game on an arm64 emulator:

1. `just android::stage-runtime`, then `just android::install`.
2. For a BPP launch, `just android::interop-package` and `just android::push-interop` (Development interop). To exercise the launch tiers instead, serve a local release: `just android::dev-signing-key`, sign the interop statement with `just android::dev-sign-interop`, serve a directory in the public `installer/` layout with any static server, and `just android::dev-manifest-port <port>`.
3. The launcher's BPP launch reaches the game's sign-in screen or main menu, and `adb logcat` shows LemonLoader's `Applied packaged deployment` with no `FATAL EXCEPTION`.

A change to the launcher is done when each affected tier shows its state on the emulator; the App logs its gate decision as `launch gate:` under the tag `BppApp`.

## Gotchas

- The debug App (`com.bazaarplusplus.android.dev`) is a separate sandbox: its game sign-in, Data Root and LemonLoader files are its own.
- A file that `adb push` puts in the App's external files directory belongs to `shell`, and the App cannot read it. Use `push-interop`, which copies through `run-as` into internal storage.
- Homebrew's `openjdk@21` is keg-only. Set `JAVA_HOME` to it, or Gradle and the commit hook run on another JDK and fail to resolve the locked toolchain.
- Unity reads `libmain.so` from `nativeLibraryDir`, so `useLegacyPackaging` (extracted native libraries) must stay on.
- Game logs can hold account data. Quote only the lines you need; never commit or share raw logs. The diagnostics export runs them through `diag/Redactor` first.
- A Development interop beats a Development origin. Run `just android::dev-reset` before testing tiers on a device that a B1 worktree used: the sandbox and its `files/dev/` survive reinstalls.
- The Release cache answers when the network fails, a 404 included: once a Pre-Adaptation record was read, `NEWER_WAITING` stays unreachable until `files/release-dev/adaptations/` is deleted with run-as.
- The game is prepared once per process (`GameSession.prepare`). A second BPP launch in the same process fails on purpose; kill the App between tier tests.
- `InputStream.readAllBytes` needs API 33 and lint fails the build on it; use `AtomicFiles.readAtMost`.
