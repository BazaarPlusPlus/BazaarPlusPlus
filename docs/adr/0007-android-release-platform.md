# Android 作为第三个发布平台，留在 lockstep 集合之外

Android 用户拿到的是一个能直接安装的 APK：官方游戏 APK 注入 LemonLoader、interop 与 BPP 的 Mods 后由 BPP 签名。它要进同一套发布链路（不可变版本目录、fragment、`promote`、Platform Release Manifest），但它的产物、节奏和形状都和桌面不同：没有 Tauri installer 与 updater 包；APK 约 2.8 GB，身份是（游戏版本、loader、interop），不是 BPP 版本；游戏每更新一次 APK 就要重新注入，BPP 的纯 mod 更新却只换几 MB 的 Mods。

决定如下。平台表 `release/release-platforms.mjs` 追加 `android-aarch64` 一行，`kind: 'android'`、`buildPlatform: 'android'`、`nodePlatform: null`（不绑定宿主操作系统），没有任何 Tauri 字段；两个桌面平台标为 `kind: 'tauri'`，Tauri 一致性检查与 `bundle.sh` 的平台查询只对它们执行，不塞一个假的 Tauri 条目。平台键是永久线上契约，只追加不改名。

Android 的 fragment 是另一种 kind：`schemaVersion: 2, kind: 'android'`，记录两个产物与 mod 自更新比较所需的事实——`apk{url,size,sha256,versionCode,signerSha256,builtForProductVersion}`、`managedPayload{url,size,sha256,signature}`、`selfUpdatable`、`historyDatabaseUserVersion`、`nonManagedPayloadDigest`、`game{gameVersion,versionCode,officialApkSha256}`、`loader{tag,sha256}`、`interopSha256`。APK 的 R2 键不在版本目录下，而是 `android/apk/BazaarPlusPlus_<游戏构建号>_lemon-<loader tag>_<interop 摘要前 8 位>.apk`，由 `manifest.mjs` 的 `androidApkKey` 从这三项算出并在校验时复算；一次纯 mod 更新的 fragment 指向已有的 APK，`builtForProductVersion` 记录它烤进去的是哪个版本的 Mods，不得晚于 fragment 的版本。Managed Payload zip 在 `<版本>/android-aarch64/managed/` 下。Platform Release Manifest `latest/android-aarch64.json` 保留共同的顶层字段（`version`、`gitCommit`、`notes`、`pub_date`），没有 Tauri 的 `platforms` 键，`downloads["android-aarch64"]` 放上述事实与可选的 `mainlandUrl`；浏览器与 mod 用 `release/downloads.ts` 的 `decodeAndroidDownload` 读它。桌面 fragment 保持 `schemaVersion: 1` 的 Tauri 形状，只把同样的 `managedPayload` 与 `selfUpdatable` 定义为可选字段，供以后的自更新使用。

`latest.json` 的 lockstep 集合固定为桌面双平台（`LOCKSTEP_PLATFORM_KEYS`）：不带 `--platform` 的 `promote`、`mirror-all` 与 `latest.json` 的推进只看 Windows 与 macOS；`promote --platform android` 校验 APK 与 Managed Payload zip 在远端存在且大小、sha256 一致，只写 `latest/android-aarch64.json`，从不碰 `latest.json`。"一个版本号只对应一个提交"对 Android 同样成立：上传与提升都把同版本的 Android fragment 和桌面 fragment 的 `gitCommit` 互相比对；Android 可以跳过版本。Android 第一版没有大陆镜像：蓝奏云的单文件上限放不下 APK，`promote --platform android` 不读也不要求镜像记录，`mirror`、`verify-mirror` 拒绝 Android。

Payload Inventory 升到 `schemaVersion: 2`：每个条目带 `host`（`bepinex` 或 `melonloader`），平台按平台表的 `payloadHost` 只安装自己宿主的条目，`platforms` 的合法值来自同一宿主的平台。MelonLoader 条目相对 Android 应用的外部文件目录（`MelonLoader/Mods/`、`MelonLoader/UserLibs/`、`MelonLoader/UserData/BazaarPlusPlus.cfg`、`MelonLoader/Latest.log`）；生产者 `apk-injection` 的条目是 APK 内部路径（`lib/arm64-v8a/libmain.so`、`lib/arm64-v8a/libe_sqlite3.so`、`assets/LemonLoader/`），由注入步骤产生，不进 mod 构建；APK 内部路径只能由它产生。生成的 `Payload.targets` 按宿主出两组条目，工程用 `BppPayloadHost` 选择，默认 `bepinex`；installer 只读 `bepinex` 条目，桌面安装与清理行为不变。

否决的方案：Android 进 lockstep 集合，Android 的发版节奏受游戏 APK 更新钳制，它跳过的任何版本都会让 `latest.json` 停住，反过来卡住桌面热修；在平台表里给 Android 塞一份假的 Tauri 字段，所有按平台读 Tauri 配置的检查都要为它写例外；APK 放在版本目录下，每个 BPP 版本都要重传 2.8 GB 而其中只有几 MB 变了；另写一份 `payload-android.json`，Payload Inventory 的意义就是文件列表只在一处。

代价：`manifest.mjs`、`publish.mjs` 与官网解码都按 kind 分支；Android 的上传与 APK 注入（#358）和 mod 的运行时自更新（#362）要遵守这里定下的 fragment 与键；Payload Inventory 先列出了 Android 宿主与 Core 程序集（#352、#354）尚未存在时的目标布局。修订 [ADR 0003](0003-per-platform-release-promotion.md) 中"`latest.json` 等每个平台"一条。
