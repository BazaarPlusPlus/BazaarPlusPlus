# Android 作为第三个发布平台，留在 lockstep 集合之外

Android 用户拿到的是一个能直接安装的 APK：官方游戏 APK 注入 LemonLoader、interop 与 BPP 的 Mods 后由 BPP 签名。目标用户没有开发背景，安装只能是"下载一个 APK 装上"；BPP 是官方合作的 mod 开发商，合作授权允许分发含游戏二进制的注入版 APK。这是本记录的前提，也是它修订下文几条"不分发游戏字节"规则的理由。它要进同一套发布链路（不可变版本目录、fragment、`promote`、Platform Release Manifest），但它的产物、节奏和形状都和桌面不同：没有 Tauri installer 与 updater 包；APK 约 2.8 GB，身份是（游戏版本、loader、interop、注入的原生库、Updater），不是 BPP 版本；游戏每更新一次 APK 就要重新注入，BPP 的纯 mod 更新却只换几 MB 的 Mods。

决定如下。平台表 `release/release-platforms.mjs` 追加 `android-aarch64` 一行，`kind: 'android'`、`buildPlatform: 'android'`、`nodePlatform: null`（不绑定宿主操作系统），没有任何 Tauri 字段；两个桌面平台标为 `kind: 'tauri'`，Tauri 一致性检查与 `bundle.sh` 的平台查询只对它们执行，不塞一个假的 Tauri 条目。平台键是永久线上契约，只追加不改名。

Android 的 fragment 是另一种 kind：`kind: 'android'`（按平台分派，`schemaVersion` 与桌面一样是 1），记录两个产物与 mod 自更新比较所需的事实——`apk{url,size,sha256,versionCode,signerSha256,builtForProductVersion}`、`managedPayload{url,size,sha256,signature}`、`selfUpdatable`、`historyDatabaseUserVersion`、`nonManagedPayloadDigest`、`game{gameVersion,versionCode,officialApkSha256}`、`loader{tag,sha256}`、`interopSha256`。`nonManagedPayloadDigest` 是锁条目 `android-online` 中 loader（tag 与 zip 的 sha256）、interop 摘要、`nativeLibs` 各库 sha256 与 Updater（`MelonLoader/Plugins/BazaarPlusPlus.Updater.dll`）sha256 的摘要，由 `manifest.mjs` 的 `androidNonManagedPayloadDigest` 定义；它与游戏版本合起来就是 APK 的身份。总方案（#367）§5.6 原把这个摘要定义为 Payload Inventory 非托管条目的文件哈希集合；Android 的这些文件（`apk-injection` 条目）在注入之前没有哈希，Patcher 的输出也不保证逐字节可复现，而纯 mod 更新必须不重建 APK 就能得到它，所以 Android 改取锁条目钉住的注入输入。桌面 fragment 的同名字段沿用 §5.6 的原定义：Payload Inventory 中生产者 `native`、`bootstrap`、`sqlite-*` 与 `updater` 的文件 `{path, sha256}` 的摘要（`managed-payload.mjs` 的 `desktopNonManagedPayloadDigest`），因为桌面这些文件在构建时就有确定的哈希（mod ADR 0014）。APK 的 R2 键不在版本目录下，而是 `android/apk/BazaarPlusPlus_<游戏构建号>_lemon-<loader tag>_<nonManagedPayloadDigest 前 8 位>.apk`，由 `manifest.mjs` 的 `androidApkKey` 算出并在校验时从 fragment 复算，所以 fragment 的摘要与它指向的 APK 不会不一致：只换了原生库（例如重新采集时升级 SourceGear.sqlite3）也得到新的键与新的 APK。APK 旁边的 sidecar（`<键>.json`）记录大小、sha256、`versionCode`、签名证书摘要、`builtForProductVersion` 与摘要本身，纯 mod 更新从它取 APK 的事实而不下载 2.8 GB；一次纯 mod 更新的 fragment 指向已有的 APK，`builtForProductVersion` 记录它烤进去的是哪个版本的 Mods，不得晚于 fragment 的版本。Managed Payload zip 在 `<版本>/android-aarch64/managed/` 下。Platform Release Manifest `latest/android-aarch64.json` 保留共同的顶层字段（`version`、`gitCommit`、`notes`、`pub_date`），没有 Tauri 的 `platforms` 键，`downloads["android-aarch64"]` 放上述事实与可选的 `mainlandUrl`；浏览器与 mod 用 `release/downloads.ts` 的 `decodeAndroidDownload` 读它。桌面 fragment 保持 `schemaVersion: 1` 的 Tauri 形状，另带必需的 `managedPayload`、`selfUpdatable`、`historyDatabaseUserVersion` 与 `nonManagedPayloadDigest`；桌面的 `selfUpdatable` 比较的是已提升的平台清单。

`latest.json` 的 lockstep 集合固定为桌面双平台（`LOCKSTEP_PLATFORM_KEYS`）：不带 `--platform` 的 `promote`、`mirror-all` 与 `latest.json` 的推进只看 Windows 与 macOS；`promote --platform android` 校验 APK 与 Managed Payload zip 在远端存在且大小、sha256 一致，只写 `latest/android-aarch64.json`，从不碰 `latest.json`。"一个版本号只对应一个提交"对 Android 同样成立：上传与提升都把同版本的 Android fragment 和桌面 fragment 的 `gitCommit` 互相比对；Android 可以跳过版本。Android 第一版没有大陆镜像：蓝奏云的单文件上限放不下 APK，`promote --platform android` 不读也不要求镜像记录，`mirror`、`verify-mirror` 拒绝 Android。

Payload Inventory（`schemaVersion: 1`，6.0.0 发布前重置）的每个条目带 `host`（`bepinex` 或 `melonloader`），平台按平台表的 `payloadHost` 只安装自己宿主的条目，`platforms` 的合法值来自同一宿主的平台。MelonLoader 条目相对 Android 应用的外部文件目录（`MelonLoader/Mods/`、`MelonLoader/UserLibs/`、`MelonLoader/UserData/BazaarPlusPlus.cfg`、`MelonLoader/Latest.log`）；生产者 `apk-injection` 的条目是 APK 内部路径（`lib/arm64-v8a/libmain.so`、`lib/arm64-v8a/libe_sqlite3.so`、`assets/LemonLoader/`），由注入步骤产生，不进 mod 构建；APK 内部路径只能由它产生。`assets/LemonLoader/` 暂以一个 bootstrap 目录条目代表 loader 的 `runtime/**`、`payload.json` 与烤进去的 `deployment/Mods/**`、`deployment/UserLibs/**`：APK 不可变、整体替换，没有按文件清理的需要；注入步骤（#358）若要按文件核对，再拆成按归属的条目。生成的 `Payload.targets` 按宿主出两组条目，工程用 `BppPayloadHost` 选择，默认 `bepinex`；installer 只读 `bepinex` 条目，桌面安装与清理行为不变。

否决的方案：Android 进 lockstep 集合，Android 的发版节奏受游戏 APK 更新钳制，它跳过的任何版本都会让 `latest.json` 停住，反过来卡住桌面热修；在平台表里给 Android 塞一份假的 Tauri 字段，所有按平台读 Tauri 配置的检查都要为它写例外；APK 放在版本目录下，每个 BPP 版本都要重传 2.8 GB 而其中只有几 MB 变了；另写一份 `payload-android.json`，Payload Inventory 的意义就是文件列表只在一处。

代价：`manifest.mjs`、`publish.mjs` 与官网解码都按 kind 分支；Android 的上传与 APK 注入（#358）和 mod 的运行时自更新（#362）要遵守这里定下的 fragment 与键；Payload Inventory 先列出了 Android 宿主（#352）尚未存在时的目标布局。

本记录修订以下记录，各自加了日期注记：[ADR 0001](0001-product-release-promotion.md) 隐含的"发布产物不含游戏字节"前提，Android Release APK 在合作授权下含游戏二进制；[ADR 0002](0002-mainland-mirror-check.md) 的"`promote` 缺少镜像记录时拒绝"对 Android 不适用，Android 的提升从不读镜像记录，这是平台规则而不是逐次的显式跳过；[ADR 0003](0003-per-platform-release-promotion.md) 中"`latest.json` 等每个平台"一条；[ADR 0007](0007-one-public-bucket-and-domain.md) 的"游戏本体文件不能进公开桶"，Android Release APK 放在公开桶的 `installer/android/apk/` 下，游戏程序集快照、interop 与官方 APK 仍只在私有桶；[ADR 0008](0008-interop-snapshots-in-snapshot-lock.md) 的"不进 Payload Inventory"，Payload Inventory 用 `apk-injection` 条目列出注入后 APK 内的路径以定义 APK 的布局，快照锁里的 Loader Release、interop 与官方 APK 这些构建输入本身仍不进清单。

2026-10-29 修订：每个产品版本都注入并上传自己的 Android Release APK，新用户装上就是当版的 Mods；已安装的用户仍在 `nonManagedPayloadDigest` 不变时只下载 Managed Payload zip。上文"APK 放在版本目录下，每个 BPP 版本都要重传"被否决的理由是上传量，现在接受这份代价：每个版本在 R2 多存约 2.9 GB，没有清理。APK 的键改为 `android/apk/BazaarPlusPlus_<版本>_<游戏构建号>.apk`（`manifest.mjs` 的 `androidApkKey`），`builtForProductVersion` 总等于 fragment 的版本；身份已发布就跳过注入的分支、APK 旁边的 sidecar 与 `--rebuild-apk` 退役。清单校验只要求 APK 在 `android/apk/` 下，因为 6.0.0 到 6.0.2 的 APK 仍以旧键命名；精确的键由 `upload` 检查。Android 的 `selfUpdatable` 改为与桌面相同，比较已提升的平台清单。6.0.0 到 6.0.2 的复用分支从未生效：Updater 的 `InformationalVersion` 带着 git 提交号，每个提交的摘要都不同，#672 去掉了它。

2026-11-01：被 [ADR 0012](0012-android-app.md) 取代。Android 不再分发注入的 APK，改由 BPP 的 Android App 在本进程里加载用户已装的官方游戏。本记录中仍有效的平台规则（平台键、不进 lockstep 集合、没有大陆镜像、Payload Inventory 的 `melonloader` 宿主）由 ADR 0012 重新承载。
