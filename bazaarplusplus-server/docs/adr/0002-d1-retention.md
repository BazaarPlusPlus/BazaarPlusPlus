# ADR 0002：D1 元数据保留 15 天

状态：已接受
日期：2026-09-12

## 决策

以 `bundles.stored_at_ms` 为起点保留 Bundle 元数据 15 天。Worker 的 `scheduled`
入口每 15 分钟执行一次清理，以 `scheduledTime - 15 天` 为固定截止时间，只删除
严格早于该时间的记录。恰好达到边界的记录保留至下一次执行。客户端时间、下载和
投递结算都不延长保留期。

每条 DELETE 通过 `idx_bundles_stored_retention` 选出最早的至多 100 个 Bundle，
在同一语句内完成选择和删除；每次调度最多执行十批。数据库外键级联清理
`ghost_battles`、`bazaardb_deliveries` 和 `bazaardb_delivery_attempts`。
`bundle_uploaders` 是部署期间持续积累的上传者声明，清理不删除它。

各批独立提交。后续批次失败时，已完成批次保持生效，调度返回失败，下一次执行
继续处理剩余记录。重试和并发调度不需要应用层游标或分布式锁。

## 理由与边界

R2 的对象生命周期为八天，Ghost 可见窗口为五天，Bundle collection 可见窗口为
八天。D1 保留十五天使投递记录和回执在对象过期后仍可供排查，同时限制历史增长。
定时清理不依赖业务请求或消费者持续在线，也不向 HTTP 接口增加维护路由。

单次清理预算避免积压转化为长事务。按配置，调度全部成功时每天最多删除
96,000 个父 Bundle；该上限不代表稳定吞吐承诺。清理期限是异步删除的资格边界，
实际删除时间取决于调度成功率和积压。十五天内的数据量和长期保留的上传者集合
仍需容量监控。

调度只使用 D1，不访问 R2、不签发下载地址。R2 生命周期继续由桶配置管理。
投递过期和耗尽重试的状态收敛仍由 claim 请求负责，每类每次最多更新 1,000 行；
过期积压未清完时不授予租约，返回带 `Retry-After: 1` 的可重试响应。

## 可观测性与验证

`d1.retention` 记录截止时间、删除的父 Bundle 数量和 `has_more`；
`d1.retention.failed` 记录中断及此前已提交的父 Bundle 数量。运维监控清理积压、
调度缺失、最老存储时间以及 D1 总容量。

测试通过公开的调度入口和维护模块验证十五天边界、存储时间口径、级联删除、
上传者保留、批次预算、故障后继续清理及实际 SQL 执行计划。相关索引由已有迁移
提供，部署该策略不需要新迁移。

元数据被删除后，Bundle 身份去重和投递回执的幂等历史随之结束；后续旧回执结算
返回 `unknown_item`。消费者需按自身需求保留去重记录。Worker 回滚不会恢复已删除
元数据，恢复依赖可用的数据库备份。
