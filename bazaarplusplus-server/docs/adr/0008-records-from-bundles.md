# ADR 0008：战绩直接读最近 8 天的 Bundle

状态：已接受
日期：2026-11-26
取代：[ADR 0007](0007-site-first-accounts.md) 第 2 条中的设备令牌、第 4 条和“R2 保留与成本”一节

## 背景

ADR 0007 让战绩搭在 Bundle 上传上：只有带有效设备令牌的上传，服务端才写 `run_summaries`，并把 Run 段复制到 `account-runs/` 长期保存。这样做有三个问题：

- 绑定之前上传的局永远进不了战绩。同一个 Bundle 再传一次时，服务端在检查令牌之前就按重复返回。
- 设备令牌只为证明“这一局是你本人上传的”，却带来了令牌表、设备激活、影子鉴权和 Mod 里的令牌存储。
- 两份存储（D1 摘要与 R2 副本）要保持一致，解绑、注销和上传途中的竞争都要专门处理。

账号功能还没有在任何平台发布，生产 D1 里没有任何 `run_summaries` 行，所以这次直接替换，不留兼容分支。

## 决策

1. **战绩就是 Bundle**：已链接游戏账号的战绩，是 `bundles` 中 `uploader_account_id` 等于该游戏账号、而且对象仍在 R2 中的行，也就是最近 8 天（`R2_RETENTION_MS`）上传的排位局（只有排位局会生成 Bundle）。服务端不复制、不长期保存战绩；Bundle 过期，战绩也随之消失。
2. **摘要存在 Bundle 行上**：每次 Bundle 入库都把 manifest 的 `projection.run` 终局字段（英雄、胜负、段位、分数、分数变化、结束时间）和 Run 段在对象中的字节范围写进 `bundles` 的列。列表与统计只读 D1；单局详情按字节范围从原 Bundle 对象读出 Run 段，交给浏览器解码。没有终局字段的行（发布版 Mod 写空 `projection.run`）不算战绩。
3. **三条网站路由用同一个归属条件**：`uploader_account_id` 等于会话账号链接的游戏账号，`stored_at_ms` 在 R2 保留窗口内，`ended_at_ms` 不为空。列表、单局摘要和 Run 段都按它判断，所以不会列出对象已经删除的局。
4. **没有设备令牌**：删除 `bpp_device_tokens`、`POST /account/devices`、`GET /account/me`、上传与 Ghost 查询上的影子鉴权，以及 Mod 中的令牌存储。`POST /account/bind` 用绑定码和官方游戏令牌链接游戏账号后，只返回游戏昵称和打码邮箱。Mod 不保存链接状态；链接状态只在网站上看。
5. **解绑与注销不删除 Bundle**：这些 Bundle 是普通的 Ghost 数据，和未绑定玩家的一样按 ADR 0002 过期。解绑后网站不再显示它们。

## 信任边界

Bundle 里的 `player_account_id` 是客户端自报的。Ghost 已经按它分配数据；战绩沿用同一信任：网站给已链接的账号看“声称属于其游戏账号”的 Bundle。链接本身由官方游戏令牌验证，所以只有游戏账号的主人能看到这些 Bundle。

代价是：知道某个玩家游戏账号 id 的人，可以伪造 Bundle，让它出现在该玩家的私人战绩页里。这需要先知道对方的 id，而且没有收益；一旦发生，网站无法区分真假。我们接受这个代价，换掉整套设备令牌。服务端从不根据这个 id 写入或授权别的东西。

## 后果

- 绑定后，最近 8 天里由能写终局字段的 Mod 上传的局立即出现，不需要补传。
- 网站只显示最近 8 天，统计也只算这 8 天。
- 每个 Bundle 行多 9 列。15 天的 D1 保留窗口里约 54 万行，约多 50 MB。
- ADR 0002 的保留规则不变；R2 的 `account-runs/` 前缀不再使用。
- 与 ADR 0007 相比，账号本身（邮箱加密码、绑定码、Turnstile、解绑、注销）不变。
