# D1 容量分析

观测时间：2026-09-12 20:08–20:15（Asia/Shanghai）。
数据库：`bazaarplusplus-mod-api-v5-db`。

当前数据库物理大小约 **3.32 GB**。容量主要来自 `ghost_battles`：战斗投影内容及其索引字段合计约 **1.76 GB**，占本次可归因逻辑内容的 **82.7%**。其中 `projection_json` 本身约 **1.14 GB**。优先优化投影 JSON 的重复字段；进一步缩短投影正文的保存时间，需要单独明确保留策略和去重语义。

本次只读取生产数据，没有执行删除、改写或变更保留策略。

## 统计口径

- 通过生产 D1 API 获取数据库大小，并按主键每页至多 20,000 行遍历五张业务表，共 150 次分页查询；分页查询最长约 875 ms。
- 表内容统计 UTF-8 文本字节及 SQLite 整数值的编码字节。索引按现有定义计算字段内容，包含 `WITHOUT ROWID` 表隐含的主键后缀，并应用各部分索引的过滤条件。[SQLite 文件格式](https://www.sqlite.org/fileformat.html#representation_of_sql_indices)
- 下表为**逻辑内容体积，不是物理表大小**，不含记录头、B-tree 页结构、溢出页和页内未使用空间。物理总量来自 D1 API。[Cloudflare 数据库接口](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/get/)
- 线上 `dbstat` 不可用，`PRAGMA freelist_count` 返回不允许访问，因此不能精确拆分各表物理页占用，也不能把物理大小与逻辑内容的差额全部判定为可回收碎片。
- 统计期间业务写入及定时清理持续运行，各页不是同一个事务快照。行数和比例应视为这个观测时段的近似全量统计。GB、MB 均为十进制单位。
- 聚合结果保存在 [统计数据](d1-capacity-audit-2026-09-12.json)。未导出玩家标识、投影正文或凭据。

## 可优化内容

### 1. 优先去掉 Ghost JSON 中的重复字段

`projection_json` 中重复保存了 `battle_id`、`recorded_at_ms` 和 `is_final_battle`。这三项已有独立列，查询响应也明确用独立列覆盖 JSON 中的值，见 [Ghost 响应构造](../src/modules/ghost-battle-discovery.ts)。

对现有 JSON 计算移除这三个字段前后的 UTF-8 字节差，合计 **184,110,199 字节，约 184.11 MB**，约为 JSON 正文的 **16.1%**。这是内容层面的可减少字节量，不保证物理文件立即等量缩小。

该优化可以保留完整的 15 天逻辑数据和现有 HTTP 响应语义。实施时应统一新写入格式，并在旧数据上分批改写，验证字段还原、重复上传和 Ghost 返回内容。

### 2. 超出 5 天查询窗口的 Ghost 正文是更大的治理候选

截至固定观测时间 `2026-09-12T12:10:56.994Z`：

- **1,181,755 条**投影的 `recorded_at_ms` 已早于五天前，占 Ghost 行数的 **65.4%**。
- 这些记录的 JSON 正文合计 **746,180,480 字节，约 746.18 MB**。
- Ghost 接口按 `recorded_at_ms` 只返回最近五天；当前 D1 清理则按父 Bundle 的 `stored_at_ms` 保留十五天，见 [查询实现](../src/modules/ghost-battle-discovery.ts) 和 [15 天保留决策](adr/0002-d1-retention.md)。

这部分可以作为“投影正文保留五天，身份去重信息及 Bundle 关系保留十五天”的设计候选，但它改变了当前完整投影的保留策略。不能直接删除整行：`(uploader_account_id, battle_id)` 主键承担跨 Bundle 的首次投影判定，整行删除后，同一战斗可能被后续 Bundle 重新插入。实现必须保留首次身份判定，避免改变“保留第一次投影、重复异常不回填”的行为，见 [提交实现](../src/modules/bundle-commit.ts)。

独立清理还需要支持按全局过期时间进行有界扫描。现有 Ghost 查询索引首列是 `opponent_account_id`，不能直接替代全局时间清理索引。

746.18 MB 和上一项的 184.11 MB 存在重叠，不能直接相加。如果要求所有逻辑投影内容完整保留十五天，应只实施重复字段精简。

## 其他数据的处理结论

- **Bundle 元数据继续保留十五天。** 其中 248,472 个已超过八天 R2 对象生命周期，但仍处在已确定的 D1 元数据保留范围内，承担身份去重及关联记录保留；不把这部分视为可直接提前删除的数据。
- **投递与回执优先维持现有周期。** 两表连同索引字段合计约 53.00 MB。投递中 248,916 条为 done，一条 pending，没有超过八天的 pending。已完成不等于没有用途，回执仍参与重复 settle 的幂等判定。
- **23 条已过期且未结算的旧回执不值得单独清理。** 关联投递均已 done，属于后续尝试已经完成的旧租约历史。这部分仅约几 KB；删除会把后续旧回执的响应从 `stale_claim` 改为 `unknown_item`，见 [结算响应判定](../src/modules/bazaardb-delivery.ts)。
- **上传者集合保留。** 23,391 条只占约 0.98 MB，其中 20,314 条首次上传时间已超过十五天。它们是部署期间持续保留的成功上传者声明，参与对手投影资格判定，不能按最近活跃时间清理。
- **没有发现其他遗留业务表。** 表结构中只有上述五张业务表、两条迁移记录及 SQLite/Cloudflare 系统表；系统表不是业务清理目标。本次没有进行额外的全库孤儿引用扫描，不能据此声称所有引用都已逐行核验。

## 当前保留策略运行情况

20:12 的索引探测发现 456 个刚超过十五天的 Bundle，最早存储时间对应约十五天零十二分钟前，符合每十五分钟异步执行的窗口；没有重新出现大量超期历史积压。

最近二十四小时写入约 43,735 个 Bundle。当前 Cron 的配置删除上限为每日 96,000 个父 Bundle，约为这个观测值的 2.2 倍；实际处理能力仍取决于调度及数据库执行是否成功。[保留策略](adr/0002-d1-retention.md)

线上 `/health` 与 Ghost 空结果探测均返回 200，Cron 配置仍为 `*/15 * * * *`。
