# History And Storage

## History Boundary

- `History` in `src-tauri/src/services/history.rs` resolves the selected installation and privately derives database, screenshot, and video paths. It owns list, detail, reveal, video deletion, cleanup preview, and cleanup execution.
- Commands in `src-tauri/src/commands/history.rs` pass ids, limits, offsets, cleanup scopes, and presets. They do not accept storage paths, cutoffs, or precomputed cleanup plans; a cleanup confirmation names its preview's plan only by the id the preview returned.
- The mod stores every instant as Unix milliseconds in `*_at_ms` columns, with a screenshot's local offset in `captured_utc_offset_minutes`. Queries filter and order on those integers; `src-tauri/src/history/instant.rs` turns them into RFC 3339 text at the column boundary, so History DTOs and overlay records keep their text fields. The overlay's `from` bound is converted to milliseconds, and a `from` that is not RFC 3339 matches no record.
- An absent run detail is a successful nullable result. Unavailable installation, unsupported schema, failed reads, and failed actions remain distinct `SemanticProblem` codes.
- `open_probed` in `src-tauri/src/history/queries.rs` opens the mod database with read/write flags and a busy timeout so SQLite can recover a dirty WAL or create shared-memory files. It probes `user_version`, retries selected transient errors, and rejects unsupported schemas without retry. The supported versions are owned by `src-tauri/history-database-compatibility.json`. The mod bumps `user_version` only for a column change, never for a data repair (mod ADR-0011), and `just release::check` fails unless the mod's version is the newest one listed. Tests read the list through `supported_mod_db_user_versions` in `src-tauri/src/config.rs` instead of restating it.

## Cleanup Safety

- `History::preview_cleanup` and `History::execute_cleanup` derive cutoffs from the same `StorageCleanupPreset` contract in `src-tauri/src/history/cleanup.rs`.
- The preview keeps its plan natively in `CleanupPlans` (`src-tauri/src/services/history.rs`) and returns its `plan_id`; `useStorageCleanup` passes that id when the user confirms. Execution runs that plan, without scanning again, when it was computed for the installation resolved under the lock, for the same scope and preset, and before any Reset or V5 import completed (`DataMaintenanceLock::database_generation`, advanced when such an operation takes the lock and again when it ends, so a preview taken while one runs is stale as well). Otherwise, or when a newer preview or a successful execution consumed it, execution plans afresh. A failed execution, such as the refusal while the game runs, keeps the plan, so the dialog's retry runs what it still shows.
- The game may run while the dialog is open, so a plan can be minutes old. It keeps the preview's cutoff and today's date: rows and files that became eligible meanwhile wait for the next cleanup. Execution trusts no plan. A planned Run is deleted only while it is exactly what the preview counted: still eligible under the plan's cutoff (`RUN_BEFORE_CUTOFF_PREDICATE`), unprotected (`PROTECTED_RUN_PREDICATE`), with the last activity it had when planned, and holding no battle, video, or screenshot the plan did not count. The mod's run upsert can resume a finished Run, and ending it again moves its last activity, so a Run resumed since the preview survives under every preset. Each screenshot delete re-checks the protection, and files go only through the reference check below.
- `execute_storage_cleanup` runs while holding the data maintenance lock ([Install And Reset](install-reset.md#data-maintenance-lock)): a cleanup started during a Reset waits for it and resolves the installation only after the Reset finished.
- `PROTECTED_RUN_PREDICATE` in `src-tauri/src/history/cleanup.rs` protects the source data of runs the mod may still seal. A History-Only Run (`runs.upload_policy = 'history_only'`) is never protected, whatever its status or upload state. The mod owns that rule (`BundleQueueStore.SealEligibleRunCondition`), and the expected protection for each run, outbox, and seal-job state is a case in the mod fixture `../bazaarplusplus-mod/tests/BundleQueueSqliteStore.Tests/fixtures/bundle-seal-eligibility.json`; the cleanup test `run_plan_protects_exactly_the_shared_seal_eligibility_cases` evaluates every case, so the predicate cannot drift from the mod silently. Unprotected runs may be cleaned up, so a later mod recovery cannot assume their source data remains. The same predicate drives planning, skipped counts, screenshot protection, and guarded execution.
- Screenshot cleanup commits eligible row deletions before unlinking files and protects today's local-date folder from the orphan sweep.
- Run-data cleanup validates the required cascade foreign keys before destructive effects. Each planned run is conditionally deleted in a transaction. After all Run deletions, including later chunks, it removes planned video metadata only when the video's current battle no longer belongs to a surviving Run. This also examines videos originally planned under a Run whose guarded delete missed: their battle may now belong to a different, deleted Run. A detached battle or a missing battle does not leave a planned video protected without a Run owner.
- Both paths use `CleanupSession::delete_unreferenced_files` in `src-tauri/src/history/cleanup.rs`. Plans nominate files and estimate bytes; execution reads current references after committing row deletions. A surviving row preserves its file, including a reference published after planning or a planned orphan that has since acquired a row. Screenshot paths, video paths, and replay payloads use this same deletion rule.
- `resolve_cleanup_file_path` in `src-tauri/src/history/files.rs` confines cleanup paths to their expected roots.

### Cleanup concurrency

`CleanupSession::open` in `src-tauri/src/history/cleanup.rs` acquires a SQLite exclusive connection lock, then uses `SystemGameProcessProbe` in `src-tauri/src/services/game_process.rs` to confirm the game is closed. A running game or failed process inspection refuses cleanup before any row or file deletion, through the existing `HistoryActionFailed` surface. The connection remains exclusively locked across every row commit, reference scan, unlink, and empty-directory removal, and releases the lock when the session ends. This uses SQLite's [connection locking mode](https://www.sqlite.org/pragma.html#pragma_locking_mode) as well as an exclusive transaction: a transaction alone would release exclusion at commit. Readers may be blocked during execution; preview remains an ordinary read. The confirmation copy tells users to keep the game closed until cleanup finishes: a launch during cleanup can time out in mod initialization and require a relaunch.

Both parts are necessary because screenshot publication writes the PNG before its database row (`ScreenshotService.BeginCaptureCurrentFrame` in `../bazaarplusplus-mod/src/BazaarPlusPlus/Game/Screenshots/ScreenshotService.cs`, followed by `EndOfRunArtifactPersistence.PersistAsync` in `../bazaarplusplus-mod/src/BazaarPlusPlus/Game/Screenshots/EndOfRunArtifactPersistence.cs`). A file can therefore be awaiting its first reference, including across local midnight, and the timestamp/run-based `ScreenshotPathBuilder.BuildRelativePath` in `../bazaarplusplus-mod/src/BazaarPlusPlus/Game/Screenshots/ScreenshotPathBuilder.cs` does not guarantee unique paths. A database lock alone cannot stop an already-running capture.

A game started after the process check is held at initialization: `DesktopComposition` in `../bazaarplusplus-mod/src/BazaarPlusPlus/DesktopComposition.cs` constructs `EndOfRunCaptureWorkflow`, which constructs the screenshot store before `Plugin.Awake` in `../bazaarplusplus-mod/src/BazaarPlusPlus/Plugin.cs` installs patches or starts replay and video writers. `SqliteStoreBase` in `../bazaarplusplus-mod/src/BazaarPlusPlus.Storage/Sqlite/SqliteStoreBase.cs` always calls `RunLogSchema.EnsureInitialized` in `../bazaarplusplus-mod/src/BazaarPlusPlus.Storage/RunLog/RunLogSchema.cs`, which requires a write transaction. That transaction cannot pass while cleanup owns the connection lock. `PvpBattleSqliteStore.Save` in `../bazaarplusplus-mod/src/BazaarPlusPlus.Storage/Battles/PvpBattleSqliteStore.cs` can update a battle's run attachment, while `CombatReplayVideoMetadataStore` in `../bazaarplusplus-mod/src/BazaarPlusPlus/Game/CombatReplay/Video/CombatReplayVideoMetadataStore.cs` can publish video references; their surviving rows are checked alongside screenshot references. Screenshot attachment is direct and immutable in the current writers: `RunScreenshotSqliteStore.Save` in `../bazaarplusplus-mod/src/BazaarPlusPlus.Storage/RunScreenshot/RunScreenshotSqliteStore.cs` only inserts rows, so planned screenshot metadata is removed with its deleted Run. This startup ordering and the fail-closed process probe are part of the cleanup concurrency contract; moving a writer ahead of store initialization must preserve equivalent exclusion. SQLite and filesystem deletion are not one transaction: a failure can leave committed row deletions and undeleted files, but must not roll back rows into references to files already removed.

## Data Ownership

The current root name comes from `BAZAAR_DATA_DIRECTORY` in `src-tauri/src/config.rs`. Reset may delete that current root; uninstall does not. History, cleanup, and the OBS overlay never read a Legacy Root; the Install page lists and deletes them ([Install And Reset](install-reset.md#legacy-roots)). `BundleOutbox/` and `bundle_outbox` remain mod-owned: installer cleanup may consult upload status but never deletes their files or rows. [ADR-0008](adr/0008-legacy-data-roots-and-v5-import.md) records that ownership boundary.

Runs the V5 import ([Install And Reset](install-reset.md#v5-import)) writes are History-Only: they never become seal candidates, so cleanup never protects them and the mod never resumes them, and an unfinished V5 Run arrives closed as `abandoned`. The import keeps a replay payload only where the installed mod's retention would, ranking imported payloads together with those the current Data Root already holds by the `replayPayloadRetainedNewestCount` and `replayPayloadRetainedAgeDays` fields of its `BazaarPlusPlus.history-database.json`; the other imported battles arrive with `local_payload_state = 'evicted'` and no file. After that the mod's replay maintenance treats the kept payloads like its own. While History has no current database but V5 history exists, `useHistoryUnavailableGuidance` in `src/features/history/useHistoryUnavailableGuidance.ts` turns the unavailable banner into a link to the Install page's import card, or to its reinstall hint while the installed mod still writes an old Data Root. It reads `get_legacy_data_presence`, which never measures a root ([Install And Reset](install-reset.md#legacy-roots)).

Frontend History List and Run Detail each own their loading lifecycle; cleanup and deletion retain the confirmed-operation seam described in [Frontend Architecture](frontend-architecture.md). History Thumbnail preparation is independent of list reads. `createHistoryListWorkflow` requests `prepare_history_thumbnails` on entry, refresh, page changes, and window resume, and tracks `pending`, `ready`, or `unavailable`; `thumbnailUrl` exposes a row's `thumbnail_url` only while `ready`. A later request keeps the current state until preparation settles, including while maintenance holds the lifecycle gate, so a refresh neither remounts nor refetches loaded thumbnails; a failed preparation makes them `unavailable`, and results of superseded requests are ignored. Preparation or image failures use the card's ordinary thumbnail fallback without blocking the list, and a card whose image failed retries it after the next applied preparation. The `prepare_history_thumbnails` command in `src-tauri/src/commands/stream.rs` reports a service start failure, such as an occupied port, as `HistoryThumbnailsUnavailable` with the bind error as its diagnostic. While the last applied preparation failed with that problem, the workflow sets `thumbnailsUnavailable` and `History` in `src/pages/History.tsx` shows a non-blocking status notice above a non-empty list, without an action; the next successful preparation clears it. Other preparation failures show only the card fallback. Browser Preview has no image service, so its stub always reports that problem.

`History::list_runs_for_page` registers the installation path used for its query with `HistoryThumbnails::register` in `src-tauri/src/stream/history_thumbnails/mod.rs` and builds each row's absolute `thumbnail_url` with `history_thumbnails::url`, the only thumbnail URL builder. The URL carries an opaque process-local source, so an existing page cannot be rebound to a different installation when the selected directory gains a database. Sources are deduplicated by path and retained until the installer exits; the database behind a source is resolved on each image request. Listing never touches the stream lifecycle. The thumbnail lookup takes the screenshot the list selected whatever its capture source; the OBS overlay's strip routes still show only end-of-run captures. The route, cache namespace, and cache sweep are described in [Stream Service](stream-service.md).

`StreamRuntime::prepare_history_thumbnails` starts a stopped service through the lifecycle gate and preserves an already-running OBS session, including its directory and display window; a start failure stays visible in the stream status. A later History entry or window resume therefore starts it again after a tray stop or completed Reset. Maintenance still excludes startup. `observeWindowResume` in `src/features/shared/windowActivity.ts` listens to native window focus and to the page becoming visible while the page is mounted, falling back to browser focus outside Tauri or when native registration fails, and refreshes both rows and thumbnails. The Windows close control uses a plain hide-to-tray label on History routes.

`list_history_runs` in `src-tauri/src/history/repo.rs` returns a page of runs with a summary across the full database. The displayed ten-win rate counts completed runs with at least ten victories, independently of the mod's outcome tiers. `createHistoryListWorkflow` in `src/features/history/historyListWorkflow.ts` corrects an out-of-range page before publishing rows, and `useHistoryPage` in `src/features/history/useHistoryPage.ts` binds that selection to the URL. `useRouteScroll` in `src/layouts/useRouteScroll.ts` restores the matching list position on return from details, including when the rows load asynchronously; primary navigation starts at the top.
