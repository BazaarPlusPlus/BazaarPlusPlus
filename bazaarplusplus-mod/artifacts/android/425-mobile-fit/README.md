# #425 Android panels fit the phone: device evidence

Emulator `bpp_api35` (API 35, 420 dpi), game `1.0.12825-production-android-d9601ded`, BPP 6.0.0 deployed as a `build_only` MelonLoader Payload. Every screenshot and log here comes from one build: plugin sha256 `c11683afa1b30048385bfb7061ee2e881e7aa0309f88f07c30212df189787549` (each log's `android.plugin.loaded` line), built from commit `9ea6074` on branch `android/425-mobile-fit-finish`. Later commits on the branch change only this folder.

Two screens: the native 2400x1080 (safe area x 136..2264, a cutout on each side) and `adb shell wm size 2560x1600` (safe area 0,0,2560,1509, the top 91 px unsafe), reset afterwards with `wm size reset`. Each `wm size` change passes through a transient portrait key (`1600x2560` or `1080x2400`) that the panels lay out for and then leave. The conventions are in `docs/architecture/android-mobile-ui.md`, the decision in ADR-0018.

## Redaction

Screenshots are halved. The main menu shows the account name top left, so every main-menu and end-of-run shot is cropped below it (`*-cropped.png`, and `01-main-menu-touch-menu.png`). History's battle rail names the real opponents of the account's own runs: `2560x1600/27-` and `28-` have those names boxed out (`*-names-redacted.png`); the other History shots show the seeded run, whose opponents are seeded `Seed Riv…` placeholders. Supporter names on the Ten-Win Builds shots are the public credits already committed in `397-livebuild/`.

Logs hold only `[BPP]` lines, and any line matching an account, user or player id, a token, or a player name is removed. S1 lost no line to that filter. S2 lost three warnings whose exception text matched it: one `live_build_panel.corpus.degraded reason_code=remote_refresh_failed` and two `lobby.version_check.degraded reason_code=request_exception`, both from the deliberate network cut below. No database is committed: this change touches no stored data.

## Test doubles (S1 only)

- **Seeded history rows.** The account has two runs, too few for the History archive or battle rail to scroll. `seed399.py` (the #399 seeder, see `399-history-rest/README.md`) added nine runs (one with 12 local battles, eight fillers with none) and four Ghost rows with `ghost_replay_state='unavailable_payload'` and an `invalid.invalid` download URL, so nothing downloads. No seal job and no outbox row were seeded. The panel reads them through its shipped `HistoryPanelRepository` queries, and the drag scroll and inspection are the shipped `AndroidHistoryPanel` code; the rows only give it enough to scroll. `seed399.py DB --remove` removed them before S2: the pulled database went from `runs=11 battles=24 battle_snapshots=20` (seeded) back to the account's own `runs=2 battles=8 battle_snapshots=8`, plus what the game itself recorded during S2 (`runs=3 battles=9`).
- **Local build corpus.** The CDN's `builds/latest.json` is not published yet, so the shipped embedded seed matches no Vanessa candidate and Ten-Win Builds can never open an inspection on its own. The #397 corpus (`397-livebuild/make_test_corpus.py`: three Vanessa builds from real template ids, the first one this run's board) was served by `python3 -m http.server` bound to 127.0.0.1 on the Mac, reached through `adb reverse tcp:18397 tcp:18397`, with `[AndroidDev] BuildCorpusPort=18397`. That setting is the existing dev-only seam: it defaults to `0`, has no settings row, logs `android.live_build.dev_corpus_override` as a warning, and changes only the URL; fetch, parse, cache, matching, layout and inspection are the shipped code (`corpus.recovered source=remote build_count=3`). The stats on those screens are made up. Afterwards the port went back to `0`, the reverse and the server were removed, and the cached `BazaarPlusPlusV6/builds.json` was deleted; S2 starts on the embedded seed (`corpus.degraded reason_code=embedded_fallback`).

## Cleanup and game state

- No seal, outbox or upload event in either log; the database after S2 has `bundle_outbox=0 bundle_seal_jobs=0`.
- Seeded rows removed, `BuildCorpusPort` back to `0`, `adb reverse --remove tcp:18397`, the local server stopped, `builds.json` deleted, the network restored, `wm size reset` (physical 1080x2400).
- To reach the end-of-run screens, S2 conceded the account's day-6 Vanessa run (`a7ef4347`) and then started a new one (`run_lifecycle.run.started run_id=2410f64a`), which the device is left in at day 1.

## Caveats

- The relayout failure path (`android.collection.relayout_failed`, the partial root destroyed and the grid returned) was not forced on the device: nothing in a live relayout fails on demand. It is covered by the guard in `AndroidCollectionPanel.Relayout` and by review; every device relayout above succeeded with `rental_leases=0`.
- At 2400x1080 the enchant preview is 10.3 sp, under the 12 sp floor, because the game's tooltip text it sits in is that size. That is the documented in-tooltip rule, not a gap: raising it past the native text would break the tooltip.
- The 2560x1600 combat shot is a monster fight; PvP combat was captured at 2400x1080 only. Both use the same `TouchLauncherLayout` band, logged identically in both fights.
