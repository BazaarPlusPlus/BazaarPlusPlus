# ADR-0019: The Combat Impact producer in Core, on a BPP combat timeline

Status: Accepted

## Context

ADR-0008 kept the Combat Impact producer (`CombatImpactProjector`, `PeriodicEffectAttribution`, `CombatImpactTransformLineage`, and the `CombatImpactEntity` it reads) in the desktop host because it read `BazaarGameShared` types: the `CombatSim` message, its events and targets, eleven combat enums, and the attribute-modifier value graph. Only the desktop could run it, and its tests needed the Managed snapshot. Issue #417 asks for the producer in Core under ADR-0015's rule: BPP vocabulary, a name map per host, and pin tests against both hosts' enums.

## Decision

1. Core owns the combat vocabulary in `src/BazaarPlusPlus.Core/Combat/`. Eleven enums mirror the game's member names: `CombatActionType`, `CombatCardAttribute`, `CombatPlayerAttribute`, `Combatant`, `CombatCardStat`, `CombatHealthChange`, `CombatAttributeOperation`, `CombatDamageType`, `CombatListComparison`, `CombatEffectPriority`, and `CombatValueModifierMode`. `CombatTimeline` copies the replay: its frames, the events the producer reads, the health and attribute updates, and the card stats. `CombatValue` and `CombatAttributeModifier` copy the modifier value graph. The value kinds that attribution reads are copied whole. The other reference kinds are copied as `CombatOpaqueReference`, which keeps only the kind, and anything else becomes `CombatUnsupportedValue`. `CombatValueModifier.GetModifiedValue` repeats the game's `TValueModifier` arithmetic.
2. The producer and `CombatImpactEntity` live in Core and read only Core types. The desktop host keeps only adapters. `DesktopCombatTimeline` copies a `CombatSim`. `DesktopCombatFacets` maps the eleven enums through ADR-0015's `CardFacetNameMap`. The entity readers over game templates (`CombatImpactEntitySnapshotReader`, `CombatImpactAttributionRuleReader`, and the other readers in `src/BazaarPlusPlus/Game/PostCombatImpact/Data/`) write Core facets. An event or action with no Core member is dropped from the timeline, as are the game's condition observations (`CombatSimEventEffectTriggered`), which no rule reads. Amended 2026-10-25: the entity readers stay in the desktop host on purpose. They interpret game template types (abilities, auras, the `ITValue` graph, the catalog), and the Combat Impact Corpus carries their output as BPP data, so no Core test needs them. Revisit when the Android host ports Post-Combat Impact: it must build the same entities from interop templates, so the reader logic moves behind a Core template model then instead of being written twice.
3. Unlike ADR-0015's card facets, the combat facets copy the game's integer values. The producer keys transition claims by `(int)` of an attribute, side by side with `CombatImpactKind` values. It also orders sets and transitions by enum value, and its diagnostics carry attribute integers. Copying the values keeps every claim key and every order the same as before, which keeps the Combat Impact goldens byte-identical. The values still belong to BPP. No code casts between a combat facet and a game enum, and no value is persisted or sent.
4. The pin tests check names and values in both directions. `DesktopCombatFacetVocabularyTests` in `tests/CombatImpactAdapter.Tests/` checks the Managed snapshot. `AndroidCombatFacetVocabularyTests` in `tests/AndroidHost.Tests/` checks the Interop Snapshot's metadata. The Android host adds its own name map when it ports Post-Combat Impact. The pin already guarantees that the map will pair every member by name. Amended 2026-10-25: the pin covers the configured snapshot only, so `DesktopCombatTimeline` also logs the first miss of each game enum as `post_combat_impact.timeline.unmapped_member` with the member it dropped. `CombatValueModifierParityTests` holds item 1's arithmetic to the game's `TValueModifier` for every mode, both rounding settings, fractions, midpoints and a zero divisor.
5. Amended 2026-10-25: the Combat Impact acceptance corpus is split by lane. `tests/CombatImpact.CorpusExport/` (host lane) decodes the committed game payloads in its `corpus/` with their trimmed catalog and writes the Combat Impact Corpus: each battle's `CombatTimeline` through `DesktopCombatTimeline`, its `CombatImpactEntity` snapshots through the entity readers, and the spawn, transform-identity and player-death facts the inventory reads, through `DesktopCombatFacets`. `CombatImpactCorpusCodec` in `tests/CombatImpact.Corpus/Format/` owns the format: gzip JSON, enums by name (ADR-0015), every collection in the order the exporter observed it. `tests/CombatImpact.Corpus/` references Core alone and projects that corpus. The evidence still names game inputs the runner never loads: the exporter hashes the `verificationInputs` (`game_data`, `game_types`, `json_runtime`) into the corpus and the runner copies them, and `GameValueTypeName` names each value by the game value type `DesktopCombatTimeline.ToValue` copies it from, through a fixed table.

## Consequences

- `tests/PostCombatImpact.Tests/` references Core alone and runs in `mod::test-core`. The tests that decode game MessagePack fixtures or read game templates move to `tests/CombatImpactAdapter.Tests/`, which tests the compiled host.
- `tests/CombatImpact.Corpus/` runs in `mod::test-core` and, as a scenario capsule, in `mod::test`, holding its evidence byte for byte to `tests/CombatImpact.Corpus/evidence/pinned-corpus.json`. Only its exporter stays a host lane: `Combat_impact_corpus_export_matches_committed_corpus` in `tests/ScenarioRunner.Tests/` re-exports the game payloads and holds the result to the committed corpus, allowing only the `game_types` and `json_runtime` hashes to follow a game update. The corpus is mod-internal, so it is no cross-project contract.
- A game member Core lacks fails a pin test. Add the Core member with the game's value; do not add a switch to the adapter.

## Relationship to other decisions

This decision replaces ADR-0008's producer boundary, which said the producer stays per host. It extends ADR-0015 with combat facets and narrows that ADR's guardrail against mirroring the game's integers, for the reason given in item 3. Combat attributes are a closed enum, not ADR-0017's name-keyed bag, because the producer reads them.
