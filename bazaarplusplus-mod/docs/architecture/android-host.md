# Android Host

`BazaarPlusPlus.Android` (`net10.0`) is the Android Host (root `GLOSSARY.md`, Host). It is a MelonMod (`src/BazaarPlusPlus.Android/Host/AndroidMod.cs`) compiled against the Interop Snapshot and the Loader Release (`build/InteropPath.props`), never against `Managed/`.

## Shape

- `Host/` owns the loader entry, the `BppLog` exit over MelonLogger (`MelonLogSink`, scope `Android`), the settings store over `MelonLoader/UserData/BazaarPlusPlus.cfg` (`IniSettingsStore`) and the Data Root (`AndroidPaths`): `BazaarPlusPlusV6` beside the MelonLoader base directory.
- `AndroidComposition` builds Core's `CoreComposition` over that Data Root and registers the record chain and the Bundle path, in start order: Core's `RunLifecycleModule` and `RunLoggingModule` over the IL2CPP probes in `GameInterop/`, then Core's `BundleSealCoordinator`. Core's `UploadPump` starts after them and is ticked from `AndroidMod.OnUpdate`; it sends each sealed Bundle to `POST /bundles` with the `android-aarch64` User-Agent token. Bundles are Run-only: the host takes no end-of-run screenshot.
- LemonLoader forwards no pause or focus callback to a melon, so `Host/AndroidAppLifecycle`, an injected `MonoBehaviour` on its own DontDestroyOnLoad object mounted on the first frame in every patch mode, receives Unity's `OnApplicationPause`. A pause parks the `BundleSealCoordinator` worker after its current pass (`bundle_pipeline.worker.paused`), and a resume wakes it for an immediate scan, job discovery included (`bundle_pipeline.worker.resumed`); its jobs are durable, so nothing is cancelled. The upload pump needs no call, since only frames tick it. Focus changes are logged and never acted on, because the notification shade takes focus while the game stays in front.
- `AndroidPvpBattleCapture` records each PvP battle that Core's `PvpBattleCaptureWindow` (ADR-0021) closes, read through `AndroidPvpBattleReads`, which serializes each message as it arrives (`AndroidReplayMessages`); `AndroidComposition` opens the window on `PVPCombat` only. It saves the Replay Payload to `CombatReplays/`, then the battle through `PvpBattleCatalog`, under the persistence lease of Core's `ReplayPayloadOperationGate`. The main thread never waits on that gate: when the lease stays held past `AndroidPvpBattleCapture.LeaseWait` (a replay holds it for its whole session), the battle is saved with its payload `missing` and `android.pvp_battle.lease_busy` logs it. `android.pvp_battle.recorded` logs each set's label and count and how long the saves held the main thread. The capture never reports to `ReplayPersistenceStateTracker`, so a Run holding a `missing` replay is composed once by the seal coordinator and then waits, without composing again, for its input deadline; an asynchronous save (#513) must report to the tracker and call `Completed` after the file is written so such a Run is recomposed when its replay lands.
- On every start Core's `ReplayPayloadMaintenanceService` sweeps `CombatReplays/` once on a pool thread, as on the desktop: orphan files, lost files, and the retention of `ReplayPayloadRetentionPolicy`.
- The Bundle composer is Core's `RunPayloadComposer`; the host supplies only `AndroidPvpBattleEvidence` (card enum values, Replay Payload check).
- `Patches/` install per class under the `[Android] PatchMode` setting (`enabled`, `observe`, `disabled`). A class that fails to install degrades only itself. `NetMessageReceivePatch` is the message intake (run initialization, battle capture); `CombatSimulatePatch` publishes `CombatSimObserved`.
- In the `enabled` mode the game fills screens narrower than 16:10, such as a foldable's inner display (Screen Fill, a Native Adjustment: Core's `Ui/ScreenFill` decides every threshold and size below, tested in `tests/SettingsDockCore.Tests/ScreenFillTests.cs`, the Mobile UI's `NativeAdjustment/TouchScreenFill` runs it on both hosts, and the host only reads and writes the game through `GameInterop/AndroidScreenFillHost`, on iOS `GameInterop/Touch/TouchScreenFillHost`, ADR-0025). The game's `LetterBoxManager` crops any screen outside 16:10 to 21:9 to the nearest ratio inside it, with black bars; Screen Fill lowers that floor to 1:1 on each HUD tick (`touch.screen_fill.applied`) and clears the manager's last screen size so it recomputes the crop. The 3D cameras keep a fixed vertical field of view, which would cut the board's sides on a narrower screen, so `Patches/ScreenFillFieldOfViewPatch` widens it after `CinemachineBrain.LateUpdate`. Between about 1.36:1 and 16:10 (3:2, say) it only keeps the 16:10 horizontal view, the HUD in its usual places (`ScreenFill.GathersHudAbove`); from 4:3 down the board is drawn 1.3 times nearer than 16:10 frames it (trimming most of the scenery beside it), never with a narrower vertical view than the game's, and the camera is raised until the board's bottom edge (the vault's) sits just above the screen's, so the HUD gathers in one band above the board. The day clock stood in the trimmed scenery, so Screen Fill's `TouchDayClock` moves the `ClockViewController` prefab, smaller and nearer the camera so the palm fronds do not cover it, into that band's left end (the board's top-left corner mirrors the vault through `BoardManager.boardCenter`); the combat clock is a row centred in it (`TouchScreenFill.BoardTop`). The game's own canvases scale with the screen's height alone (3840×2160, `matchWidthOrHeight` 1), so narrower than 16:10 they get less width than any panel was laid out for, and the settings menu and the hero picker ran off both sides; Screen Fill's `TouchScreenFillCanvases` moves each such canvas's match toward its width just far enough that it is as wide as 16:10 makes it (tooltips excepted), and puts it back at 16:10 or wider (`ScreenFill.CanvasMatch`). The 21:9 ceiling stays.
- In the `enabled` mode the host adds the interaction features, which touch replaces the desktop's hotkeys for. Every BPP setting lives in the game's own settings dialog, as on the desktop: `Patches/NativeSettingsPatches` prefix the dialog's `ScrollSpyController.Awake`, and `Settings/AndroidNativeSettingsSection` (the desktop's `BppNativeSettingsSectionController` on IL2CPP) clones the Support section and its navigation toggle into a BazaarPlusPlus section whose rows are clones of the dialog's own toggle, dropdown and button, grouped by control and driven by `BppSettingsDockCatalog.Definitions`. `Settings/AndroidSettingsDock` registers those rows through Core's `SettingsDockEntryRegistry`: BazaarDB upload (`[BazaarDB] UploadScreenshots`, the desktop's label; here it gates only History's account-link form, since the host takes no end-of-run screenshot), Core's Combat status bar and Game History (no hotkey, so its plain label), the `[Android] UpgradePreview` switch that stands in for the desktop's Shift hotkey, and the game-update row, dimmed with the reason while there is nothing to download: the game is current, the check has not answered yet, or it failed (a failed check never reads as current). Each row stays native-sized and is a 48 dp target: the section's spacing grows until a row and its share of the gaps reach it, a transparent hit area covers that share, and a dropdown's own template fits so each option is 48 dp; the geometry re-applies from the clone's native sizes when the dialog opens (on the section's first tick after `OptionsDialogController.OnEnable`, which itself only rereads the settings) or the screen key changes, and at once on a language change, so it shrinks as well as grows (`android.settings.touch_targets`; `android.settings.section_visibility` repeats the hit sizes and measures the navigation column in screen pixels a second later, once the dialog has laid itself out). A failed install undoes what it changed outside the section: the entries, the hidden footer, and the split container's frame. The desktop's other rows are not offered: their features are not on Android. `Host/AndroidTouchUi` creates the Mobile UI's HUD, whose shortcuts put a Collection icon by the settings button in the lobby and in a run and a Ten-Win Builds icon beside it in a run only (layout in [mobile-ui.md](mobile-ui.md)), and puts History in the game's own menus: a tile in the lobby MENU grid (`GameInterop/AndroidNavigationMenuEntry`, after the native tiles) and a row after Resume in the in-run menu (`GameInterop/AndroidFightMenuEntry`, which tightens the fixed column's spacing and dims the row in a combat or replay, as the game dims Return to Main Menu). Both are clones of a native control with the game's behaviours removed (`GameInterop/AndroidNativeMenuClone`); a tap closes the menu, then opens History (`android.native_menu.tile_tapped`, `touch.history.opened reason=native_menu`). `AndroidNativeHud` resolves the active lobby/hero-select or fight-menu anchor for the port, which the HUD searches among scene objects every 0.5 s only while no fight or replay plays and no active gear is held; a gear hidden during a fight is kept, so it is not searched for and its shortcuts are not laid out again when the fight ends, while a search outside fights always lays them out anew (`touch_icon_relayouts`); `AndroidNativeArt` borrows its round frame without native callbacks. The Mobile UI's `TouchHudIcons` owns the linked desktop book/history artwork and the dedicated crowned-card Ten-Win Builds icon, which the csproj embeds under the Mono host's names; the combat clock rasterizes only its play and pause glyphs (`TouchPlaybackIcons`). `AndroidTouchUi.Tick`, from the melon's `OnUpdate`, warms Ten-Win Builds' and Collection's data, ticks History's menu entries and reads a hardware Escape as a back press. These textures, like History's badge atlases, drop their CPU pixel copy once their sprites are cut. Icons hide during combat, card inspection, native popups or an open Main Overlay Panel. The shortcuts, History's menu entries and the three panels have no switch: they are always on. There is no intermediate BPP menu.
- `GameInterop/CardRental/AndroidCardRental` is the host's one rental of the game's card UI prefabs, as the desktop's native card preview: a panel rents a card (template, tier, enchantment) under one of its RectTransforms, re-targets it, and returns it; Core's `CardRentalCore` (`src/BazaarPlusPlus.Core/Cards/CardRental/`, shared with the Mono host's touch surfaces, ADR-0024) keeps the ledger and the per-kind pool, `AndroidCardRentalBackend` instantiates through the game's `AssetLoader` and runs `CardPreviewBase.SetUp`. The melon ticks it every frame, and the Overlay Panel Host releases everything on a scene change, after the panels it closed or told let go of their own, and on a Panel Switch-Off; the periodic summary and `android.card_rental.released` carry the counts, and `card_balanced=true` means every rental came back.
- The Mobile UI's `Mobile/Collection/TouchCollectionPanel` ([collection.md](collection.md), ADR-0025) is the desktop Collection panel on touch, opened from the book icon: Core's `CollectionViewState` drives the same tabs, search, filters, sources, Day chip and hero preference, the sheet is Core's `CollectionTouchLayout` (header with title, tabs, search and close; a drag-scrolled filter rail beside the grid), `TouchCollectionGrid` lays out Core's `CollectionGridLayout` in the column count `CollectionTouchLayout.GridColumns` picks for its width and rents a card per visible cell, and `TouchCollectionInspection` compares tier values and expands available enchantment effects beside the tapped card in the shared inspect sheet; the back key closes the inspection, then an expanded rail picker, before the panel (its modal to the Overlay Panel Host). The host binds its services in `Collection/` (`AndroidCollectionRunReads`, the day-tier source, the hero preference store). `AndroidCollectionCatalog`, the host's `ICollectionCardCatalog`, builds the catalog once per game language and keeps it for the session. It waits for `GameInstance.IsInitialized`, since the game's localization answers in English until then. A pool thread then loads it from `<DataRoot>/CollectionCatalog/` (Core's `CollectionCatalogCacheStore`, one file per language, keyed by the game data and translation manifest ETags, the game version and the mod build), or reads the candidate ids from the game data's `cards` table. On a miss the main thread loads each candidate with the game's `GetCardById` and projects it, 33 ms a frame while the panel waits, one card a frame while the touch UI warms it outside fights and replays, skipping a frame after one slower than 20 ms. Only a build with no failed or missing card, whose language, static data manager and manifests did not change, is saved. `android.collection.catalog_built` logs the source, the counts and per-card p50/p95/max. A catalog from the cache hands the rental no templates, so `TouchCollectionGrid` stops renting after 5 ms a frame.
- The Mobile UI's `Mobile/LiveBuild/TouchLiveBuildPanel` ([mobile-ui.md](mobile-ui.md), ADR-0025) is the desktop's Ten-Win Builds panel (Live Build, [panels.md](panels.md)) on touch, opened from its crowned-card icon; the Mono host mounts the same panel on iOS. It owns Core's `LiveBuildPanelState` for one open and walks the live boards through the port (`GameInterop/AndroidLiveCardSnapshotReader` here) for Core's `LiveCardSnapshotRead`; `TouchLiveBuildView` renders the snapshot as a full sheet: the framed pinned recommendation with its pager in the right operation column (header in the dense fallback), then a framed fixed lower board with one button in the adjacent utility column cycling current board, stash and shop (only the selected board holds rentals), and the corpus, hero, metric cells and guidance in a sidebar. `TouchLiveBuildBoard` is the native board mapper: each planned card rents the game's prefab through the port's card rental (`AndroidCardRental` here) at its socket, and a re-render re-rents only the cards that changed. A tap replaces the desktop's hover: on a shop, stash or board card it toggles a candidate, on a recommended card it opens `TouchLiveBuildInspection`, the card enlarged with its name and text. The composition root owns the ten-win Remote Embedded Catalog (`LiveBuild/AndroidTenWinBuildCatalog`, the desktop's parser, URL and cache file name, the seed linked into this assembly) and its `BuildRecommendationRepository`, and disposes it on stop; the Mobile UI's `TouchLiveBuildData` holds the recommendations and consumes composition-owned `Supporters/AndroidSupporterData` as Core's `ISupporterRotation`, shared with Collection. The latter owns Core's `SupporterCatalogModule` over `Supporters/AndroidSupporterCatalog` (the desktop's parser, URL, cache file and seed, Core's `SupporterCatalogSettings`) and one attribution rotation. The build catalog loads on the touch UI's first frame or when its panel is built (`touch.live_build.data_warmed`); opening Collection warms only the supporter catalog. Each open names the next supporter of one rotation (Core's `BPPSupporterAttribution`) in the sponsor button at the top of the overview; until a list has loaded, it shows the sponsor action. The lower board defaults to current on open and keeps its selection through relayout. `[AndroidDev] BuildCorpusPort`, 0 by default, is a developer seam only: set, the catalog fetches `http://127.0.0.1:<port>/metrics/v6/builds/latest.json`, a corpus a test serves on the Mac through `adb reverse`, and logs `android.live_build.dev_corpus_override` at startup.
- `GameInterop/AndroidCardTemplateText.Description` is the one text an inspected card shows in Collection, Ten-Win Builds and History: the game's own tooltip pipeline (`CardPreviewBase.SetUp`'s order: `DTOUtils.CreateCard`, the tier's attributes, the enchantment for an item, then `CardTooltipData.GetCardDescription` and `BuildCombinedEffectDescription`) at the card's tier and enchantment, so ability values read as in the game's tooltip. Each block renders on its own and a failed one logs `android.card_text.render_failed` with its step; with no block left the text falls back to the template's authored text with its placeholders resolved and its `{aura.*}` tokens dropped (`CollectionAbilityPlaceholders.DropAuraPlaceholders`). That text names its keyword icons as `<sprite name=…>`, which TMP's default sprite asset lacks, so a label showing it hands itself to the Mobile UI's `KeywordSprites.Apply`, which gives it the loaded sprite asset that holds its first icon (`touch.card_text.sprites icon asset`, once per icon; `asset=` empty when none holds it and the icon stays a box). An icon no known asset holds rescans the loaded assets at most once a frame, so one panel build shares one scan, and a later frame scans again in case an asset loaded since.
- `GameInterop/AndroidGameFont` is the font every BPP surface draws with: a copy of the main-menu version label's font (`android.fonts.copied`, once per session), marked `DontUnloadUnusedAsset` because only managed code holds it: a scene load's unused-asset sweep would otherwise destroy it under the panels built with it, and Ten-Win Builds would fail to open in a run. The game loads its Noto CJK fallbacks only in a CJK language, so in English a Chinese supporter name would draw as empty boxes; the first CJK text a surface hands `AndroidGameFont.Cover` loads the game configuration's `zh-CN` fallbacks through Addressables, as the desktop's `NativeGameTypography` does, and appends them to the copy's chain only (`android.fonts.fallbacks_ready`, or `android.fonts.fallbacks_failed` with its reason). The game's own text keeps its chain; a dynamic source font keeps its atlas, since the copy is then static and asks the source first.
- `Host/AndroidOverlayPanels` is the Overlay Panel Host's Android adapter ([panels.md](panels.md), ADR-0022): History, Collection and Ten-Win Builds register with Core's `OverlayPanelHost` through it, and so does the Mobile UI's HUD, which never opens ([mobile-ui.md](mobile-ui.md)), so on Android too at most one is open, every panel closes for combat and does not open in it, and History stays open across a scene change except into a combat. A combat on Android loads no scene, so the frame's combat rule, not the scene policy, is what closes History when one starts (`touch.history.closed reason=combat`). The melon builds it at startup in every mode, feeds it a frame from `OnUpdate`, and calls `SceneLoaded` from `OnSceneWasLoaded`, which advances the scene generation the host reads as its scene token, and lets the host close, notify and release. The melon creates History's `TouchHistoryEntry` and `AndroidTouchUi` registers Collection and creates Ten-Win Builds' `TouchLiveBuildEntry`, each of which registers through the Mobile Platform Port's overlay registration (`AndroidMobilePlatform.RegisterOverlayPanel`, this adapter); Collection and Ten-Win Builds are built on their first open, History at startup, since its coordinator returns from a replay while it is closed. A panel's own close button, a failed relayout, and History's replay start and return go through its handle (the Mobile UI's `MobilePanelHandle`), which carries the string reason the panel's log lines name. Combat, the frame count and the card release are delegates the melon injects; the adapter calls no IL2CPP (ADR-0016).
- Touch fit ([mobile-ui.md](mobile-ui.md), ADR-0018): Core's `Ui/TouchMetrics` turns the screen size, `Screen.dpi` (400 when the device reports none) and `Screen.safeArea` into overlay-canvas units, with 48 dp targets and 12 sp text as floors, and `Ui/TouchChrome` is the frame every surface's layout starts from (sheet, header, type scale, close button, inspect sheet); all of it is Unity-free and tested. the Mobile UI's `TouchScreen` reads the metrics and places a rect; each panel re-lays itself out when the screen key (size, dpi, safe area) changes. The back key closes the top-most BPP surface first: `AndroidOverlayPanels.TryConsumeBack` asks the host to dismiss the open panel's modal layer (History: its note and More dialogs, a card or skill inspection, the skills sheet; Ten-Win Builds and Collection: the inspected card), else close the panel; `Patches/BackKeyPatches` consumes the game's escape for it, so the game's escape menu opens only when none of them is open.
- The Mobile UI's `History/TouchHistoryPanel` is the desktop's History panel ported ([panels.md](panels.md)), which `Host/AndroidMod` composes from `AndroidComposition`, `GameInterop/AndroidLobbyScene` and `GameInterop/AndroidCardTemplateIndex` (Core's `IHistoryCardTemplates`): it owns Core's `HistoryPanelState` and `HistoryPanelCoordinator` for the host's lifetime and renders Core's `HistoryPanelViewModelBuilder` output through `TouchHistoryPanelView`, an owned full-screen uGUI sheet laid out from Core's `HistoryTouchLayout` (Unity-free, from `TouchMetrics`, tested in `tests/HistoryPanelDecisions.Tests/HistoryTouchLayoutTests.cs`) with the Runs, Ghost and Favorites sections, the header supporter action (shared catalog and sponsor link with Collection), the archive and battle rail (drag scroll with inertia, logged as `touch.history.scrolled`), the pagers, the page label, the boards with their messages, a footer of visible actions (delete or remove, favorite or note, skills, replay), the status line, and the More dialog (database status, server check, and the BazaarDB account-link form behind `HistoryPanelDecisions.ResolveAccountLinkGate`). Core's view model shows Record only where the host's `IReplayRecordingAvailability.Supported` is true, which `AndroidNoRecording` is not. It stays open across scenes except into a combat; a scene change closes only the overlays that rent cards (the card inspection and the skills sheet), while the note and More dialogs stay open, a note on its unsaved draft (`TouchHistoryOverlays`, `touch.history.scene_changed`), as on the desktop, whose scene change rebuilds only the boards. It closes on its close button, the back key, a combat or a replay start, and has no switch to turn it off; after a replay it reopens with its selection once the replay session is over and the lobby is active, unless it was closed meanwhile (`touch.history.return_cancelled`); Core's coordinator holds the pending return, and the host only cancels it. Archive rows use `GameInterop/AndroidPortraits` through the port and the Mobile UI's `PortraitView`; rail chips carry the opponent's portrait beside the day; rank badges (rows and rail chips) and finished-run trophies are the game's art from `GameInterop/AndroidRankArt` in the Global scope, through the port's `RankBadge` and `RunTrophy`, bound through the Mobile UI's `ArtImage`, with the rank name or tier as text when a load yields nothing. A run row is four columns: the portrait carrying hero identity, day and mode over a compact timestamp, the rank badge with any Legendary rating, and the trophy or state badge; the two BPP badge atlases are the desktop's PNGs linked into the assembly, marked `DontUnloadUnusedAsset` because a scene load otherwise destroys whichever atlas no row shows at that moment. `AndroidComposition.CreateHistoryDependencies` composes it: the repository on the history database, Ghost sync over History's own `ModApiSession`, which the composition owns and disposes last (a session that cannot be built fails the composition's start, ADR-0006), and Core's `HistoryPanelReplayService` over the replay runtime and `AndroidNoRecording`. Favorites run through Core's `HistoryFavoriteService.OverRuntime`, with the replay copy loaded by the Android replay runtime. Delete is a two-tap confirm and refuses a Seal-protected Run ([panels.md](panels.md)). `TouchHistoryBoard` renders each board from Core's `HistoryBoardProjection` as native cards rented from `GameInterop/CardRental/AndroidCardRental` through the port. A redraw returns only removed or changed cards, using `TouchHistoryBoard.Key` to identify reusable rentals; close, scene change and board reattachment return all rentals. A tap inspects a card in `TouchHistoryInspection`. Skills open the game's own mobile skill overlay through `GameInterop/AndroidNativeSkillOverlay` (the port's `NativeSkillOverlay`): `TouchHistorySkillsSheet` first picks a side (a side without skills is dimmed), and the overlay gets bare `SkillProxyRenderer`s carrying only the card and tier, as the end-of-run summary feeds it. The overlay's canvas is raised over History's, History closes it on the back key, and its proxies are destroyed when it closes. A section, or a Run, with nothing to show says so once in the detail column, without boards or actions.
- `CombatReplay/AndroidCombatReplayRuntime` plays a saved or Ghost battle from History through Core's `SavedReplayPlayback` (ADR-0020), which owns the protocol and holds a saved battle's playback lease for its session. The runtime keeps the `Events.StateChanged` listener, the replay guard hookup and the tick; `CombatReplay/AndroidSavedReplayHost` is the port: the main-thread scope, the cleanup without an opening-state restore, History's five-second row-probe cache, and the `android.replay.*` events and counters fed from the module's notices. `CombatReplay/Bootstrap/AndroidReplayBootstrap` bootstraps the game scene from the lobby, injects the battle (the spawn through `NetMessageProcessor.Handle`, the captured boards onto the card models, the opening events), pushes `ReplayState` and calls `Replay()`, logging each stage as `android.replay.bootstrap_stage`. `Events.StateChanged` delivers the state exit; the only exits are the native recap continue and the `ReplayState.Exit` prefix, which returns to the lobby (ADR-0002). `Patches/AndroidReplayPatches` hold the replay's `Task` seams on IL2CPP (`StartRunAppState.FinalizeRunInitialization` returns the game's completed task; the item setup and board spawn tasks are recorded, never replaced) and its visual seams, each counting its hits for `android.hooks.summary`. `AndroidReplayGuard` keeps any message the intake sees during a replay out of the PvP capture and counts it; run lifecycle is untouched. Not ported yet: the desktop's presentation, audio, VFX and soundtrack warmers and its socket-effect restoration.
- `Host/AndroidMainThread` is the main thread as a `SynchronizationContext`, ticked first in `AndroidMod.OnUpdate`. History's and the replay's entry points run inside its scope (every History control through the Mobile UI's `UiActions.OnTap`, which runs `Host/AndroidUiActions.Run`), so their awaits resume on the main thread; the record chain's pool work keeps its own threads. Game tasks are awaited only through `GameInterop/Il2CppTasks`, which polls them each frame, and History's host ports (`Host/AndroidHistoryPorts`: the clock, the profile account, the `PlayerPrefs` link hint) answer 0 or null off the main thread.
- `GameInterop/AndroidUpgradePreview` owns only the upgrade state BPP enters on a live item. `Patches/CardTooltipPatch` binds it when the primary tooltip actually renders, after the game has admitted the show request; an already active native pedestal preview stays game-owned. The Mobile UI's `Previews/TouchPreviewSwitches` offers a per-tooltip upgrade switch, through `GameInterop/AndroidTooltipPreviewHost`, which the render patch hands each primary tooltip; `[Android] UpgradePreview` chooses its initial value. `AndroidUpgradePreviewValues` keeps the existing leased `AndroidUpgradePreviewValueProjection`, including aura multipliers, over Core's `UpgradePreviewValueMath`: the native `NextTierHasAttribute` gate misses indirect changes such as Sea Shell's `Custom_0`, while BPP projects every affected token and cooldown. A render returns its lease even on failure. Closing or replacing the tooltip, a scene load, combat, or opening a Main Overlay Panel releases BPP's preview. Mobile input can dismiss the tooltip after a BPP button's onClick; `CardTooltipHidePatch` suppresses that dismissal only while the focused app's pointer is inside the visible switches or expanded effects, outside combat. Back clears that protection before handing a collapsed inspection back to native input. The enchant preview follows the desktop's `[EnchantPreview] Mode` (OFF/AUTO/ON, default ON), a Choice row in the native settings section: the Mobile UI's `Previews/TouchEnchantPreview.InlineCandidates` applies Core's `EnchantPreviewVisibility`, and under AUTO `GameInterop/AndroidChoicePedestals` reads the offered pedestal (choice, encounter, level-up or pedestal screen) for Core's `ChoiceScreenPedestalResolver`, keeping only the enchantment(s) an enchant pedestal applies. Those enchantments are listed in the tooltip's main text, expanded, one line each at the item's current quality: `CardTooltipRenderPatch` builds the section when the contents render and `EnchantPreviewPassivePatch` appends it below the native passive text, sized by `TouchMetrics.ReadablePercent`; a held upgrade preview keeps it off, as on the desktop. The touch actions are Collection toggle rows appended to the native mobile tooltip's description scroll: the upgrade switch, and, only for an item whose main text lists no enchantments (mode OFF, or AUTO with no enchant pedestal), an enchantment switch with its effects collapsed below it. `GameInterop/AndroidEnchantPreviewHost.Candidates` offers an eligible item's available enchantments, excluding its current enchantment; `TouchEnchantPreview.Build` lazily renders the live card at its current and higher qualities through the adapter's `RenderEffect`, then merges changing numbers through `CollectionTierTooltipTextMerger`. The expanded section uses native effect text and enchantment name colours, shares the native description scroll at body size, and collapses first on Back. Collection continues using the same `RenderEffect` with a static card and no run context.
- `Game/AndroidQuestPreview` appends completion rewards in native quest rows; `AndroidAggregateItemPreview` adds missing-type hints for aggregate items. Both read the shared Detailed Preview switch and restore or regenerate native text when disabled. `Game/AndroidEncounterPreview` reads the static-data SQLite file on a background task, uses Core's `EncounterChoicePlanParser` for event choice/outcome structure, and renders current localized descriptions into the native passive block. It reads the same Detailed Preview setting. Android covers event choices and random outcomes with day/hero/ownership gates, and merchants: the background read keeps each merchant's quality rule (`EncounterChoicePlanParser.TryParseMerchantTierRule`, the JSON form of the desktop's `EncounterMerchantTierResolver`), and its tooltip shows the pinned tier or the day's tier odds through Core's `EncounterPreviewTextFormatter.BuildQualityLine`. The odds are `GameInterop/AndroidDayTiers`, the run's game mode's `ItemSkillSpawnTierPercantagesByDay` as the desktop's `GameDataDayTierSource` reads it, also passed to the event formatter. Dynamic-pool constraint summaries (the parser's reward-pool callback) and hero level-up rewards remain desktop-only.
- `Game/AndroidCombatStatus` feeds Core's `CombatStatusBarState` from native CombatStarted/CombatEnded events and the per-frame `FinalBlowSlowDownController.Process` patch. The clock is logical simulation time: each processed frame is 50 ms and the first frame is zero. Native pause stops frame delivery; speed changes playback pace rather than the clock's units. The Mobile UI's `Hud/TouchCombatClock` shows time with touch pause/resume and speed buttons right of the vault ([mobile-ui.md](mobile-ui.md)); it hides while a card is inspected. The default-on Android combat-timer switch controls its visibility and releases BPP's pause when disabled. Scene changes reset the displayed battle and release an owned pause without resetting preferred speed; as on the desktop, the panel stays shown for the whole run or replay and keeps a finished fight's time until the next one starts. The speed button cycles the three supported speeds. Only BPP-owned pauses are resumed by cleanup.
- `Lobby/AndroidVersionCheck` runs on every `MainMenuScene` load: Core's `MainMenuSelfUpdate` over the `android-aarch64` Platform Release Manifest ([self-update.md](self-update.md)), the status on the version label (its new-APK text localized), and the APK this copy needs (Core's `AndroidGameUpdate.Needed`): a newer game by build number in `game.gameVersion` against `Application.version`, or the same game with a release the self-update decision calls `ManualUpdate` (the BPP runtime inside the APK changed); an APK for an older game is never offered. The game-update row names that reason and opens the APK's URL. `Lobby/AndroidApkUpdatePrompt` asks once per published product version in the game's own generic popup (`PopupManager.ShowGenericPopup`), two seconds after the menu loads and only while no popup or panel covers it, and records the version under the Data Root (`android-apk-prompt.txt`). `Patches/UpdateRequiredPatch` sees the game refuse a run for an outdated client (`ServersHealthService.IsUpdateRequired`, asked only from `StartRunAppState.CheckClientVersion`); the game's message points at a store that cannot install over a BPP-signed APK, so once its popup closes the prompt asks again that session, or says the APK is on its way when BPP has not published it yet. `[Dev] ReleaseManifestPort` (0, off, by default) points the check at `http://127.0.0.1:<port>/`, so a device test serves a manifest from the developer's machine through `adb reverse` and shows the row active; it takes a port rather than a URL so it can only ever reach loopback, and `android.version_check.dev_manifest` warns at start while it is set.
- Shared code comes from Core's `net10.0` output, with Storage and ModApi through it; the host links no Core or desktop source. `just mod::android-deploy` pushes the build to the `melonloader` paths of the Payload Inventory (root `GLOSSARY.md`), read through the generated `Payload.targets`: BPP's assemblies into `MelonLoader/Mods/`, third-party ones into `MelonLoader/UserLibs/`, the Updater into `MelonLoader/Plugins/` ([self-update.md](self-update.md)).

## Gotchas

- SQLite's native `libe_sqlite3.so` must sit in the APK's `lib/arm64-v8a/` (the Android release's injection step adds it). External storage is `noexec`, so `UserLibs/` cannot carry it; a deploy to an APK without it fails at the first store open.
- A `T?` an IL2CPP getter returns arrives as an `Il2CppSystem.Nullable` proxy over a boxed `T`, whose `HasValue` and `Value` are wrong: every player attribute read as 0 and opponent ranks came out shifted. Read the dictionary or field behind it, or go through `AndroidGameIds.Unboxed`; the board captures read every card's section, socket, tier, size, and enchantment that way. The other direction throws: a generated setter or constructor unboxes its `Il2CppSystem.Nullable` argument through `Il2CppObjectBaseToPtrNotNull`, so passing `null` for an absent value raised a `NullReferenceException` and the replay lost its opponent portrait. Pass `AndroidGameIds.Optional`, an empty proxy for an absent value.
- A `bool` read through an IL2CPP struct proxy, such as a `ValueTuple`'s `Item2`, read as true in C#, yet the game method it was passed back into acted as if it were false, where a literal `true` worked: the upgrade preview handed the typography's `renderedWithIcon` to `TooltipTypography.ColorKeywords` and drew a second keyword icon after every value (`Damage` after `25»45`). Only that symptom was observed, not its mechanism. Pass such a bool through `AndroidGameIds.Canonical`, which rebuilds it as a fresh `bool`; that ended the symptom on the device.
- Every Android store opens the database with `AndroidComposition.DatabaseOptions` (`DELETE`): a Storage store given no options would switch the file to WAL. Core's seal coordinator, upload pump, and composer therefore take the options as a required argument. `DELETE` keeps one self-contained file that `adb pull` reads whole. WAL opened, wrote, and read back on the emulator's FUSE Data Root, but that is one process on one device, not a reason to switch.
- A message here is an IL2CPP proxy, which the managed MessagePack cannot read: Replay Payload bytes come from the game's own serializer (`Il2CppMessagePack.MessagePackSerializer.Serialize<T>` with the concrete message type and `MessagePackConfig.Options`, as the desktop's `DesktopPvpBattleReads`). That runs on the main thread only. Nothing decodes the bytes back at capture (dropped for the battle hand-off hitch in #479; its share of that hitch was not measured): the game's serializer first reads them at playback (`CombatReplay/AndroidCombatReplayLoader`), so a payload it cannot read fails that start (`combat_replay.playback.failed`), by which point it may already be in a Bundle. The seal worker is a pool thread that must not call into IL2CPP, so `AndroidPvpBattleEvidence` checks a payload for well-formed MessagePack and resolves card enums from the interop enums, which are managed.
- Harmony can replace the IL2CPP `CombatSimHandler.Simulate` `Task`, as the desktop's `CombatSimPatch` does for replay: a prefix that returned an `Il2CppSystem.Threading.Tasks.TaskCompletionSource<Object>`'s `Task` held the combat until BPP completed it from `OnUpdate` after running the original 3 s later, and the game awaited it and finished the fight (#360 spike, removed after the measurement).
- LemonLoader installs no managed `SynchronizationContext`: an `await` started from a melon callback resumes on a pool thread, where a call into IL2CPP is a native fault, not an exception. History's coordinator and Core's `SavedReplayPlayback` publish on the caller's context, so they run under `AndroidMainThread`. Awaiting an `Il2CppSystem` task directly compiles (its awaiter implements `INotifyCompletion`) but resumes outside the pump; `AndroidHostThreadingRuleTests` holds the host's IL to `Il2CppTasks` and keeps the Core module's awaits off the pool.
- The online Android build has no `SocketBehavior`: the replay's network host is `Il2CppNetworking.NetworkManager`. The game's private fields the desktop reaches by reflection surface as interop properties (`AppState._gameSimHandler`, `RunManager._baseBoardReference`, `GameMessageHandler`1._handledMessages`).
- Ghost sync counts a downloaded snapshot's templates on a pool thread, where the static data manager must not be called. It reads `GameInterop/AndroidCardTemplateIndex`, which answers true until it is built rather than build itself off the thread. When History opens, the main thread reads only the manager's `_dbPath` and a pool thread reads the ids from that game-data file's `cards` table; the manager's own `GetCardMap` deserializes every card and froze the main thread for 26 s on the emulator.
- `new Il2CppStringArray(0)` and `new Il2CppStructArray<Vector3>(4)` bind the int literal to the interop array's `(IntPtr pointer)` constructor, since `int` converts implicitly to `nint`, and wrap address 0 or 4: History's `GetWorldCorners` buffer crashed the game with a SIGSEGV and the replay's empty opponent loadout lost its portrait. Size an interop array with a `long` (`0L`, `4L`); `AndroidHostInteropRuleTests` holds the host's IL to that.
- A reader of the DELETE-mode database cannot overlap a write, so History's repository opens it with `busy_timeout` and a page read during a write burst waits instead of failing.
- A uGUI `GameObject` holds one `Graphic`: a second `Image` on a rect that already has one is null, and History's skills sheet threw in its constructor. `TouchHistoryUi.TapArea` takes the fill so the hit area is the rect's only `Graphic`.
- `android.hooks.summary` is checked every `AndroidMod.SummaryIntervalMs` and written only when one of its counts changed since the last one written; each scene load forces one within `AndroidMod.SceneSummaryDelayMs` (`AndroidMod.OnSceneWasLoaded`). A stretch of `Latest.log` without summaries means nothing was counted, not a stalled host, and the smoke waits for the summary that follows `MainMenuScene`, not for a count of them.
- An unreadable `BazaarPlusPlus.cfg` still installs the hooks (`PatchMode` falls back to `enabled`) but starts no record chain: `android.record_chain.start_failed` follows `android.settings.load_failed`, and nothing is recorded, sealed, or uploaded until the file reads.
- The startup `android.build_channel.probe` logs `server_option=missing` on every online build, the Online answer: as on desktop, only the PTR fork of `Config` declares `ServerOption`. It does not show whether Il2CppInterop exposes the nested type; only a PTR or staging Android capture can.
- A managed `MonoBehaviour` exists in IL2CPP only after `ClassInjector.RegisterTypeInIl2Cpp<T>()`, and the type needs the `(IntPtr)` constructor; `AddComponent<T>` on an unregistered type fails. Unity calls the injected `Update`. Its `StartCoroutine` takes an `Il2CppSystem.Collections.IEnumerator`, not a managed iterator: run a managed coroutine through `MelonCoroutines.Start`, where both `yield return null` and `WaitForSeconds` resume.
- `TooltipParentComponent.HideCardTooltipController` returns early while a card-to-card transition runs, and tapping a second card calls it during that transition. Releasing the upgrade preview on every call left the new card's tooltip showing next-tier values with its controller out of preview, so `AndroidUpgradePreview` releases only when the tooltip's `CurrentCard` was cleared.
- Every `SceneLoader.LoadScene` hides the card tooltip before it loads anything (`LoadingStarted` raises `LoadAddressableSceneStarted`, which `TooltipParentComponent` answers with `HideCardTooltipController`), so a held upgrade preview normally ends as `tooltip_hidden`, and pausing the app ends it the same way. Only a load that starts during the 0.25 s card-to-card transition, which also runs when the first tooltip opens, keeps the hold past that early-returning hide; `AndroidMod.OnSceneWasLoaded` then releases it as `scene_changed`, with the controller still alive because the new scene loads before the old one unloads. A probe that calls the game's own `SceneLoader.LoadScene` inside that window exercised this on the device (#402); no player-reachable path was observed, but keep that release defensively, or the controller stays in preview and `upgrade_preview_entered` runs ahead of `exited`. A network cut does not load a scene either: the game reconnects in place, even after nine minutes in airplane mode, and the resync it receives on reconnect hides the held tooltip, which releases it as `tooltip_hidden` (#400). Only a Resume from the main menu while offline makes the game change scene by itself: it loads `Gameplay` with no run, and about a minute later returns to `MainMenuScene` with its Connection Issues alert (`GoToMainMenuAndShowConnectionAlert`). That is the path the #396 and #397 evidence uses for a game-started scene change with a touch panel open; the run resumes normally once the network is back. Opening the settings dialog, from the gear or the back key's pause menu, hides the tooltip the same way, so the `switched_off` release never runs during a hold; `AndroidSettingsDockTests` covers it.
- A rented card belongs to the asset scope it was instantiated in, and a lobby ↔ run scene change releases the `Current` scope's assets, whitening every instance of it, live or pooled; a re-`SetUp` does not bring the art back. The backend instantiates in `AssetScope.Global` (a real `Il2CppSystem.Nullable<AssetScope>`; the generated method rejects null) and the rental still destroys its pool on every scene load. The instantiate and set-up tasks are IL2CPP `Task`s polled from the frame tick, never awaited (#396 spike; its findings are in the issue's comments and its capture in git history).
- A card prefab carries its own `Canvas`, so a `RectMask2D` above it does not clip it: the Collection grid draws first and opaque header and footer bands over it hide the cards scrolled past its edges. The backend disables its `GraphicRaycaster`s and turns raycasts off through a `CanvasGroup`, or the card eats the cell's tap and the scroll drag. Its `AspectRatioFitter` resizes the root against the parent every layout pass, so the backend sizes the root itself and disables the fitter.
- The first `JsonGameDataManager.GetCardMap()` call of a game session held the main thread 5–35 s on the emulator while the game deserialized every card; `GetCardById` reads and deserializes one row and keeps it. No Android code calls `GetCardMap`; the game itself calls it only for its encounter ban popup (`EncounterBanPopupController`). Text typed into the search field through `adb shell input text` reached the filter only on the soft keyboard's OK; a real keyboard was not tried.
- The Android back key reaches the game as Escape, and `PopupManager.HandleEscape` opens the escape menu over whatever BPP shows. `BackKeyPatches` prefixes it and `PopupManager.OnOpenSettings`; `AndroidTouchUi.Tick` also reads `Keyboard.escapeKey` each frame. The answer must be synchronous, since the prefix decides whether the game's handler runs, so the host's escape runs inside the hook rather than on the next frame, and `AndroidOverlayPanels` stamps a consumed press with its frame so one press seen by both closes only one surface.
- Live Build's refresh awaits the catalog with `ConfigureAwait(false)` and resumes on a pool thread; `TouchLiveBuildPanel` posts the result to the main thread through the port (`AndroidMainThread` here) before `LiveBuildPanelState.CompleteRefresh`, and `touch.live_build.refresh_completed` logs `fetched_on_main_thread` and `completed_on_main_thread`. A rented card's own `Canvas` escapes the list's `RectMask2D` here too, so the pinned row and an opaque band under the list hide the cards scrolled past its edges.
- Native tooltip text carries `<line-height>` and inline size tags. The expanded enchantment section uses the same `ChipFlow.Definitions` renderer as Collection, with body-sized labels and measured wrapped effects; it never appends an unbounded list to the native passive block.
- The settings dialog's `ScrollSpyController` wires the sections and navigation toggles of its `_entries` in `Awake`, so the BazaarPlusPlus section and its entry are cloned and appended to that array in a prefix, as on the desktop. Also as on the desktop, the dialog's "changes are saved automatically" footer is hidden and the split container grown into the space, or the added entry pushes the last navigation button off the column; measure that space from the rects' own corners, since the container's bounds include its scrolled content.
- A `TMP_Dropdown` builds its open list from the template's `Toggle` item: each option takes the item's height and keeps its padding inside the content, and the list shrinks to its items but never grows past the template. Growing only the item clipped the first or last option; the content and the template grow with it.
- A Harmony postfix on `CinemachineBrain.PushStateToUnityCamera`, which takes a `ref CameraState`, crashed the game with a SIGSEGV in `libil2cpp.so` as the Gameplay scene loaded. `ScreenFillFieldOfViewPatch` therefore follows the brain's argument-less `LateUpdate` instead.
