# Android Host

`BazaarPlusPlus.Android` (`net10.0`) is the Android Host (root `CONTEXT.md`, Host). It is a MelonMod (`src/BazaarPlusPlus.Android/Host/AndroidMod.cs`) compiled against the Interop Snapshot and the Loader Release (`build/InteropPath.props`), never against `Managed/`.

## Shape

- `Host/` owns the loader entry, the `BppLog` exit over MelonLogger (`MelonLogSink`, scope `Android`), the settings store over `MelonLoader/UserData/BazaarPlusPlus.cfg` (`IniSettingsStore`) and the Data Root (`AndroidPaths`): `BazaarPlusPlusV6` beside the MelonLoader base directory.
- `AndroidComposition` builds Core's `CoreComposition` over that Data Root and registers the record chain and the Bundle path, in start order: Core's `RunLifecycleModule` and `RunLoggingModule` over the IL2CPP probes in `GameInterop/`, then Core's `BundleSealCoordinator`. Core's `UploadPump` starts after them and is ticked from `AndroidMod.OnUpdate`; it sends each sealed Bundle to `POST /bundles` with the `android-aarch64` User-Agent token. Bundles are Run-only: the host takes no end-of-run screenshot.
- `AndroidPvpBattleCapture` frames each PvP battle from the net messages (opening `PVPCombat` game sim, combat sim, next game sim), as the desktop's `CombatReplayCaptureService` does. At the opening it takes the four board captures (`AndroidPvpBattleSnapshots`, in Core's `PvpBattleCardSetDocument` shape), and retries an empty or failed player set live at the combat sim and the close under Core's `PvpBattleCaptureRule`, the desktop's rule; it serializes each message as it arrives (`AndroidReplayMessages`), and saves the Replay Payload to `CombatReplays/`, then the battle through Storage's `PvpBattleSqliteStore`, under the persistence lease of Core's `ReplayPayloadOperationGate`. `android.pvp_battle.recorded` logs each set's label and count and how long the saves held the main thread.
- On every start Core's `ReplayPayloadMaintenanceService` sweeps `CombatReplays/` once on a pool thread, as on the desktop: orphan files, lost files, and the retention of `ReplayPayloadRetentionPolicy`.
- The Bundle composer is Core's `RunPayloadComposer`; the host supplies only `AndroidPvpBattleEvidence` (card enum values, Replay Payload check).
- `Patches/` install per class under the `[Android] PatchMode` setting (`enabled`, `observe`, `disabled`). A class that fails to install degrades only itself. `NetMessageReceivePatch` is the message intake (run initialization, battle capture); `CombatSimulatePatch` publishes `CombatSimObserved`.
- In the `enabled` mode the host adds the interaction features, which touch replaces the desktop's hotkeys for. `Ui/AndroidTouchUi` is a BPP button on the left edge that opens one panel: Settings switches `[Android] UpgradePreview`, `[EnchantPreview] Mode` (`Always` or `Off`; the desktop-only `AutoOnPedestalChoice` reads as `Off`, since the host has no pedestal probe) and `[Android] CollectionPanel`, and shows the game-update row; History lists the Data Root's Runs and the selected Run's battles through `History/AndroidHistoryReader`, read-only; a Run row is the desktop's, Storage's `HistoryRunColumns.Select` read through `HistoryPanelRowMapper.ReadRun`, and only the reader's offset paging is its own. `[Android] TouchMenu` hides the button. The panel and its controls are BPP's own uGUI (`Ui/AndroidUiKit`), not the game's menus.
- `GameInterop/CardRental/AndroidCardRental` is the host's one rental of the game's card UI prefabs, as the desktop's native card preview: a panel rents a card (template, tier, enchantment) under one of its RectTransforms, re-targets it, and returns it; `CardRentalCore` keeps the ledger and the per-kind pool, `AndroidCardRentalBackend` instantiates through the game's `AssetLoader` and runs `CardPreviewBase.SetUp`. The melon ticks it every frame and `AndroidMod.OnSceneWasLoaded` releases everything after the touch UI closed its panels; the periodic summary and `android.card_rental.released` carry the counts, and `card_balanced=true` means every rental came back.
- `Collection/AndroidCollectionPanel` is the desktop Collection panel on touch ([collection.md](collection.md)), opened from the menu's Card Collection tab while `[Android] CollectionPanel` is on: Core's `CollectionViewState` drives the same tabs, search, filters, sources, Day chip and hero preference, `AndroidCollectionGrid` lays out Core's `CollectionGridLayout` and rents a card per visible cell, and `AndroidCollectionInspection` re-targets the tapped card to the chosen tier and enchantment. `AndroidCollectionCatalog` builds the catalog once per game language and keeps it for the session. Switching the setting off closes the panel and destroys the pooled cards.
- `GameInterop/AndroidUpgradePreview` puts the item whose tooltip a tap opens into the game's own upgrade preview (`CardController.EnterUpgradePreview`), which renders its next-tier values; it holds at most one controller and releases it when another card opens, the tooltip closes, the switch turns off, or a scene loads. Each render of the held item's tooltip leases a `GameInterop/AndroidUpgradePreviewValueProjection` (the desktop's value projection, aura multipliers included, over Core's `UpgradePreviewValueMath`), keyed by the tooltip data's pointer and returned when the render ends; `AndroidUpgradePreviewValues` renders that tooltip's text with BPP's next-tier values, which the game leaves out for literal ability and aura values, and sets its cooldown clock. The periodic summary's `upgrade_values_leased` and `upgrade_values_returned` match whenever no tooltip is rendering. `GameInterop/AndroidEnchantPreview` renders each enchantment's text against the game's lock-mode preview card (`CardExtensions.ApplyPreviewEnchantment`) and appends it to that render's passive block.
- `Lobby/AndroidVersionCheck` runs on every `MainMenuScene` load: Core's `MainMenuSelfUpdate` over the `android-aarch64` Platform Release Manifest ([self-update.md](self-update.md)), the status on the version label, and, when the build number in the manifest's `game.gameVersion` is above the one in the running game's `Application.version`, the game-update row that opens the APK's URL.
- Shared code comes from Core's `net10.0` output, with Storage and ModApi through it; the host links no Core or desktop source. `just mod::android-deploy` pushes the build to the `melonloader` paths of the Payload Inventory (root `CONTEXT.md`), read through the generated `Payload.targets`: BPP's assemblies into `MelonLoader/Mods/`, third-party ones into `MelonLoader/UserLibs/`, the Updater into `MelonLoader/Plugins/` ([self-update.md](self-update.md)).

Not on Android yet: Ghost import, replay playback, favorites, and the native boards of the desktop History panel; and Live Build. Both can rent cards through `AndroidCardRental` now.

## Build and test

`tests/AndroidHost.Tests` fails if the compiled host references BepInEx or a desktop assembly, or defines a BPP type outside `BazaarPlusPlus.Android` (a linked source). It also loads the compiled host and runs the code that never calls into IL2CPP (ADR-0016): the History reader, the Bundle evidence over the interop enums, the composer over the DELETE-mode database, the replay sweep, and the card rental's ledger over a fake backend (`CardRentalCoreTests`). It runs in `just mod::test-core`, the suites that need no Managed snapshot, and in the `mod-android` CI lane, with the two goldens on the `net10.0` binding this host ships: `tests/BundleV6Codec.Net10.Tests` (the Run segment) and `tests/RunLoggingPipeline.Net10.Tests` (the history database), each of which must reproduce the desktop binding's goldens byte for byte. `just mod::android-*` drives one device, and `just mod::android-setting <section> <key> <value>` switches one feature for an on/off capture; `just mod::android-smoke <mode>` asserts injection, hook hit, and feature on it before a release; no CI lane runs a device ([development guide](../../../docs/development.md#android-冒烟)).

## Gotchas

- SQLite's native `libe_sqlite3.so` must sit in the APK's `lib/arm64-v8a/` (the Android release's injection step adds it). External storage is `noexec`, so `UserLibs/` cannot carry it; a deploy to an APK without it fails at the first store open.
- A `T?` an IL2CPP getter returns arrives as an `Il2CppSystem.Nullable` proxy over a boxed `T`, whose `HasValue` and `Value` are wrong: every player attribute read as 0 and opponent ranks came out shifted. Read the dictionary or field behind it, or go through `AndroidGameIds.Unboxed`; the board captures read every card's section, socket, tier, size, and enchantment that way.
- A `bool` read through an IL2CPP struct proxy, such as a `ValueTuple`'s `Item2`, reads as true in C#, yet passed back into a game method the game took it as false where a literal `true` worked: the upgrade preview handed the typography's `renderedWithIcon` to `TooltipTypography.ColorKeywords` and drew a second keyword icon after every value (`Damage` after `25»45`). Pass such a bool through `AndroidGameIds.Canonical` first.
- Every Android store opens the database with `AndroidComposition.DatabaseOptions` (`DELETE`): a Storage store given no options would switch the file to WAL. Core's seal coordinator, upload pump, and composer therefore take the options as a required argument. `DELETE` keeps one self-contained file that `adb pull` reads whole. WAL opened, wrote, and read back on the emulator's FUSE Data Root, but that is one process on one device, not a reason to switch.
- A message here is an IL2CPP proxy, which the managed MessagePack cannot read: Replay Payload bytes come from the game's own serializer (`Il2CppMessagePack.MessagePackSerializer.Serialize<T>` with the concrete message type and `MessagePackConfig.Options`, as the desktop's `PvpReplayPayloadFactory`), and each is decoded back before the payload is kept. That runs on the main thread only. The seal worker is a pool thread that must not call into IL2CPP, so `AndroidPvpBattleEvidence` checks a payload for well-formed MessagePack and resolves card enums from the interop enums, which are managed.
- Harmony can replace the IL2CPP `CombatSimHandler.Simulate` `Task`, as the desktop's `CombatSimPatch` does for replay: a prefix that returned an `Il2CppSystem.Threading.Tasks.TaskCompletionSource<Object>`'s `Task` held the combat until BPP completed it from `OnUpdate` after running the original 3 s later, and the game awaited it and finished the fight (#360 spike, removed after the measurement).
- An unreadable `BazaarPlusPlus.cfg` still installs the hooks (`PatchMode` falls back to `enabled`) but starts no record chain: `android.record_chain.start_failed` follows `android.settings.load_failed`, and nothing is recorded, sealed, or uploaded until the file reads.
- The startup `android.build_channel.probe` logs `server_option=missing` on every online build, the Online answer: as on desktop, only the PTR fork of `Config` declares `ServerOption`. It does not show whether Il2CppInterop exposes the nested type; only a PTR or staging Android capture can.
- A managed `MonoBehaviour` exists in IL2CPP only after `ClassInjector.RegisterTypeInIl2Cpp<T>()`, and the type needs the `(IntPtr)` constructor; `AddComponent<T>` on an unregistered type fails. Unity calls the injected `Update`. Its `StartCoroutine` takes an `Il2CppSystem.Collections.IEnumerator`, not a managed iterator: run a managed coroutine through `MelonCoroutines.Start`, where both `yield return null` and `WaitForSeconds` resume.
- `TooltipParentComponent.HideCardTooltipController` returns early while a card-to-card transition runs, and tapping a second card calls it during that transition. Releasing the upgrade preview on every call left the new card's tooltip showing next-tier values with its controller out of preview, so `AndroidUpgradePreview` releases only when the tooltip's `CurrentCard` was cleared.
- Every `SceneLoader.LoadScene` hides the card tooltip before it loads anything (`LoadingStarted` raises `LoadAddressableSceneStarted`, which `TooltipParentComponent` answers with `HideCardTooltipController`), so a held upgrade preview normally ends as `tooltip_hidden`, and pausing the app ends it the same way. Only a load that starts during the 0.25 s card-to-card transition, which also runs when the first tooltip opens, keeps the hold past that early-returning hide; `AndroidMod.OnSceneWasLoaded` then releases it as `scene_changed`, with the controller still alive because the new scene loads before the old one unloads. A probe that calls the game's own `SceneLoader.LoadScene` inside that window exercised this on the device (#402); no player-reachable path was observed, but keep that release defensively, or the controller stays in preview and `upgrade_preview_entered` runs ahead of `exited`.
- A rented card belongs to the asset scope it was instantiated in, and a lobby ↔ run scene change releases the `Current` scope's assets, whitening every instance of it, live or pooled; a re-`SetUp` does not bring the art back. The backend instantiates in `AssetScope.Global` (a real `Il2CppSystem.Nullable<AssetScope>`; the generated method rejects null) and the rental still destroys its pool on every scene load. The instantiate and set-up tasks are IL2CPP `Task`s polled from the frame tick, never awaited (#396 spike, `artifacts/android/396-collection/spike/`).
- A card prefab carries its own `Canvas`, so a `RectMask2D` above it does not clip it: the Collection grid draws first and opaque header and footer bands over it hide the cards scrolled past its edges. The backend disables its `GraphicRaycaster`s and turns raycasts off through a `CanvasGroup`, or the card eats the cell's tap and the scroll drag. Its `AspectRatioFitter` resizes the root against the parent every layout pass, so the backend sizes the root itself and disables the fitter.
- The first `JsonGameDataManager.GetCardMap()` call of a game session holds the main thread 5–35 s on the emulator while the game deserializes every card (`android.collection.catalog_built map_ms`); the panel shows its loading text for a frame first. The TMP search field of the soft keyboard commits on the keyboard's OK, so the filter applies then, not per keystroke.
- The game's rendered tooltip text carries its own `<line-height=1.6em>` and `<size>` tags for full-size text. Appended at reduced size, they kept full-height lines and the enchant list overflowed a phone tooltip; `AndroidEnchantPreview` strips the line heights and scales the sizes (`ItemEnchantPreviewText.ScaleInlineSizes`).
