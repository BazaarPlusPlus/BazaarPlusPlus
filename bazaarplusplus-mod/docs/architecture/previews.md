# Encounter Preview, Card Preview, And Tooltips

The Encounter Preview query boundary, the native card preview owning module, and the tooltip presentation surfaces. `GameInterop/Tooltips` holds two adapters that must not be merged.

Core's `EncounterPreviewModule` is the one owner of event, encounter-step, and hero-level preview semantics on both hosts: the Detailed Preview switch, the combat gate, routing by card type, merchants, and final presentation; both query kinds resolve to the single `EncounterPreviewResult` record (`src/BazaarPlusPlus.Core/Game/EncounterPreview/EncounterPreviewModule.cs`). Its queries take only a template id and card type or a level and hero, plus native text already present at the patch boundary; game state (the current plans with the day tiers and live values of the same source, hero, inventory, keyword colours, each template's shown texts) is read through `IEncounterPreviewReads`, which each host implements once: the desktop's `DesktopEncounterPreviewReads` over `IEncounterPreviewGameRuntime`, Android's `AndroidEncounterPreviewReads`. On the desktop, `EncounterPreviewPlanPublisher` owns cache identity, plan loading or compilation, and publication (`src/BazaarPlusPlus/Game/EncounterPreview/EncounterPreviewPlanPublisher.cs`). Beginning a source generation first removes the old snapshot; generation checks prevent a superseded load from publishing, while a successful compile remains published with degraded status if its cache write fails (`src/BazaarPlusPlus.Core/Game/EncounterPreview/EncounterPreviewPlanRegistry.cs`). The disk cache stays because a cold start is slow: measured 2026-10-03 on macOS, game `1.0.12575-staging-macos-arm64-fecb8f8e` (Steam build 25661913), time-to-ready from the observed new source to `event_preview.plans.ready` was 6.1 s median cold (6106/5946/6256 ms; compile itself 0.55 s, the rest loading the card map the compiler needs, which a cache hit skips) against 0.17 s warm (181/164 ms), while the main thread saw 83–86 frames over 50 ms with a worst frame of 466 ms cold versus 4 slow frames and a worst of 200 ms warm — a temporary probe in `EncounterPreviewStaticDataObserver.Update` timed the window and summed `Time.unscaledDeltaTime` per frame (#161).

Everything downstream of the game's data compiles into Core (`src/BazaarPlusPlus.Core/Game/EncounterPreview/`), typed on card facets (ADR-0015): the plans, snapshot, registry and disk cache, the reward filter and the result-text parser, the event and level-up resolvers and formatters, tooltip prose markup, and card-count requirements over the `EncounterInventory` snapshot (tag names as strings). The day-tier weight table is the Core snapshot `GameDataDayTierTable` (`src/BazaarPlusPlus.Core/GameState/`). Both hosts read a card's plans off its static-data JSON through Core's `EncounterPreviewCardReader`: its kind, heroes, texts and dealt reward, and for an event its choices or random outcomes and, for a merchant, the quality rule it sells by (`EncounterPreviewEventPlan.Merchant`). The desktop has typed templates, so `EncounterStructuredParser` writes each one back with the settings the game reads static data with (`BazaarJsonSerializerSettings`, which writes every `$type` discriminator and enum name), and `EncounterPreviewCardRoundTripTests` holds that JSON to the card table Android's raw rows are held to (`tests/Shared/fixtures/encounter-preview-cards.json`). The host keeps what reads game types: the plan compiler with its typed level-up route and the loader, that serializer route, the publisher, its reads and its game runtime, and `EncounterPreviewGameText`, which captures static ability values and is installed as `EncounterPreviewLocalization.TextLocalizer`, the game's localization port; unset, a title or description falls back to its English text, then its key. The disk cache persists facets by member name, never their integers.

`EncounterPreviewStaticDataObserver` is only the Unity frame adapter that reports a newly ready source to the publisher (`src/BazaarPlusPlus/Game/EncounterPreview/EncounterPreviewStaticDataObserver.cs`). Tooltip patches receive the module through the `BppPatchFeatures` bundle and consume semantic results; they do not read plans, static-data maps, inventory, or CollectionPanel formatters (`src/BazaarPlusPlus/Patches/BppPatchFeatures.cs`, `src/BazaarPlusPlus/Patches/Tooltips/`). `CardAbilityValueReader` centralizes the shared reflection seam over game-authored ability/aura action and attribute values; Event Preview and Collection keep their separate localization and typography policies (`src/BazaarPlusPlus/GameInterop/Cards/CardAbilityValueReader.cs`). `GameDataDayTierResolver` is the shared GameInterop day-tier owner for Collection's Day gate and Event Preview: it exposes typed unavailable states, retries transient readiness, and rejects an Event Preview query whose plan source is no longer the current manager; its generation-keyed caching and `MaximumTier` semantics are pinned in `docs/MEMORY.md` (`src/BazaarPlusPlus/GameInterop/DayTiers/`).

`GameInterop/CardPreview` is the owning module for native card prefab selection, instantiation, setup/resize, reflection, hover state, tooltip replacement, pooling, and destruction. Production callers see only `INativeCardPreviewHost`, a per-owner `INativeCardPreviewScope`, and opaque `INativeCardPreviewSession` intent operations (`src/BazaarPlusPlus/GameInterop/CardPreview/NativeCardPreviewContracts.cs`). Each scope has its own pool: closing rejects new acquisitions, cancels and waits outstanding setup, invalidates/destroys active sessions, then destroys idle objects; a session released after closing cannot re-enter the pool (`src/BazaarPlusPlus/GameInterop/CardPreview/NativeCardPreviewScopeLifetime.cs`). Successful acquisition means the game template resolved, a synthetic instance was built, the owner prepared the inactive prefab, and native setup plus resize completed before the session was delivered, with the subject's attributes shown over the template's (`src/BazaarPlusPlus/GameInterop/CardPreview/NativeCardPreviewFactory.cs`). Card prefab instantiation remains owned here, while `GameInterop/AssetLoading` owns cross-build `AssetLoader` signature adaptation; card previews request the native current scope rather than the `Global` lifetime used by process-static caches. The host also owns complete presentation visibility: the game's `CardPreviewBase.Show` covers only art/frame, so item gem groups remain concealed through setup and cancellation, are revealed only after a successful session `Show`, and are always concealed by `Hide` (`src/BazaarPlusPlus/GameInterop/CardPreview/NativeCardPreviewPresentation.cs`). Concrete pool/runtime/reflection/resource types are confined to this owning module by `NativeCardPreviewArchitectureTests`.

Enchant preview visibility is a three-state setting controlled by `PreviewVisibilityMode`: `Off`, `AutoOnPedestalChoice`, and `Always` (default `Always`). `ItemEnchantPreviewSettingsDockEntry.Create()` supplies its cycle order (`Off → AutoOnPedestalChoice → Always`), and `BppSettingsDockCatalog.ResolvePreviewVisibilityModeStatus` its status labels (`src/BazaarPlusPlus.Core/Game/ItemEnchantPreview/ItemEnchantPreviewSettingsDockEntry.cs`). Enchant text is useful always but can be noisy or irrelevant, hence the automatic pedestal-relevance mode between the explicit off/always choices; upgrade preview is an on-demand comparison, so it deliberately has no visibility mode, only `Hold` (default) or `Toggle` activation for its Shift key, persisted as `[Hotkeys] UpgradePreviewActivationMode` with no legacy boolean migration. `HotkeyActivationState` resets the latched toggle state when the activation mode or binding changes and processes at most one transition per frame (`src/BazaarPlusPlus/Game/Input/HotkeyActivationState.cs`).

The game's upgrade preview fuses a value only when the next tier's template carries its attribute, so the upgrade tooltip renders every value token against a copy of the item at its next tier (`src/BazaarPlusPlus/Game/Tooltips/UpgradePreviewValueProjection.cs`, out-of-combat multiplier auras from `UpgradePreviewAttributeMultiplierResolver`); the arithmetic lives in Core's `UpgradePreviewValueMath`, which the Android Host's projection shares ([android-host.md](android-host.md)).

`TooltipPreviewModePolicy` owns preview priority: upgrade hotkey wins first, then enchant hotkey, then enchant `Always`, then enchant `AutoOnPedestalChoice` only when the current choice pedestal is an enchant pedestal (`src/BazaarPlusPlus/Game/Tooltips/TooltipPreviewModePolicy.cs`). The mode rule below the hotkeys is Core's `EnchantPreviewVisibility`, and the pedestal classification Core's `ChoiceScreenPedestalResolver` over `PedestalEnchantCatalog` (`src/BazaarPlusPlus.Core/GameState/`), which the Android host applies too. A `TooltipModifierRefreshController` mountable re-resolves open preview tooltips when the Ctrl/Shift hold state changes: for both ordinary game cards and hovered synthetic previews, refresh verifies the visible primary tooltip belongs to the hovered session, keeps the existing native controller alive, replaces its `CardTooltipData`, and synchronously settles layout behind a temporary visibility gate; it never replays native hide/show positioning and fades (`src/BazaarPlusPlus/Game/Tooltips/TooltipModifierRefreshController.cs`, `src/BazaarPlusPlus/GameInterop/Tooltips/NativeCardTooltipContentRefresher.cs`). The tooltip patch surface also covers encounter/event tooltips, quest reward previews, aggregate-item missing types, and hero level rewards (`src/BazaarPlusPlus/Patches/Tooltips/`). Both hosts expose one **Detailed Preview** switch through Core's `DetailedPreviewSettingsDockEntry`, backed by `BppSettings.EnableDetailedPreviewConfig`. The retired Event Preview and Quest Preview keys are no longer read. Disabling it immediately restores tracked native quest text/layout and hides all four pooled desktop sections; Android refreshes the current native card tooltip. Mod-appended text goes through the shared `BppTooltipSections` helper, which keeps the cloned native donor typography and attaches the game's own zh-CN fallback chain only when BPP-authored content contains CJK (`src/BazaarPlusPlus/Patches/Tooltips/BppTooltipSections.cs`).

`GameInterop/Tooltips` holds two unrelated native-tooltip adapters that must not be merged. `NativeCardTooltipContentRefresher` replaces the `CardTooltipData` of an already-visible primary tooltip and settles its layout. `NativePairedTooltipHost` owns the separate "custom content inside the native auxiliary tooltip, pinned beside the native card tooltip" presentation: native state capture/restore, the `CanvasGroupGate` visibility gates, the cloned native background, the paired fade, side selection, and coordinate conversion (`src/BazaarPlusPlus/GameInterop/Tooltips/NativePairedTooltipHost.cs`). Composition creates one plugin-lifetime host; it is not `IDisposable`, and the releasable unit is the `NativePairedTooltipSession` a feature acquires from it. The host reports placement outcomes through `PlacementResult` and never logs: reason codes, their once-only latches, and native show/hide arbitration stay with the consuming feature, because that latch behavior decides how many records reach the log. It also does not arbitrate the native auxiliary singleton; other code drives it directly (`src/BazaarPlusPlus/Game/CombatReplay/CurrentReplayRecordingButtonController.cs`), so a single active session serializes only this host's own usage. Purely geometric decisions are the unit-tested `NativePairedTooltipPlacementMath`; the shared `NativePairedTooltipMetrics.Epsilon` deliberately serves both as a geometry tolerance and as the CanvasGroup alpha interactivity threshold. Combat Impact is currently the only consumer, supplying its own trim strategy through `IPairedContentBudget`. While it builds content, it reads the trim limit from `NativePairedTooltipSession.TryMeasureContentHeightLimit` and skips native previews for rows that the budget will always hide; its `NativePostCombatImpactTooltipView` is a feature UI adapter rather than a Harmony patch, so by the layering rules it belongs under `Game/` and stays in `Patches/` as recorded debt. The host's generality is "multiple features sharing this paired shape", not "any native tooltip host". `NativePairedTooltipArchitectureTests` keeps this module free of feature and patch dependencies.

Core's `Cards/EffectiveCardTags` owns the union of runtime, template and active-enchantment public and hidden tags. `GameInterop/Cards/DesktopEffectiveCardTags.Read` supplies the desktop Encounter inventory and Combat Impact; Android's `AndroidEncounterPreviewReads.ReadInventory` supplies facets from its native cards. Each host selects only the active enchantment and retains its inventory walk. `EffectiveCardTags.EncounterTagNames` projects names for ordinal Encounter matching; Combat Impact consumes the facet sets, with null for an empty set. Core tests cover source union and per-card counting; desktop host tests retain native template and enchantment selection coverage.

## Gotchas

Traps and rules that bite only this feature; most failed silently at least once.

- Rendering the reused uGUI card prefab through an offscreen camera into a `RenderTexture` silently yields an empty texture under URP — native board previews stay on the `ScreenSpaceOverlay` canvas; do not re-propose the RT path.
- `CardPreviewBase.SetUp` overwrites Saved Card Values: it adopts the instance's attribute dictionary, writes the starting tier into it, then replaces it with a copy carrying the tier's and enchantment's values. Every surface that sets up a card (the native board, this module's factory, the touch rental, the detached text card) therefore goes through `NativeCardSetUp`: `Keep` before the set-up, `Kept.ShowOn` after a successful one, which writes the values over the client card, draws an item's gems again, and puts them back into the instance's dictionary, because a board re-renders the same instance and `NativeBoardSignature` keys on it. The tooltip needs no extra step, because `CardTooltipData` reads the same client card. [`src/BazaarPlusPlus/GameInterop/Cards/NativeCardSetUp.cs`]
- The card UI prefab (`CardPreviewItem`) has no ammo bar. Only the board item (`ItemController`) and the combat recap card (`RecapItemVisualController`) carry an `ItemAmmoController`. An item on a BPP item board (History, Ten-Win Builds, and on touch the inspect sheet of a board card, through `CardRentalSubject.OnBoard`) therefore borrows the recap card's bar. The host loads `SmallRecapCardGameplayAssetRef` once in Global scope and keeps a hidden copy of its controller. For each card, the copy draws the client card's tier and `AmmoMax` with the game's `ResetAmmoView`, and a clone of its `ammoBar` goes on the card. That is maximum ammo, as the game's board shows outside combat. Core's `AmmoBarPlacement` places and scales it. Its values come from a measurement of the game's board, not from the recap card: the recap card's layout puts the bar about 15 % larger and below the frame. The desktop takes the bar off in `NativeBoardCardRental.ResetVisuals` before the game's pool gets the card back, so it never shows on the game's own screens. A failed template load logs `static_cards.ammo_bar.unavailable` (`android.ammo_bar.unavailable` on touch) and the boards show no bar. [`src/BazaarPlusPlus/GameInterop/Cards/NativeCardAmmoBar.cs` | `src/BazaarPlusPlus.Android/GameInterop/CardRental/AndroidCardAmmoBar.cs`]
- Pooled native tooltip clones share one root-canvas `sortingOrder`, and `overrideSorting` cannot be set on a root canvas. Layering a BPP preview above the other (locked) clone means raising this clone's root-canvas order while visible, refcounted per owner; sibling order inside the prefab is irrelevant. This bug class recurred three times. [`src/BazaarPlusPlus/Patches/Tooltips/TooltipLayerOverride.cs`]
- The only working concealment seam for the native auxiliary tooltip is the `auxParent` CanvasGroup gate: `Tooltip_Aux_P`'s `auxParent` owns the complete visual tree, and a CanvasGroup on the controller root sits above the prefab's nested Canvas — silently inert. Teardown keeps the gate closed; owned gates `DestroyImmediate` on restore, since a deferred destroy leaves an end-of-frame corpse that `GetComponent` adopts and silently ungates. [`src/BazaarPlusPlus/GameInterop/Tooltips/NativePairedTooltipHost.cs` | `tests/RuntimeIntegration.Tests/GamePremiseCompatibilityTests.cs` pins the `auxParent` field; no test runs the gate]
- Native `ShowAuxiliaryTooltipController` only `SetText`s — it never reactivates header/body, so a pooled controller handed back with inactive text nodes collapses to a tiny empty frame over the board. The show handoff force-reactivates requested nodes; a frame audit conceals `visible_without_text` leftovers. Only a Combat Impact takeover leaves such nodes, so the audit runs from its auxiliary request until an idle native display shows both nodes active (`NativeAuxiliaryTooltipAnomalyRules.TextNodesProvenRestored`), not throughout normal play. [`src/BazaarPlusPlus/GameInterop/Tooltips/NativePairedTooltipHost.cs` | `src/BazaarPlusPlus/Game/PostCombatImpact/PostCombatImpactController.cs`]
- Combat Impact's waits on native tooltip work end by unscaled time as well as by frames (`NativeTooltipWaitBudget`). The native show fades are DOTween sequences on unscaled time, about 0.16 s at any frame rate, and the game's VSync option sets the target frame rate to the monitor's refresh rate. A 60-frame bound ran out first above about 360 fps, so the hover failed with `primary_tooltip_create_timed_out` or `auxiliary_tooltip_create_timed_out` and only the native tooltip showed (#973). A failure that suppresses the hover logs its reason at Warn. [`src/BazaarPlusPlus/GameInterop/Tooltips/NativeTooltipWaitBudget.cs` | `src/BazaarPlusPlus/Game/PostCombatImpact/PostCombatImpactController.cs`]
- Locking a native card tooltip (`SetLockedFlag(true)`) re-enables `blocksRaycasts` via `ToggleInteractabilityOnCanvas`; a tooltip overlapping the pointer then steals hover, and the synthetic `PointerExit` yields a show/hide flicker loop. Keep the lock but force raycasts off while BPP owns the controller. [`src/BazaarPlusPlus/Game/PostCombatImpact/PostCombatImpactController.cs` | `src/BazaarPlusPlus/Patches/PostCombatImpact/PostCombatImpactRecapPatch.cs`]
- Synthetic or unknown GUIDs must not repeatedly reach native-preview template lookup; the grid negative-caches `TemplateUnavailable` per catalog generation. [`src/BazaarPlusPlus/GameInterop/CardPreview/NativeCardPreviewFactory.cs`]
- The Package merchant summary is cached per static-data manager, package template and game language, never per run, although the native renderer resolves description tokens against `Data.Run` and the first render can happen outside a run (Collection, History). It stays correct only while the first sentence `PackageMerchantSummaryText.Format` keeps resolves no run-dependent token. In current English GameData the only merchant tokens are a fixed `{aura.3}` (Midsworth, Quixel, Laurel, Barkun) in the second sentence; translated descriptions were not checked. A merchant with a run-dependent value, or a locale that moves a token before the first sentence terminator, would freeze the summary for the session. The Android host's cache in `AndroidEncounterPreview` has the same scope and the same limit. [`src/BazaarPlusPlus/GameInterop/Cards/PackageMerchantSummary.cs`]
- A description token shows seconds when the game styles its value as a millisecond attribute (`TooltipExtensions.RequiresConversionToSeconds`), while the template stores milliseconds, so `CardAbilityValueReader` converts at read time: an unconverted `FlatCooldownReduction` of 1000 renders "reduce its cooldown by 1000 second". Compiled plans keep those texts in the disk cache, whose identity names the game build and channel but not the mod, so a change to what the capture writes bumps `EncounterPreviewCacheStore.SchemaVersion`. [`src/BazaarPlusPlus/GameInterop/Cards/CardAbilityValueReader.cs` | `src/BazaarPlusPlus.Core/Game/EncounterPreview/EncounterPreviewCacheStore.cs`]
- Mod-appended tooltip text goes through `BppTooltipSections`, which clones the tooltip's own passive-text block at 0.75 font scale, keyed per controller and purpose. [`src/BazaarPlusPlus/Patches/Tooltips/BppTooltipSections.cs`]
