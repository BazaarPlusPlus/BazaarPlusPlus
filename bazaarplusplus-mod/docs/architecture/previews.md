# Encounter Preview, Card Preview, And Tooltips

The Encounter Preview query boundary, the native card preview owning module, and the tooltip presentation surfaces. `GameInterop/Tooltips` holds two adapters that must not be merged.

`EncounterPreviewModule` is the single owner of event, encounter-step, and hero-level preview semantics, from cache identity and plan compilation through localization and final presentation; all three query kinds resolve to the single `EventPreviewResult` record (`src/BazaarPlusPlus/Game/EventPreview/EncounterPreviewModule.cs`). Its typed query interface accepts only stable template ids/current level plus native text already present at the patch boundary; game state (the current static-data source, hero, inventory, one generation-matched day-tier result, native keyword typography) is read through `IEncounterPreviewGameRuntime` (`src/BazaarPlusPlus/Game/EventPreview/EncounterPreviewGameRuntime.cs`). Beginning a source generation first removes the old snapshot; generation checks prevent a superseded load from publishing, while a successful compile remains published with degraded status if its cache write fails (`src/BazaarPlusPlus/Game/EventPreview/EncounterPreviewPlanRegistry.cs`).

`EventPreviewStaticDataObserver` is only the Unity frame adapter that reports a newly ready source to the module (`src/BazaarPlusPlus/Game/EventPreview/EventPreviewStaticDataObserver.cs`). Tooltip patches receive the module through the `BppPatchFeatures` bundle and consume semantic results; they do not read plans, static-data maps, inventory, or CollectionPanel formatters (`src/BazaarPlusPlus/Patches/BppPatchFeatures.cs`, `src/BazaarPlusPlus/Patches/Tooltips/`). `CardAbilityValueReader` centralizes the shared reflection seam over game-authored ability/aura action and attribute values; Event Preview and Collection keep their separate localization and typography policies (`src/BazaarPlusPlus/GameInterop/Cards/CardAbilityValueReader.cs`). `GameDataDayTierResolver` is the shared GameInterop day-tier owner for Collection's Day gate and Event Preview: it exposes typed unavailable states, retries transient readiness, and rejects an Event Preview query whose plan source is no longer the current manager; its generation-keyed caching and `MaximumTier` semantics are pinned in `docs/MEMORY.md` (`src/BazaarPlusPlus/GameInterop/DayTiers/`).

`GameInterop/CardPreview` is the owning module for native card prefab selection, instantiation, setup/resize, reflection, hover state, tooltip replacement, pooling, and destruction. Production callers see only `INativeCardPreviewHost`, a per-owner `INativeCardPreviewScope`, and opaque `INativeCardPreviewSession` intent operations (`src/BazaarPlusPlus/GameInterop/CardPreview/NativeCardPreviewContracts.cs`). Each scope has its own pool: closing rejects new acquisitions, cancels and waits outstanding setup, invalidates/destroys active sessions, then destroys idle objects; a session released after closing cannot re-enter the pool (`src/BazaarPlusPlus/GameInterop/CardPreview/NativeCardPreviewScopeLifetime.cs`). Successful acquisition means the game template resolved, a synthetic instance was built, the owner prepared the inactive prefab, and native setup plus resize completed before the session was delivered (`src/BazaarPlusPlus/GameInterop/CardPreview/NativeCardPreviewFactory.cs`). Card prefab instantiation remains owned here, while `GameInterop/AssetLoading` owns cross-build `AssetLoader` signature adaptation; card previews request the native current scope rather than the `Global` lifetime used by process-static caches. The host also owns complete presentation visibility: the game's `CardPreviewBase.Show` covers only art/frame, so item gem groups remain concealed through setup and cancellation, are revealed only after a successful session `Show`, and are always concealed by `Hide` (`src/BazaarPlusPlus/GameInterop/CardPreview/NativeCardPreviewPresentation.cs`). Concrete pool/runtime/reflection/resource types are confined to this owning module by `NativeCardPreviewArchitectureTests`.

Enchant preview visibility is a three-state setting controlled by `PreviewVisibilityMode`: `Off`, `AutoOnPedestalChoice`, and `Always` (default `Always`). `ItemEnchantPreviewSettingsDockEntry.Create()` supplies its cycle order (`Off → AutoOnPedestalChoice → Always`), and `BppSettingsDockCatalog.ResolvePreviewVisibilityModeStatus` its status labels (`src/BazaarPlusPlus/Game/ItemEnchantPreview/ItemEnchantPreviewSettingsDockEntry.cs`). Enchant text is useful always but can be noisy or irrelevant, hence the automatic pedestal-relevance mode between the explicit off/always choices; upgrade preview is an on-demand comparison, so it deliberately has no visibility mode, only `Hold` (default) or `Toggle` activation for its Shift key, persisted as `[Hotkeys] UpgradePreviewActivationMode` with no legacy boolean migration. `HotkeyActivationState` resets the latched toggle state when the activation mode or binding changes and processes at most one transition per frame (`src/BazaarPlusPlus/Game/Input/HotkeyActivationState.cs`).

`TooltipPreviewModePolicy` owns preview priority: upgrade hotkey wins first, then enchant hotkey, then enchant `Always`, then enchant `AutoOnPedestalChoice` only when the current choice pedestal is an enchant pedestal (`src/BazaarPlusPlus/Game/Tooltips/TooltipPreviewModePolicy.cs`). A `TooltipModifierRefreshController` mountable re-resolves open preview tooltips when the Ctrl/Shift hold state changes: for both ordinary game cards and hovered synthetic previews, refresh verifies the visible primary tooltip belongs to the hovered session, keeps the existing native controller alive, replaces its `CardTooltipData`, and synchronously settles layout behind a temporary visibility gate; it never replays native hide/show positioning and fades (`src/BazaarPlusPlus/Game/Tooltips/TooltipModifierRefreshController.cs`, `src/BazaarPlusPlus/GameInterop/Tooltips/NativeCardTooltipContentRefresher.cs`). The tooltip patch surface also covers encounter/event tooltips (gated by the `Game/EventPreview` settings toggle), quest reward previews and aggregate-item missing types (separate implementations sharing the default-off `QuestPreview/Enabled` gate), and hero level rewards (`src/BazaarPlusPlus/Patches/Tooltips/`); disabling Quest Preview immediately restores tracked native quest text/layout and hides its pooled aggregate-item sections. Mod-appended text goes through the shared `BppTooltipSections` helper, which keeps the cloned native donor typography and attaches the game's own zh-CN fallback chain only when BPP-authored content contains CJK (`src/BazaarPlusPlus/Patches/Tooltips/BppTooltipSections.cs`).

`GameInterop/Tooltips` holds two unrelated native-tooltip adapters that must not be merged. `NativeCardTooltipContentRefresher` replaces the `CardTooltipData` of an already-visible primary tooltip and settles its layout. `NativePairedTooltipHost` owns the separate "custom content inside the native auxiliary tooltip, pinned beside the native card tooltip" presentation: native state capture/restore, the `CanvasGroupGate` visibility gates, the cloned native background, the paired fade, side selection, and coordinate conversion (`src/BazaarPlusPlus/GameInterop/Tooltips/NativePairedTooltipHost.cs`). Composition creates one plugin-lifetime host; it is not `IDisposable`, and the releasable unit is the `NativePairedTooltipSession` a feature acquires from it. The host reports placement outcomes through `PlacementResult` and never logs: reason codes, their once-only latches, and native show/hide arbitration stay with the consuming feature, because that latch behavior decides how many records reach the log. It also does not arbitrate the native auxiliary singleton; other code drives it directly (`src/BazaarPlusPlus/Game/CombatReplay/CurrentReplayRecordingButtonController.cs`), so a single active session serializes only this host's own usage. Purely geometric decisions are the unit-tested `NativePairedTooltipPlacementMath`; the shared `NativePairedTooltipMetrics.Epsilon` deliberately serves both as a geometry tolerance and as the CanvasGroup alpha interactivity threshold. Combat Impact is currently the only consumer, supplying its own trim strategy through `IPairedContentBudget`; its `NativePostCombatImpactTooltipView` is a feature UI adapter rather than a Harmony patch, so by the layering rules it belongs under `Game/` and stays in `Patches/` as recorded debt. The host's generality is "multiple features sharing this paired shape", not "any native tooltip host". `NativePairedTooltipArchitectureTests` ratchets the plumbing into this module.
