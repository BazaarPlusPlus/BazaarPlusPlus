# Combat Replay, Screenshots, Uploads, And Ghost Battles

Local saved replay startup awaits `ISavedReplayRuntime.ReplaySavedAsync`. Core reserves admission and a payload lease before `PendingSavedReplayRead` reads the catalog and compressed payload on a worker. History keeps its pending state until the read and `BeginStart` handoff finish. Cancellation, stale selection, an active Run or a ReplayState exit during the read prevents handoff without starting or rolling back a game. The worker owns a separate reference to the same lease: runtime disposal releases admission immediately but maintenance stays blocked until the read actually ends, even after the host stops pumping continuations. Successful handoff transfers the owner reference continuously through playback. Game decoding and startup remain on the existing host path.

History offer probes share `SavedReplayOfferCache` on both hosts: positive and negative answers live for five realtime seconds, and read exceptions are never cached. Multiple view and click checks reuse that hint, but taking an offer invalidates it and playback still reads the actual payload. The Android adapter reports a failed probe as unavailable; the desktop lets History report the exception.

Replay recording and playback, optional video capture, end-of-run screenshot capture, bundle sealing, the single upload feed, and ghost battle import.

Combat replay records local PvP battle replay payloads and lets HistoryPanel start playback when a local or downloaded ghost replay payload is available. Video recording is optional and supported on macOS and Windows through platform-native render plugins (Metal/VideoToolbox/AVFoundation; D3D11/Media Foundation); availability is gated by the native plugin and output directory configuration (`src/BazaarPlusPlus/Game/CombatReplay/Video/CombatReplayRecordingGate.cs`).

Local replay payloads are a bounded cache, while battle facts and successful MP4 recordings are durable user artifacts. Startup maintenance runs off the constructor path behind the same operation gate as payload persistence and playback: one bulk SQLite inventory drives orphan cleanup and the `newest 200 ∪ last 30 days` retention policy, and a transactional `ready → delete_pending → evicted` lifecycle makes file failures retryable. File deletion uses at most four workers under the same maintenance lease; catalog operations remain on the caller, completed IDs retain their input order, and cancellation waits for started file operations before releasing the lease. Deleted files still marked `delete_pending` are completed by the next pass. Active runs, playback/persistence work, waiting or sealing Bundle seal jobs, Seal-Eligible Runs, and pending outbox rows are protected. History treats a replay as saved only while `local_payload_state` is `ready`. Video ownership and file health are orthogonal (`attachment_state` and `file_state`): run deletion detaches metadata in the run-delete transaction but keeps completed MP4s; reconcile marks missing/recovered files, reports unknown successful MP4s without deleting them, and removes only expired unprotected temporary/failed residue. Detached recording metadata remains in the store (`src/BazaarPlusPlus.Core/Game/CombatReplay/ReplayPayloadMaintenanceService.cs`, shared with the Android host; `src/BazaarPlusPlus/Game/CombatReplay/Video/ReplayVideoArtifactMaintenanceService.cs`).

Desktop presentation warmup deduplicates card requests only within one warmup. It calls the game's `AssetLoader.PreloadAssets` and `PreloadCard` on each replay, leaving pool and handle reuse to the game scope; `ReleaseScope(InRun)` resets the game's shared-preload flag. A completed preload call is not proof that every native asset loaded: the game owns its internal shared-preload failure state. Override loads retain their explicit null check and report failed assets. Like `VFXManager.TryInstantiateVFXByAddress`, an override key whose `/Projectiles/` segment has an existing `/Emitters/` twin warms the twin, and warms the key itself only when the twin loads as null or throws, which is not a degradation (`src/BazaarPlusPlus/Game/CombatReplay/Warmup/PresentationWarmer.cs`, `WarmPresentationAssetsAsync`).

To read a replay payload outside Unity, decode through `CombatReplayPayloadStore` plus `MessagePackSerializer.Deserialize<NetMessageGameSim/NetMessageCombatSim>` with `MessagePackConfig.Options`; `CombatReplayLoader` returns an Assembly-CSharp type, so it only works inside the game process.

`tests/CombatImpact.Corpus/` is the offline acceptance module for the complete Combat Impact model. It references Core alone and projects the Combat Impact Corpus `tests/CombatImpact.Corpus/corpus/pinned-corpus.json.gz` in `just mod::test-core` and, as a scenario capsule, in `just mod::test`, comparing its evidence with `tests/CombatImpact.Corpus/evidence/pinned-corpus.json`. The host-lane `tests/CombatImpact.CorpusExport/` writes that corpus from the game payloads in its `corpus/`, and `ScenarioRunner.Tests` (`Combat_impact_corpus_export_matches_committed_corpus`) holds a fresh export to the committed one; `just mod::test-corpus <path>` exports and projects an external corpus (ADR-0019 item 5). The evidence records the corpus artifacts, `GameData.db`, and interpreting game assemblies so results reproduce against the same inputs; `tests/CombatImpact.Corpus/evidence/README.md` owns regeneration.

Saved-replay playback state algebra lives in the pure `SavedReplayLifecycle` core in Core (`src/BazaarPlusPlus.Core/Game/CombatReplay/SavedReplayLifecycle.cs`). Core's `SavedReplayPlayback` is its translation layer for both hosts: it holds the active operation and its payload lease, runs the start, and executes publishes, cleanup and menu dispatch through the host's `ISavedReplayHost`, whose desktop form is `DesktopSavedReplayHost`; `CombatReplayRuntime` only wires it to the game (ADR-0020; behavior tests in `tests/SavedReplayPlayback.Tests/`). The load-bearing states and windows (staged start commits, the shared 15-second exit-suppression latch, the two-phase exit decision, pending menu-return polling) are enumerated in ADR-0005. On desktop, `DesktopSavedReplayHost.BeginStart` decodes the payload's three MessagePack parts on a pool thread (the seal worker already decodes through the same `CombatReplayLoader`), and the start awaits the decode at the end of `BootstrapAsync`; a payload that does not decode therefore fails the start after the bootstrap, through the start-failed cleanup and rollback, rather than inside `BeginStart`.

A failed lobby bootstrap dispatches the native `Events.RunInterrupted` event before resetting run data or unloading scenes in desktop `ReplayBootstrap.RollbackBootstrapAsync` and Android `AndroidReplayBootstrap.RollbackBootstrapAsync`. This gives registered native audio and effect listeners their interruption cleanup while they still exist. A dispatch exception is recorded and returned as a rollback failure after the remaining cleanup is attempted. Native event dispatch catches individual listener exceptions itself, so successful dispatch alone does not prove that every listener cleaned up.

Saved-replay startup treats the native `ReplayState.SpawnCombatCards` task as the board-readiness boundary. Native state entry starts that task without awaiting it, so sampling active item setup or `BoardManager` flags alone can observe a false quiet frame before the first controller activates. The Harmony seam tracks both the complete board-spawn task and individual item setup tasks inside a scoped `ReplayPresentationTaskTracker`; startup waits until all tracked work completes and a render boundary passes without discovering new work, under the existing bounded failure rollback (`src/BazaarPlusPlus/Patches/Combat/CombatReplayItemPresentationReadinessPatch.cs`, `src/BazaarPlusPlus/Game/CombatReplay/Bootstrap/ReplayItemPresentationReadiness.cs`). Fixed delays and expected-controller counts are not substitutes for this native work boundary.

`CombatReplayVideoRecorder` owns the video capture session (`src/BazaarPlusPlus/Game/CombatReplay/Video/CombatReplayVideoRecorder.cs`). Two contracts hold across it: audio capture is additive (tap failure never aborts video recording, and only usable sample-bearing WAVs are retained), and on playback end the finalization inputs are frozen into detached contexts with encoder drain/audio mux/metadata completion dispatched off the main thread, so a later replay cannot overwrite them. At playback end the audio taps stop off the main thread too: the main thread only hands them over, and a tracked background task joins each capture thread, releases the backend (WASAPI COM objects, or the CoreAudio IOProc, aggregate device and process tap), closes the WAV and keeps or deletes it; finalization waits for that task before muxing, and on macOS, whose aggregate device has a fixed UID, the next recording waits for it (bounded) before building its capture session, so the wait never counts toward the recording; past the bound the recording continues as silent video with `AudioCaptureFailed`. An abort (superseded, disabled, destroyed) still stops its taps synchronously, since a new recording or the process exit waits for that stop on the main thread anyway (`src/BazaarPlusPlus/Game/CombatReplay/Audio/ReplayAudioTapStopper.cs`). A History recording's `RECORDING` row is likewise inserted by a tracked background task that finalization joins before `SaveFinish`, which only updates an existing row. The current replay's row stays a synchronous reservation, since arming promises it, but `CombatReplayVideoMetadataStore.ReserveStartOnMainThread` gives up on a locked database after about a second instead of the stores' two and the arm reports the failure. The recorder's shutdown drain waits for these tasks like any finalization (`ReplayVideoAudioMuxer.DispatchTracked`). The persisted `duration_ms` column is the video's length, which installer History shows: the encoded timeline's frame count over the fps, because both native encoders stamp frame n at n / fps (`ReplayVideoCaptureResult.VideoDurationMs`). The `combat_replay.video_capture.stats_observed` event logs that as `video_duration_ms`; its `duration_ms` field spans session construction to drain completion, so it includes encoder start and drain and is a diagnostic span: the video timeline starts at the first frame, when `WallClockCfrPacer` locks its clock. The same event splits it into `init_ms`, `first_frame_wait_ms`, `capture_ms` and `drain_ms` (`ReplayVideoSessionTimeline`); the terminal `combat_replay.video_recording.*` event's `duration_ms` starts earlier still, at the playback start. The finalizers live outside the MonoBehaviour in `ReplayVideoRecordingFinalizer`, so their terminal outcomes are tested without the game (`tests/CombatReplayRecording.Tests/RecordingFinalizerScenarios.cs`). An abort's finalizer owns the terminal of the operation it took: it reads the tap stop and start metadata before the encoder drain, so a throwing drain cannot erase them, and a start that throws after its operation became active posts no fallback of its own (`ReplayVideoRecordingFinalizer.CompleteBeginException`).

BPP UI chrome suppression is centralized in `Game/OverlayPanels`: screenshot mode hides the Collection and Ten-Win Builds dock buttons and the combat status bar; replay recording mode hides only those dock buttons, intentionally leaving the combat status bar visible; there is no separate settings-dock suppression target (`src/BazaarPlusPlus/Game/OverlayPanels/BppUiChromeSuppression.cs`). Native tooltip suppression is a separate shared, owner-scoped adapter in `GameInterop/Tooltips`: replay presentation, replay video, and end-of-run capture hold independent leases; high- and low-level native show paths are gated while any lease is active, and cleanup unlocks and conceals primary, secondary, auxiliary, and locked tooltips. Controller discovery includes inactive objects so the native parent's current controller remains authoritative; one process-wide controller snapshot serves every lease and rescans only after a controller Awake/OnDestroy, a destroyed cached controller (`NativeTooltipControllerCacheCore`), or a change in the tooltip parent's identity or child count. An inactive controller no longer owned by that parent cannot render while the show gates are held and is skipped as stale for that audit. Active or authoritative controllers still require their native visibility surface; unavailable surfaces retain the fail-open degraded-capture path. Debug sampling records both the stable native audit reason and the maximum skipped inactive-controller count (`src/BazaarPlusPlus/GameInterop/Tooltips/NativeTooltipSuppression.cs`, `src/BazaarPlusPlus/Patches/Tooltips/NativeTooltipSuppressionPatches.cs`).

End-of-run capture is one run-scoped `EndOfRunCaptureWorkflow`: its core owns readiness, bounded attempts, deadlines, artifact validation, Continue blocking, and the single terminal outcome (`src/BazaarPlusPlus/Game/Screenshots/EndOfRunCaptureWorkflowCore.cs`), with the internal `EndOfRunCaptureDriver` as its Unity/native surface adapter (`src/BazaarPlusPlus/Game/Screenshots/EndOfRunCaptureDriver.cs`). The contracts that must hold: readiness requires native reveal start, a cleared screen transition, settled skills, and either 500 ms of structural card-pose stability after observed motion or the native `FaceUp` completion fallback (empty card boards retain their native settled path), and readiness starts capture automatically. Each attempt acquires BPP and native-tooltip suppression, clears hover/locked state, and passes a second bounded clean-frame barrier (native tooltip visibility audits clean and the post-clean card hierarchy stays structurally stable for a fresh 500 ms window) before `ScreenCapture` runs. The barrier is best-effort: missing native seams, unavailable visual audits, preparation exceptions, or the deadline degrade to an immediate capture with a terminal reason instead of dropping the artifact (`src/BazaarPlusPlus/Game/Screenshots/EndOfRunCleanFramePreparationCore.cs`). Suppression leases remain held until the captured frame's RGBA pixels have been copied out of Unity when preparation remains available; Run metadata (day, victories, hero, rank, rating, and placement) is copied into an immutable value immediately before frame capture; persistence reads only that value, never the later live run. Continue is released at that boundary, while PNG encoding, atomic file write, and metadata persistence continue in the background without consuming or replaying the native click. A verified PNG is never deleted or recaptured when metadata persistence fails or times out; a late artifact from a capture canceled before frame acquisition is deleted. Composition exposes the workflow's two-intent interface to patches before mounting the driver, so the Continue and raw reveal patches fail open during startup and teardown (`src/BazaarPlusPlus/DesktopComposition.cs`, `src/BazaarPlusPlus/Patches/EndOfRun/`).

`BundleSealCoordinator` is the single background workflow owner of input convergence, payload composition, screenshot JPEG budgeting, deterministic bundle construction, self-open verification, atomic publication, and crash reconciliation; event-bus handlers only enqueue wakes or a job-discovery request and do no work themselves (`src/BazaarPlusPlus.Core/Game/BundlePipeline/BundleSealCoordinator.cs`). The worker has no fixed scan interval. Job discovery (`EnsureEligibleJobs`, a write that scans the Run history) runs at startup, on Android resume, when Run Logging reports a Run written completed (`RunLogRunCompleted`, published after `CompleteRun` commits the row, the 2 s deferred completion included), after upload validation commits a new seal job (`BundleSealJobRecreated`), and in safety passes at most 300 s apart for a missed report; other wakes only list the waiting jobs and read again only those that are due. After each pass `BundleSealWakeSchedule` sets the next wake: a job's backoff end, the next pass for a job skipped earlier that became due during the pass, an attempted job still waiting on an input every 5 s until its input deadline, nothing for a job parked until the next launch, and the 300 s cap when no job waits. The 5 s input poll stays because some inputs land without a wake: the Android host publishes no `CombatReplayPersistenceDrained`, so a replay wait there is released only by polling. A failed job discovery or file recovery retries in 5 s. A Run first discovered by the safety pass is already past its 2-minute input deadline and seals with the inputs it has. An attempt converges its inputs before any costly work: replay persistence, the account, the screenshot's presence, then the composed Run's omitted replays, counted before the size budget so a replay `RunPayloadComposer.FitToBudget` trims never holds the Run; only then is the screenshot encoded and the payload budgeted. The budget trims in a fixed order (non-projection replays, projected battles oldest first, snapshots without a replay, then non-terminal events oldest first) and finds the fewest trims per phase by probing 1, 2, 4, … and bisecting, so it encodes a large Run a logarithmic number of times. That assumes another trim never grows the gzip size; while it holds, the result equals trimming one at a time, and when every trim of a phase still overflows the whole phase applies (`RunPayloadComposer.ApplySizeBudget`, pinned by the `size-budget-*` cases of the pipeline golden). A Run held by omitted replays is not composed again until a replay persistence completion (`ReplayPersistenceStateTracker.CompletionGeneration`, read before composing) or its input deadline (`BundleSealInputObservation.RememberedReplayPayload`), since for an ended Run whose persistence has drained no replay can land without that completion; a new replay writer must call `Completed` after its file is written. It lives in Core with its composer, `RunPayloadComposer`, which reads the database only through Storage (`RunLogBundleSource`, `PvpBattleSqliteStore`; ADR-0012) and the board captures as Core's `PvpBattleCardSetDocument`; the host supplies only the game-typed reads (`IPvpBattleEvidenceBinding`: card enum values and Replay Payload verification) and the image codec (`IBundleScreenshotEncoder`), which `DesktopBundleSealCoordinator.Create` binds on desktop and `AndroidComposition` on Android. Stable bundle id/time are allocated before file creation, and startup recovery adopts a renamed file only when its durable allocation identity matches. The convergence/queue ownership split (pure `BundleSealConvergence` decisions, Storage-owned `BundleQueueStore` SQL) is recorded in ADR-0006. Every seal-path failure is decided by `BundleSealFailurePolicy` from the stage it happened in and its exception graph, then recorded through `BundleQueueStore.RecordSealFailure` (state, consecutive `attempts` for that code, time, bounded diagnostic) and logged with the original exception under a storm-limited category (`bundle_pipeline.seal.deferred`, `.environment_blocked`, `.degraded`, `.terminal`). Runtime failures (missing member, type load, assembly binding, type initializer) park the Run as waiting with `seal_environment_blocked`: it runs again once per launch, so a mod or game update retries it without a migration, and it ends as `seal_environment_blocked_expired` only after five parked launches and 60 days past its input deadline. Other failures retry with exponential backoff (5 s to 1 h) and end as `seal_retry_exhausted` only after eight consecutive failures with the same code and 14 days; codec failures in payload budgeting, encoding, or Bundle build are terminal at once. A job that fails again 90 days or more past its input deadline ends whatever its code, so alternating failures cannot pin its sources in History cleanup forever; a first failure never ends that way. Each Run is attempted in isolation and skipped while backing off, so one failing Run cannot abort a pass or starve later Runs. A replay that exists but cannot be used is reported by `RunPayloadComposer` with its load status and decode exception (a failure without an exception retains the codec reason and payload type in a diagnostic `InvalidDataException`): bytes that do not decode omit that replay with a `replay_invalid` log even when the cause looks like IO (truncated MessagePack, corrupt gzip), a file that cannot be read retries the Run, and a runtime failure anywhere in the exception chain parks it. File recovery and pending-file validation run once per launch, on passes until one completes, so a backlog is not re-read every pass; a pending file that goes bad later fails `BundleUploadFeed`'s length and digest check, which schedules the same reseal. They are per file; a runtime that cannot open a Bundle neither deletes an orphan nor invalidates a pending outbox, and maintenance failures never stop waiting Runs from sealing (`BundleSealCoordinator.ReconcileAsync`).

Waiting-queue reads return usable jobs and individual row-conversion failures separately (`BundleQueueStore.ListWaitingJobs`, `src/BazaarPlusPlus.Storage/BundleQueue/`). The coordinator reports each failure through `BundleSealFailurePolicy` as `seal_job_unreadable` with its available Run identity and original parse exception, then continues the valid jobs. It leaves malformed rows unchanged and retries reading them on subsequent normal passes, including the safety scan; a repaired row needs no restart. Query or connection failures still abort the read. Account freezing first checks whether either the Run or its seal job has an unknown account, so an existing, already frozen pair needs no writer lock; conditional writes inside the transaction preserve each row's first account (`BundleQueueStore.FreezePlayerAccountId`). Likewise, `PvpBattleSqliteStore.AttachToRun` skips the writer lock for an already attached battle, keeping the conditional write for a new attachment. Missing rows retain the original write path because another writer may still be creating them.

Payload budgeting returns the selected encoded bytes from `RunPayloadComposer.FitToBudget` (`src/BazaarPlusPlus.Core/Game/BundlePipeline/RunPayloadComposer.cs`); publication reuses them unless the final screenshot-omitted flag changes. That flag stays after budget trimming, preserving the existing trim choices near the size limit.

A reconcile pass arms uploads once after publishing its backlog, including partial progress before cancellation, so each recovered run cannot independently bypass the pump cadence. Pending-file invalidation checks the current outbox state in its transaction; a stale validation result cannot overwrite a completed upload (`BundleSealCoordinator.ReconcileAsync`, `BundleQueueStore.FailOutboxAndScheduleReseal`). `bundle_seal_jobs.input_deadline_at_ms` is a Unix-millisecond integer like every other stored instant, so `ListWaitingJobs` and `idx_bundle_seal_jobs_state` order deadlines numerically and no write path can store a format that sorts wrongly. Only that explicit invalidation schedules a reseal: a server rejection or local retention expiry is final instead of sealing a replacement Bundle on every pass. The rule for which Runs get a new seal job is `BundleQueueStore.SealEligibleRunCondition`, composed by `EnsureEligibleJobs` and replay maintenance (`PvpBattleSqliteStore.ScheduleReplayPayloadDeletion`). It rejects a History-Only Run (`runs.upload_policy = 'history_only'`) before any other check, so imported history is never sealed and replay maintenance releases its replays. The mod never writes that policy, and `RunLogStore.ResumableRunCondition` also keeps such a Run from being resumed, reopened by `CreateRun`, or shown as the current Run in History, in case an import left one active. `tests/BundleQueueSqliteStore.Tests/fixtures/bundle-seal-eligibility.json` is its cross-project contract: both mod consumers and installer History cleanup evaluate its cases.

There is exactly one upload feed and one Core `UploadPump` per host (desktop drives it from the `BackgroundUploadPump` MonoBehaviour): each `BundleUploadFeed.Session` owns a `ModApiSession`, sends immutable `.bundle` files to `POST /bundles` with `Content-Length` and `Content-Digest`, maps typed endpoint dispositions, persists retry time through `BundleQueueStore`, and commits success before deleting through the narrow `IBundleOutboxFiles` port (root-confined, so upload ordering and retention are testable without moving file policy into Storage) (`src/BazaarPlusPlus.Core/Game/BundlePipeline/`). Ghost discovery uses `GET /ghost-battles?limit=200`; replay download uses the plugin-owned History session, validates the bundle and run identities through `RunBundleV6Contract`, reconstructs only a complete target battle, saves it atomically, and persists `remote_available`, `local_ready`, `unavailable_payload`, or `expired` so permanent failures are not retried; only `ReplayAvailabilityCodec` maps these columns to Replay Availability (`src/BazaarPlusPlus.Core/Game/HistoryPanel/Ghost/`). The host supplies the profile account, the replay verification and card enum names (`IPvpBattleEvidenceBinding`), and the static-data template check the row counts need. Unexpected import failures use `ghost_bundle_import_failed` and remain terminal across syncs. The exact wire and payload contracts are documented in `docs/contracts/run-payload-v6.md`; transport/result/persistence ownership is recorded in ADR-0006.

Upload retries split by cause. `BundleUploadClient` types a request timeout, a transport error, HTTP 408, 429 and 5xx as `EndpointUnavailable`; every other retryable answer (an untrusted 409, an invalid success receipt, a server-marked retryable error on another status) and a local `file_io_error` are about one Bundle. An `EndpointUnavailable` answer ends the attempt's batch and opens a queue backoff held in the Session's memory. `BundleUploadFeed.RetryDelay` owns the schedule: it doubles from the pump interval (`ModApiUploadDefaults.IntervalSeconds`) per consecutive failure, applies jitter before the `BundleUploadFeed.MaximumRetryDelay` cap, and takes Retry-After as a floor. The window is measured from the attempt's start, so it lines up with the pump tick, and counts as over a little before its end so a jittered window does not slip to the following tick. It never ends sooner after the failure than one interval (or Retry-After), so an attempt that spent its window on a slow upload and a timeout does not retry at once. While the window lasts, an attempt runs only cleanup and reports itself deferred (`QueueBackoff`), so it reads, hashes and sends nothing. The failed row keeps only the server's Retry-After, so a restart retries it after the startup delay. An accepted upload, an explicit arm (`UploadArmRequested` or leaving a run), or a new Session ends the backoff; a permanent rejection or a failure about one Bundle does not. The Session handles those arm signals through `SubscribeArmSignals`, which the pump subscribes before its own arm handlers so the backoff is cleared before the armed attempt can start. A failure about one Bundle backs off that row alone with the same formula over its recorded `attempts`, which counts every upload attempt of that row, network failures included. The feed never arms itself, so offline the wake count no longer grows with the backlog; because the pump keeps its fixed tick, a window ends on the first tick at or after it.

## Gotchas

Traps and rules that bite only this feature; most failed silently at least once.

- `CombatReplayPayloadStore`/`GhostBattlePayloadStore` stay thin named facades over `FileBackedPayloadStore<T>`. Capsules construct `CombatReplayPayloadStore` directly, so renaming it breaks their build; `GhostBattlePayloadStore` and the `.mpack.gz` suffixes are not test-pinned. [`tests/BundlePipeline.Tests/Program.cs`]
- `tests/BundlePipeline.Tests` is the Bundle pipeline's end-to-end anchor: it seals and uploads through real SQLite stores and outbox files, writes every Bundle to `artifacts/bundle-pipeline/`, and fails unless its normalized summary matches `tests/BundlePipeline.Tests/fixtures/bundle-pipeline.golden.json` byte for byte. Its inputs must stay deterministic: game `NetMessage*` constructors draw a random `MessageId`, so the replay fixtures set it. Regenerate the golden only with `BPP_UPDATE_GOLDENS=1` and review the diff. [`tests/BundlePipeline.Tests/PipelineArtifacts.cs`]
- Dock-button lifecycle controllers must live on the always-active native button, never a `SetActive(false)` clone — inactive clones get no `LateUpdate` and miss later state transitions. The replay dock button's tooltip is the native cue activator's `defaultValue`, not a BPP-positioned auxiliary tooltip. [`src/BazaarPlusPlus/Game/CombatReplay/CurrentReplayRecordingButtonController.cs`]
- Clone the controller-free native donor first, then attach the BPP MonoBehaviour to the stable owner — cloning a GameObject that already carries a BPP controller duplicates the controller. [`src/BazaarPlusPlus/Game/CombatReplay/CurrentReplayRecordingButtonController.cs`]
- The native end-of-run reveal uses `CreateRawGraph`, whose delay roots have no `ScriptPlayableOutput` and therefore never complete — cards stay FaceDown and screenshot readiness never fires. `EndOfRunRawRevealCompletionPatch` injects a port-1 output per root; keep it. [`src/BazaarPlusPlus/Patches/EndOfRun/EndOfRunRawRevealCompletionPatch.cs`]
- `UploadPump.Dispose` is a two-point dispose: release arm subscriptions first, dispose the session only after the drain callback. Merging them lets an in-flight `RunAttemptAsync` hit disposed resources. [`src/BazaarPlusPlus.Core/Game/Upload/UploadPump.cs` | ADR-0005]
- Saved replay audio warmup touches banks with three different owners. The game's `RunInterrupted` (`BoardManager.UnloadBoardAudio`) unloads `SoundManager.PlayingSoundTrackSO`'s banks and the hero board's SFX bank, so the warmup warms only the soundtrack the game plays and hands it over as `PlayingSoundTrackSO` when that is still null. A board SFX bank the warmup loaded itself, on a board that is not the player's, has no game unload path: `ReplayAudioBankOwnership` records it and `AudioBankWarmer.ReleaseOwnedBanks` unloads it once the saved replay settles outside `ReplayState`. That is a `DesktopSavedReplayHost.Notify` notice, not a cleanup step, because on the Exit button the cleanup steps run inside the `ReplayState.Exit` prefix, before the game stops the music. Never `Addressables.Release` the warmed `SoundtrackSO` handle; `PlayingSoundTrackSO` keeps using it, and the game's own `LoadSoundtrack` never releases it either. [`src/BazaarPlusPlus/Game/CombatReplay/Warmup/AudioBankWarmer.cs` | `src/BazaarPlusPlus/Game/CombatReplay/Warmup/ReplayAudioBankOwnership.cs`]
