# Combat Replay, Screenshots, Uploads, And Ghost Battles

Replay recording and playback, optional video capture, end-of-run screenshot capture, bundle sealing, the single upload feed, and ghost battle import.

Combat replay records local PvP battle replay payloads and lets HistoryPanel start playback when a local or downloaded ghost replay payload is available. Video recording is optional and supported on macOS and Windows through platform-native render plugins (Metal/VideoToolbox/AVFoundation; D3D11/Media Foundation); availability is gated by the native plugin and output directory configuration (`src/BazaarPlusPlus/Game/CombatReplay/Video/CombatReplayRecordingGate.cs`).

Local replay payloads are a bounded cache, while battle facts and successful MP4 recordings are durable user artifacts. Startup maintenance runs off the constructor path behind the same operation gate as payload persistence and playback: one bulk SQLite inventory drives orphan cleanup and the `newest 200 ∪ last 30 days` retention policy, and a transactional `ready → delete_pending → evicted` lifecycle makes file failures retryable. Active runs, playback/persistence work, Bundle seal jobs, eligible completed runs that may still seal, and pending outbox rows are protected. History reads `has_local_payload` instead of assuming replay eligibility. Video ownership and file health are orthogonal (`attachment_state` and `file_state`): run deletion detaches metadata in the run-delete transaction but keeps completed MP4s; reconcile marks missing/recovered files, reports unknown successful MP4s without deleting them, and removes only expired unprotected temporary/failed residue. Detached recording metadata remains in the store (`src/BazaarPlusPlus/Game/CombatReplay/ReplayPayloadMaintenanceService.cs`, `src/BazaarPlusPlus/Game/CombatReplay/Video/ReplayVideoArtifactMaintenanceService.cs`).

To read a replay payload outside Unity, decode through `CombatReplayPayloadStore` plus `MessagePackSerializer.Deserialize<NetMessageGameSim/NetMessageCombatSim>` with `MessagePackConfig.Options`; `CombatReplayLoader` returns an Assembly-CSharp type, so it only works inside the game process.

`tests/CombatImpact.Corpus/` is the opt-in offline acceptance module for the complete Combat Impact model. It is deliberately excluded from `tests/BazaarPlusPlus.Tests.slnx`; the default suite references it only for compile protection and never executes its corpus gate. `just mod::test-corpus <path>` is its only normal interface, and its retained evidence records the corpus artifacts, `GameData.db`, and interpreting game assemblies so results reproduce against the same inputs.

Saved-replay playback state algebra lives in the pure `SavedReplayLifecycle` core; `CombatReplayRuntime` is its translation layer, which executes publishes, portrait cleanup, and menu dispatch but holds no transition logic (`src/BazaarPlusPlus/Game/CombatReplay/SavedReplayLifecycle.cs`; behavior tests in `tests/CombatReplayPlaybackLogging.Tests/SavedReplayLifecycleTests.cs`). The load-bearing states and windows (staged start commits, the shared 15-second exit-suppression latch, the two-phase exit decision, pending menu-return polling) are enumerated in ADR-0005.

Saved-replay startup treats the native `ReplayState.SpawnCombatCards` task as the board-readiness boundary. Native state entry starts that task without awaiting it, so sampling active item setup or `BoardManager` flags alone can observe a false quiet frame before the first controller activates. The Harmony seam tracks both the complete board-spawn task and individual item setup tasks inside a scoped `ReplayPresentationTaskTracker`; startup waits until all tracked work completes and a render boundary passes without discovering new work, under the existing bounded failure rollback (`src/BazaarPlusPlus/Patches/Combat/CombatReplayItemPresentationReadinessPatch.cs`, `src/BazaarPlusPlus/Game/CombatReplay/Bootstrap/ReplayItemPresentationReadiness.cs`). Fixed delays and expected-controller counts are not substitutes for this native work boundary.

`CombatReplayVideoRecorder` owns the video capture session (`src/BazaarPlusPlus/Game/CombatReplay/Video/CombatReplayVideoRecorder.cs`). Two contracts hold across it: audio capture is additive (tap failure never aborts video recording, and only usable sample-bearing WAVs are retained), and on playback end the finalization inputs are frozen into detached contexts with encoder drain/audio mux/metadata completion dispatched off the main thread, so a later replay cannot overwrite them (`src/BazaarPlusPlus/Game/CombatReplay/Audio/ReplayAudioTapStopper.cs`).

BPP UI chrome suppression is centralized in `Game/OverlayPanels`: screenshot mode hides the CollectionPanel dock button and the combat status bar; replay recording mode hides only the dock button, intentionally leaving the combat status bar visible; there is no separate settings-dock suppression target (`src/BazaarPlusPlus/Game/OverlayPanels/BppUiChromeSuppression.cs`). Native tooltip suppression is a separate shared, owner-scoped adapter in `GameInterop/Tooltips`: replay presentation, replay video, and end-of-run capture hold independent leases; high- and low-level native show paths are gated while any lease is active, and cleanup unlocks and conceals primary, secondary, auxiliary, and locked tooltips. Controller discovery includes inactive objects so the native parent's current controller remains authoritative, but an inactive controller no longer owned by that parent cannot render while the show gates are held and is skipped as stale for that audit. Active or authoritative controllers still require their native visibility surface; unavailable surfaces retain the fail-open degraded-capture path. Debug sampling records both the stable native audit reason and the maximum skipped inactive-controller count (`src/BazaarPlusPlus/GameInterop/Tooltips/NativeTooltipSuppression.cs`, `src/BazaarPlusPlus/Patches/Tooltips/NativeTooltipSuppressionPatches.cs`).

End-of-run capture is one run-scoped `EndOfRunCaptureWorkflow`: its core owns readiness, bounded attempts, deadlines, artifact validation, Continue blocking, and the single terminal outcome (`src/BazaarPlusPlus/Game/Screenshots/EndOfRunCaptureWorkflowCore.cs`), with the internal `EndOfRunCaptureDriver` as its Unity/native surface adapter (`src/BazaarPlusPlus/Game/Screenshots/EndOfRunCaptureDriver.cs`). The contracts that must hold: readiness requires native reveal start, a cleared screen transition, settled skills, and either 500 ms of structural card-pose stability after observed motion or the native `FaceUp` completion fallback (empty card boards retain their native settled path), and readiness starts capture automatically. Each attempt acquires BPP and native-tooltip suppression, clears hover/locked state, and passes a second bounded clean-frame barrier (native tooltip visibility audits clean and the post-clean card hierarchy stays structurally stable for a fresh 500 ms window) before `ScreenCapture` runs. The barrier is best-effort: missing native seams, unavailable visual audits, preparation exceptions, or the deadline degrade to an immediate capture with a terminal reason instead of dropping the artifact (`src/BazaarPlusPlus/Game/Screenshots/EndOfRunCleanFramePreparationCore.cs`). Suppression leases remain held until the captured frame's RGBA pixels have been copied out of Unity when preparation remains available; Run metadata (day, victories, hero, rank, rating, and placement) is copied into an immutable value immediately before frame capture; persistence reads only that value, never the later live run. Continue is released at that boundary, while PNG encoding, atomic file write, and metadata persistence continue in the background without consuming or replaying the native click. A verified PNG is never deleted or recaptured when metadata persistence fails or times out; a late artifact from a capture canceled before frame acquisition is deleted. Composition exposes the workflow's two-intent interface to patches before mounting the driver, so the Continue and raw reveal patches fail open during startup and teardown (`src/BazaarPlusPlus/BppComposition.cs`, `src/BazaarPlusPlus/Patches/EndOfRun/`).

`BundleSealCoordinator` is the single background workflow owner of V5 input convergence, payload composition, screenshot JPEG budgeting, deterministic bundle construction, self-open verification, atomic publication, and crash reconciliation; event-bus handlers only enqueue wakes (`src/BazaarPlusPlus/Game/BundlePipeline/BundleSealCoordinator.cs`). Stable bundle id/time are allocated before file creation, and startup recovery adopts a renamed file only when its durable allocation identity matches. The convergence/queue ownership split (pure `BundleSealConvergence` decisions, Storage-owned `BundleQueueStore` SQL) is recorded in ADR-0006. Every seal-path failure is decided by `BundleSealFailurePolicy` from the stage it happened in and its exception graph, then recorded through `BundleQueueStore.RecordSealFailure` (state, consecutive `attempts` for that code, time, bounded diagnostic) and logged with the original exception under a storm-limited category (`bundle_pipeline.seal.deferred`, `.environment_blocked`, `.degraded`, `.terminal`). Runtime failures (missing member, type load, assembly binding, type initializer) park the Run as waiting with `seal_environment_blocked`: it runs again once per launch, so a mod or game update retries it without a migration, and it ends as `seal_environment_blocked_expired` only after five parked launches and 60 days past its input deadline. Other failures retry with exponential backoff (5 s to 1 h) and end as `seal_retry_exhausted` only after eight consecutive failures and 14 days; codec failures in payload encoding or Bundle build are terminal at once. Each Run is attempted in isolation and skipped while backing off, so one failing Run cannot abort a pass or starve later Runs. A replay that exists but cannot be used is reported by `RunPayloadComposer` with its decode exception: invalid data omits that replay with a `replay_invalid` log, an unreadable file retries the Run, and a runtime failure parks it. File recovery and pending-file validation are per file; a runtime that cannot open a Bundle neither deletes an orphan nor invalidates a pending outbox, and maintenance failures never stop waiting Runs from sealing (`BundleSealCoordinator.ReconcileAsync`).

Opening a database from before the JSON compatibility repair (user_version 2) applies a transactional, one-time queue migration (`RunLogSchema.EnsureInitialized`, `BundleQueueStore.RecoverLegacyJsonFailures`). Only terminal `bundle_build_failed` jobs whose diagnostic identifies a missing Newtonsoft `JToken` method return to waiting; allocations and original convergence deadlines survive, and jobs with a pending or uploaded outbox stay unchanged. A later failure cannot trigger the migration again; later runtime failures are handled by environment parking instead, and the migration's text match stays frozen until user_version 2 databases are no longer supported. This also covers reseal jobs created after `pending_file_invalid`; permanent outboxes without an attributed seal job are not revived. Terminal inputs may already have been cleaned up, and previously scheduled replay deletions still complete. Missing replay or screenshot inputs follow the existing convergence degradation; a Run-only Bundle does not create a BazaarDB screenshot delivery.

A reconcile pass arms uploads once after publishing its backlog, including partial progress before cancellation, so each recovered run cannot independently bypass the pump cadence. Pending-file invalidation checks the current outbox state in its transaction; a stale validation result cannot overwrite a completed upload (`BundleSealCoordinator.ReconcileAsync`, `BundleQueueStore.FailOutboxAndScheduleReseal`). Only that explicit invalidation schedules a reseal: any outbox row ends a run's eligibility, so a server rejection or local retention expiry is final instead of sealing a replacement Bundle on every pass (`BundleQueueStore.EnsureEligibleJobs`).

There is exactly one upload feed and one `BackgroundUploadPump`: each `BundleUploadFeed.Session` owns a `ModApiSession`, sends immutable `.bundle` files to `POST /bundles` with `Content-Length` and `Content-Digest`, maps typed endpoint dispositions, persists retry time through `BundleQueueStore`, and commits success before deleting through the narrow `IBundleOutboxFiles` port (`src/BazaarPlusPlus/Game/BundlePipeline/`). Ghost discovery uses `GET /ghost-battles?limit=200`; replay download uses the plugin-owned History session, validates the bundle and run identities through `RunBundleV5Contract`, reconstructs only a complete target battle, saves it atomically, and persists `remote_available`, `local_ready`, `unavailable_payload`, or `expired` so permanent failures are not retried (`src/BazaarPlusPlus/Game/HistoryPanel/Ghost/`). Discovery restores legacy `ghost_bundle_invalid` failures for one new import attempt; new unexpected import failures use `ghost_bundle_import_failed` and remain terminal across syncs. The exact wire and payload contracts are documented in `docs/contracts/run-payload-v5.md`; transport/result/persistence ownership is recorded in ADR-0006.
