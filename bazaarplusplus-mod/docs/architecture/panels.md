# Overlay Panels, History, And Live Build

Main-overlay-panel lifecycle, the native HistoryPanel surface, and the board adapters used by HistoryPanel and LiveBuildPanel.

`Game/OverlayPanels/OverlayPanelHost.cs` is the single Unity adapter that owns main-overlay-panel lifecycle: it reads per-frame input (escape, panel toggle hotkeys, combat state, scene changes), runs the pure `OverlayLifecycleCore` rules, and dispatches open/close/tick to registered panels (`src/BazaarPlusPlus/Game/OverlayPanels/OverlayPanelHost.cs`). It mounts before every panel mount, and CollectionPanel, HistoryPanel, and LiveBuildPanel all register through its accessor, enforcing at-most-one-open-panel (`src/BazaarPlusPlus/BppComposition.cs`). Lifecycle tests live in `tests/OverlayPanelLifecycle.Tests/`.

HistoryPanel is mounted through `HistoryPanelMount` with a single-constructor `HistoryPanelDependencies` (run state, data service, replay service, optional probe/link surfaces, and the combat-replay directory path as a plain string); run state is the read-only two-member `IHistoryPanelRunState` (`IsInGameRun`, `CurrentServerRunId`) adapting `IRunContext` (`src/BazaarPlusPlus/Game/HistoryPanel/IHistoryPanelRunState.cs`, `src/BazaarPlusPlus/Game/HistoryPanel/HistoryPanelDependencies.cs`). Its owned uGUI view uses native artwork, portraits and trophies with scrolling run/battle lists (`src/BazaarPlusPlus/Game/HistoryPanel/Ui/HistoryPanelView.cs`). `HistoryPanel.NativeBoards.cs` projects a single normalized snapshot set into native cards and skills for `GameInterop/MonsterBoardPreview/OwnedMonsterBoardPreview.cs`. Each adapter owns a `MonsterBoardTooltip` clone, preserves native card pooling, and fits the carpet independently of its scrolling skills. Each board carries only a persistent ownership title directly above it; opponent identity, rank, rating and outcome stay in the battle list. Ownership wording is section-dependent: Runs shows the opponent above the local player, while Ghost drops the opponent rect entirely and the single surviving board is the CHALLENGER's, because ghost payloads stay in recorder perspective (ADR-0002) and `BuildPlayer` reads `Snapshots.PlayerHand`. Neither native history controllers nor the active monster tooltip are reused.

`HistoryPanelLayout` is the panel's Unity-free geometry record, compiled directly into `tests/PureBehavior.Tests`. It owns the column spans, archive row heights, the board and title rects, and the day strip, and it is the single place top-down authoring flips into Unity's bottom-up anchors. Because the panel matches `.5`, a normalized value is worth a different number of canvas units at every aspect ratio, so its tests assert against aspect ratios rather than resolutions. The run archive uses compact rows with hero identity, mode, day, completed duration in whole minutes and timestamp; the rank and numeric Legendary rating precede the rightmost outcome trophy. Ghost archive rows retain their taller layout. The battle timeline is a narrow vertical rail between the archive and the boards, one chip per battle with portrait, day and rank across the top, a numeric Legendary rating beneath the rank, the opponent's name below, and an outcome bar along the bottom. It keeps the page's newest-first order: the latest day appears at the top, matching the archive and the newer/older pager arrows. Row slots and battle indices are identical. It scrolls and pages because a run has no hard battle cap. The win target ends a run at ten wins, but losses only drain prestige. The boards are width-constrained (the carpet wants 2600:550), so the rail's width comes directly out of card size, and the two boards are always the same height because they are peers.

`HistoryPanelCoordinator` owns page, selection and detail state. Each page owns its rows and cursors together; visible rows are read-only projections of that page, while the view takes a separate render snapshot. Summary records carry metadata only, and selected-detail state owns the loaded board snapshots. Run and battle pages use time/ID cursors and a maximum of 40 summaries; indexed SQL applies hero, outcome, day and account filters before the limit (`src/BazaarPlusPlus/Game/HistoryPanel/Storage/HistoryPanelRepository.Pages.cs`). Snapshot JSON and Ghost payloads are read only for the selected detail. Each read channel keeps one running operation and one replaceable pending request; session/account/selection checks prevent obsolete publication. The persistent view reuses 40 archive rows and 40 battle rows. The archive retains record IDs and visible scroll anchors across refreshes. `HistoryTimelineScroll` preserves the timeline's exact offset on refresh and on clicks, including partly visible rows; a changed selection entirely outside the viewport is revealed at the nearest edge, without centering or row snapping. Temporary empty loading pages retain the previous offset and selection until rows return; subsequent detail or badge refreshes leave manual scrolling alone.

Downloaded Ghost facts remain visible regardless of discovery age. Maintenance traverses hidden `local_ready` rows in bounded batches and restores only payloads with matching battle/account identities; the conditional update also checks bundle identity. Undownloaded facts expire after the discovery window. Ghost files are bounded to 16 MiB compressed and 64 MiB expanded; rejection preserves the file (`src/BazaarPlusPlus/Game/HistoryPanel/Storage/HistoryPanelDataService.cs`). Native Gameplay/MenuShortcuts input is suppressed by a manager-scoped lease while the account input is focused, reapplied after native context updates, and restored from the current context when focus ends (`src/BazaarPlusPlus/GameInterop/Input/NativeTextInputLease.cs`).

HistoryPanel keeps replay, recording and deletion beside the archive. Its More dialog contains database status, remote health probing, supporter attribution and the BazaarDB account-link form (`src/BazaarPlusPlus/Game/HistoryPanel/Ui/HistoryPanelView.Actions.cs`). The dialog owns a foreground canvas above the native board canvases. The account-link card POSTs a one-time code to the bazaardb.gg redeem endpoint through `BazaarDbLinkClient`, built at startup on a dedicated 30s-timeout HttpClient independent of the mod-api base URL (`src/BazaarPlusPlus/Plugin.cs`), with link state persisted by `Game/HistoryPanel/AccountLink/BazaarDbAccountLinkStore.cs`. Server health display state is derived from the mod API health probe result without changing storage state (`src/BazaarPlusPlus/Game/HistoryPanel/HistoryPanelServerHealth.cs`).

`HistoryPanelMenuEntry` appends an owned data row after merchandise in the native navigation menu. `HistoryPanelMenuPatches` reaches it through `BppPatchHost`. Accepted replay launches retain the history origin; when the replay session finishes and `SceneLoader.ActiveScene` is `HeroSelectScene`, the panel reopens with its selection and scroll positions preserved.

`GameInterop/ItemBoardPreview` provides board planning shared by HistoryPanel and LiveBuildPanel. `BppItemBoardSlotPlanner` plans cards onto a 10-socket board, with special handling for selectable shop/container boards (`src/BazaarPlusPlus/GameInterop/ItemBoardPreview/BppItemBoardSlotPlanner.cs`). Both panels project planned items through `NativeMonsterBoardItemMapper` and render owned native `MonsterBoardTooltip` instances through `GameInterop/MonsterBoardPreview`; Collection retains the shared measured frame-height proportion for its independent card fitter.

LiveBuildPanel owns an opaque full-screen uGUI view over the native Collection background. A right overview holds the title with a top-right close action, a compact corpus section with its refresh action in the heading and freshness/status underneath, a build navigation section with the page count and two large previous/next buttons, and a vertical supporter list. Four simultaneous peer sections on the left show recommendation, shop, stash, and current board; fine rules and spacing separate their contents over one consistently dimmed native backdrop, with a stronger rule for the recommendation. The overview uses a vertical rule rather than an opaque slab. Navigation chevrons use one closed mesh with shared vertices through the elbow. `LiveBuildPanelLayout` divides the height-scaled canvas between equal item-only carpet regions after reserving headers, metrics, and candidate tags; the carpet is height-constrained, so every unit given to the metrics row is taken from card size. Match evidence renders as one fixed cell per metric (an 11px label over a 16px value) because a single concatenated line ellipsized the last metric away on narrow panels, and the no-recommendation guidance owns a separate slot rather than sharing the metric styling. Native sockets and size spans determine placement. Titles, empty/loading status, and metrics align with the loaded carpet's horizontal bounds; those bounds position the overview and section decoration without resizing the preview region itself. Candidate state remains feature-owned and keyed by template id across selectable sources; the native adapter reports loaded frame geometry and template identity, and the view positions non-interactive native-art tags beneath those frames. Native hover stays on the prefab. Replacement and close synchronously end the tracked hover; close hides and detaches each owned root before waiting for native acquisition to finish and settling all rentals, including failed setup. No card setup is cancelled mid-acquisition. A weak identity gate rejects late native tooltip shows after the owning board retires, without hiding another owner’s tooltip.

The board adapter uses `NativeCardPrefabLoader` to rent native prefabs, records ownership before Resize/SetUp, validates loaded art/frame state, and restores prefab layout before pool return. Missing templates are cached per static-data manager; partial failure preserves successful cards. Item and skill hover events register borrowed targets with `NativeCardPreviewHost`, which applies the existing tooltip refresh transaction without owning board rentals. Locked/secondary tooltips retain their existing skip policy. Geometry revisions drive LiveBuild marker updates; stable frames skip forced layout, recursive board fitting and marker rebuilds.
