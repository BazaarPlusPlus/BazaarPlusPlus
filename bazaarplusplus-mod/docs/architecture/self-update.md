# Self-update

The mod updates its own Managed Payload (root `GLOSSARY.md`). On the desktop Core downloads and stages it; on Android the Android App stages it before each BPP launch (root ADR 0012). The Updater swaps it in at the next start. ADR-0014 records why the work is split this way.

## Shape

- **Check.** `MainMenuVersionCheckController` (desktop) or `AndroidVersionCheck` (Android) reads its platform's Platform Release Manifest from the dedicated mod endpoint selected by `ReleaseManifestEndpoints.ForPlatformKey`, through `ReleaseManifestClient`. `MainMenuSelfUpdate` passes the result to `SelfUpdatePolicy` together with `RunningManagedPayload`, which is the version, `RunLogSchema.LocalDatabaseSchemaVersion`, and the digest of the runtime it runs on: the installed manifest's, or, inside the Android App, the Launch Record's `app.nonManagedPayloadDigest` (`AndroidLaunch.RuntimeDigest`), since the installed Mods may have been staged by an earlier App with another runtime. A record of another process, or a development App's record with no digest, leaves the installed manifest's. Each check logs `self_update.release.checked`. Android checks on every main-menu visit through one `HttpClient` for the process; `ReleaseManifestClient` remembers its last successful tagged answer with the `ETag` and asks with `If-None-Match`, so a `304` returns that answer and every visit still sees a newly published version.
- **Stage.** `SelfUpdateStaging.Ensure` keeps one staging per version in flight and retries after a failure. `ManagedPayloadStager` downloads into `<Data Root>/Updates/.download-<version>-<guid>/`, verifies the zip and then the extracted files, and renames the directory to `Updates/<version>/`. It logs `self_update.payload.staged` or `self_update.payload.stage_failed` with a `reason_code`. Android stages nothing: `AndroidVersionCheck.CreateSelfUpdate` gives `MainMenuSelfUpdate` no download transport (`MainMenuSelfUpdate.StagesManagedPayload` is false), so a `Stage` decision only shows `RestartFromApp`, and the Mods swapped in are always the ones the App staged for the interop it loaded.
- **Label.** `MainMenuVersionLabelFormatter` appends the `MainMenuUpdateStatus` the check last published (`MainMenuSelfUpdate.StatusFor`); it owns the label text: "restart to update" for a staged version, "restart from the BPP App" for one only the Android App stages, and "update via installer" or, on Android, "install the new BPP App" for a release the copy cannot take. On Android it also names Compatibility Mode after the BPP version. The status is process-wide and carries over between main-menu visits.
- **Swap.** `ManagedPayloadSwap` in `src/BazaarPlusPlus.Updater/` runs from `BepInExPatcher.Initialize` or `MelonUpdaterPlugin.OnPreInitialization`. It writes its journal and backups under `Updates/.swap/`. Its log lines read `[BPP][Updater] event=updater.*` and go to the loader's log, not through `BppLog`. On Android `UpdaterRun.RuntimeDigest` first reads the Launch Record (`updater.launch_record.read`); when it parses and this process wrote it, the staged manifest's non-managed digest is compared with the record's `app.nonManagedPayloadDigest` instead of the installed manifest's, while the history schema and the newer-version rule still compare with the installed manifest. No record, an unreadable one, another process's, or a development App's without a digest keeps the installed manifest's rule.

Every desktop release still ships a complete installer containing that version's Payload, alongside the Managed Payload zip. If the game cannot download an update or the installed environment is incompatible, the user can download the installer from the website and install the release. The installer does not check or download the mod separately. Both update endpoints publish the same release record; root [ADR 0011](../../../docs/adr/0011-separate-mod-update-endpoint.md) owns that decision.

## Build and test

The Updater builds both targets. Each host project references one of them with `ReferenceOutputAssembly=false`, and the generated `Payload.targets` places that build. `tests/Updater.Tests` covers verification and the swap, and reads the Android App's Launch Record golden, `../bazaarplusplus-android/contracts/launch-record.v1.json`, and its mutations (`LaunchRecordTests`). `tests/SelfUpdate.Tests` stages with Core and then swaps with the Updater.

To check a swap by hand:

1. Build a newer Managed Payload zip with `release/managed-payload.mjs`.
2. Stage it with `ManagedPayloadStager` into the game's Data Root.
3. Start the game. The loader log shows `updater.swap.applied`, or `updater.staged.rejected` with its `reason_code`.

## Gotchas

- A development build has no installed manifest. Core therefore never stages for it, and the Updater compares only versions. An installed manifest that exists but does not parse makes the Updater refuse every staged payload (`installed_manifest_invalid`).
- On Android a swapped `MelonLoader/UserLibs/` file loads one launch late (ADR-0014).
- `ManagedPayloadStager` verifies a staged version once per instance and remembers it, so Android's per-visit check does not re-hash `Updates/<version>/`. If that directory is deleted or corrupted later in the session, the decision stays `Staged`, nothing stages it again this session, and the label keeps saying restart to update. That restart's Updater finds nothing valid to swap, the next session (on Android, the Android App's next launch) stages the version again, and the update lands one start later. For a version staged in the same session `SelfUpdateStaging.Ensure` already behaved this way; the memo extends it to a version an earlier session staged and this one verified.
