# Hotkeys And The Settings Dock

User-rebindable hotkeys and the settings dock: how a row is contributed, where its order comes from, and how binding paths are normalized.

Settings-dock rows themselves are data: every cycling or boolean row is a `CyclingSettingsDockEntry<T>` (with a `Toggle` factory for the bool case) built by a per-feature static factory supplying order, key, value ladder, read/write delegates, highlight predicate, status text, and an optional `onChanged` hook (`src/BazaarPlusPlus.Core/Game/Settings/CyclingSettingsDockEntry.cs`). Only the history-panel action button and the force-lockable end-of-run screenshot toggle remain hand-built definitions; the History row is Core's `HistoryPanelSettingsDockEntry`, which the desktop gives its hotkey label (`HistoryPanelHotkeyDockEntry`).

BPP hotkeys are user-rebindable and persisted in config per action. `BppHotkeyActionId` covers five actions: the two hold-preview hotkeys (Ctrl enchant / Shift upgrade defaults) plus toggles for CollectionPanel, LiveBuildPanel, and HistoryPanel (`src/BazaarPlusPlus/Game/Input/BppHotkeyActionId.cs`); rebinding rows are cloned from native settings rows (`src/BazaarPlusPlus/Game/Input/BppKeyBindRowController.cs`), and panel toggle presses are resolved per frame by the Overlay Panel Host. Binding-path normalization, ctrl/shift alias expansion, conflict detection, and the default/display data tables are the pure `HotkeyBindingPathCore` (`src/BazaarPlusPlus/Game/Input/HotkeyBindingPathCore.cs`, compile-linked into the zero-ManagedPath `tests/HotkeyBindingPath.Tests/`); `BppHotkeyService` remains the Unity/config facade. Binding paths in `BazaarPlusPlus.cfg` `[Hotkeys]` are untrusted input: junk normalizes to empty and falls back to the action default. The Android host has no keyboard: its touch settings are [mobile-ui.md](mobile-ui.md)'s.

The settings dock registers all feature rows through `SettingsDockEntryRegistry` with order constants centralized in `BppSettingsDockOrder`; the registry, `BppSettingsDockCatalog`, the order, and the Enchant preview and History rows are Core's (`src/BazaarPlusPlus.Core/Game/Settings/`), so the Android host registers its own roster through them into the same native dialog ([android-host.md](android-host.md)); the roster spans history, name override, bilingual item names, cosmetic names, legendary position, enchant preview, event and quest previews, combat status bar, Chinese locale, supporter list, voice subtitles, end-of-run screenshot, BazaarDB upload, and the platform-gated graphics upscaling rows (`src/BazaarPlusPlus/MonoHostComposition.cs`). There is no BPP font selector because all BPP-owned game UI follows the game's font assets.

Both hosts draw the rows in the game's own settings dialog, and what a row shows is decided in Core's `BppSettingsSectionRules` (`src/BazaarPlusPlus.Core/Game/Settings/BppSettingsSectionRules.cs`). `BuildOrder` puts toggles, then choices, then actions, in catalog order inside each kind. `Resolve` calls each delegate of a row once per refresh, an invisible row's too, and returns a `BppSettingsRowState`: a choice is always interactable, its selected index is clamped to its options, and a choice whose state is null leaves its dropdown as it is. `SameState` compares two refreshes field by field and option by option, and a host writes its rows only on a change or a forced refresh. `StandardIndex` ignores a pick of the synthetic current option and shifts the others by one; it passes any other index on, and the row's `SelectStandardChoice` ignores one outside its values. `OnActionTap` ignores a tap on an inactive action and closes the dialog first for a collapsing one. The hosts read the language code, find and clone the donor rows, hide the footer and write the states onto their controls: `BppNativeSettingsSectionController` on the desktop, which also pairs the toggles in two columns, and `AndroidNativeSettingsSection` on Android, which also makes each row a touch target and dims an inactive action. Core does not catch: an exception from a definition reaches the host, where Android drops the section and the desktop does not catch.

The combat status bar's settings-dock toggle controls visibility during runs and replays and persists through `BppSettings.EnableCombatStatusBarConfig`; while it is off the bar prepares no fonts and builds no canvas until it is switched on (`src/BazaarPlusPlus/Game/CombatStatusBar/CombatStatusBar.Canvas.cs`, `EnsureUi`); hiding paused controls resumes playback without resetting the preferred speed (`src/BazaarPlusPlus.Core/Game/CombatStatusBar/CombatStatusBarSettingsDockEntry.cs`, `Create`, whose hook the desktop gives; `src/BazaarPlusPlus.Core/Game/CombatStatusBar/CombatStatusBarState.cs`, `OnVisibilitySettingChanged`). It keeps its plugin-owned mount and screen-space layout. Portrait bounds supply geometry only; rendering uses the native PvP transition canvas's camera and plane distance on `AboveBoard`, below the native transition backgrounds. This keeps scene decorations behind the controls while allowing the transition curtains to cover them (`src/BazaarPlusPlus/Game/CombatStatusBar/CombatStatusBar.Canvas.cs`, `RefreshLayout`; `src/BazaarPlusPlus/GameInterop/HeroPortraits/NativePlayerPortraitBounds.cs`, `TryRead`).

Cosmetic Names is a default-off boolean in `[CosmeticNames] Enabled`. `CosmeticItemNamePatch` attaches one `CosmeticNameOverlay` to each individual loadout item at `CosmeticItem.SetData`; category buttons are separate native components. The overlay resolves the collectible template's name by item GUID, then tries the asset and sale-item names through the current game localization service, falling back to the English name when no translation exists. Default collectibles with authoring identifiers instead of translated names receive a localized default-item label, keyed by the native `IsDefault` flag. Game-font text uses glyph-geometry centering within the thumbnail's bottom shadow strip; both move upward by at least half a character height. The strip anchors to the image loader's visible viewport rather than its image rectangle, which is wider than the clipped thumbnail for carpets. It reacts to config, game-language, and Chinese locale-mode changes through one `CosmeticNameOverlayObserver` mountable, which reads them once per frame and drives retries only while an overlay is enabled; complete Chinese labels pass through `L.ResolveChinese` before display (`src/BazaarPlusPlus/Game/CosmeticNames/`).

The desktop **Animated Portraits** toggle (`[AnimatedHeroPortraits] Enabled`) replaces static hero portraits on both sides, including saved replays, with the skin’s animated Spine when a reliable composition can be recovered. `Game/HeroPortraits/AnimatedHeroPortraitController` tracks native portrait changes and restores the sprite on disable. `Game/HeroPortraits/PortraitPreparation.PrepareAsync` owns matching, breakout preparation, their caches and the captured-image handoff, returning a prepared result for `NativeAnimatedHeroPortrait.Create`. It checks the portrait and prefab after each asynchronous stage; the controller retains its slot and setup-generation checks before publishing. Unreliable and timed-out matches are remembered for the loaded sprite and animation variant; cancellation by the owning slot remains retryable. Cached portraits prepare during native setup; publication waits until masks and renderers are ready. Native animated portraits retain their own rendering.

After matching, `PortraitPreparation` reuses captured images where available and analyzes sampled poses to keep related prop surfaces together within an exterior-area budget. `PortraitBreakoutAnalyzer.Analyze` uses artwork evidence and local rig relationships; `NativePortraitLayeredRenderer` applies the resulting masks in native draw order without image analysis during playback. Breakout failure or timeout leaves the accepted animation clipped to the strict frame. Numeric plans persist under the Data Root, but their disk keys include captured images and poses: a disk hit still needs capture, while a matching in-memory plan skips preparation. Resource-index candidates do not guarantee a ready breakout plan; a cache miss releases the static-artwork hold before expensive work or waiting for breakout preparation.

## Gotchas

Traps and rules that bite only this feature; most failed silently at least once.

- The BPP hotkey conflict check compares BPP actions only against other BPP actions, never native `Gameplay/*` bindings. [`src/BazaarPlusPlus/Game/Input/BppHotkeyService.cs`]
- Each binding path owns one enabled `InputAction`, which the Input System keeps monitoring until it is disposed. A changed binding is noticed only by raw-value compare in `GetBindingPath`, which disposes the replaced path's action unless another hotkey still resolves to it; release paths there, not in one setter, so a BepInEx config reload is covered too. [`src/BazaarPlusPlus/Game/Input/BppHotkeyService.cs`]
- BPP settings dock buttons are clones of native dock buttons that must avoid native-button bounds and re-sync geometry for several frames after a screen-size change. [`src/BazaarPlusPlus/Game/Settings/BppDockButtonVisuals.cs`]
- Core's `Ui/HudVisibility.DesktopDockButton` hides Collection and Ten-Win Builds on end-of-run screens and during screenshot suppression, and requires each button's setting and available layout. Its touch rules additionally hide under panels, native popups, inspection and scene changes; those touch-only conditions do not change desktop behavior. [`src/BazaarPlusPlus/Game/Settings/BppPanelDockButtonsController.cs`, `ApplyVisibility`]
- The dock layout probe skips any button under a `BPP_`-named object and caches each Transform's name verdict by instance ID until the scene changes, so an object must carry its final name from the frame it is created: renamed to `BPP_` after a probe has seen it, it still counts as a native blocker; renamed away from `BPP_`, it is still skipped. [`src/BazaarPlusPlus/Game/Settings/BppDockButtonScreenLayout.cs`, `HasBppName`]
