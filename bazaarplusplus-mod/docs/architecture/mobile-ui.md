# Mobile UI

How every BPP surface fits a touch screen, on the Android host and on the Mono host on iOS: the panel shortcuts and combat clock by the game's HUD, Collection, History (with its Ghost section and replay entry), Ten-Win Builds, the previews in the game's own tooltip, and Screen Fill. The Android host itself is [android-host.md](android-host.md); the decision for one source tree is [ADR-0025](../adr/0025-one-mobile-ui-source-for-both-hosts.md), for one shared frame [ADR-0018](../adr/0018-android-touch-surfaces-share-one-frame.md), and for touch surfaces on the Mono host [ADR-0024](../adr/0024-mono-host-touch-surfaces-on-mobile.md).

## One source tree

The Mobile UI is `src/BazaarPlusPlus.Mobile/`, namespaces `BazaarPlusPlus.Mobile.*`. It is no project of its own: both host projects compile it through `<Compile Include>`, the Android host always and the Mono host on every platform, though the Mono host installs its port and mounts the Mobile UI only on a mobile platform (`TouchPlatform.IsMobile`); the desktop keeps the Desktop UI in `Game/`. Each host's `GlobalUsings.cs` maps the TextMeshPro namespace and names the game's card preview type `GameCardPreview`. `CoreLayeringTests.Mobile_ui_has_no_second_source_tree` fails on a source file under the Mono host's `Game/Touch/` or `Game/*/Touch/` or the Android host's `Ui/`, where the hand-mirrored copies lived until #701.

| Directory | Holds |
|---|---|
| `MobilePlatform.cs` | the Mobile Platform Port, `IMobilePlatformPort`, its holder `MobilePlatform` and the records it hands over (native art, the skill overlay) |
| `MobilePanelHandle.cs` | a panel's handle on the Overlay Panel Host, with the source of its last open and the reason of its last close |
| `Ui/` | the kit (`UiKit`, `ChipFlow`, `NativeSkin`, `PortraitView`, `KeywordSprites`, `TouchScreen`, `UiActions`), `ScrollTracker`, `ArtImage`, `InspectionText`, and `InGameTheme.g.cs`, which `just design::build` generates |
| `LiveBuild/`, `Collection/`, `History/` | the three Main Overlay Panels: Ten-Win Builds, Collection, History |
| `Hud/` | the HUD: the panel shortcuts (`TouchShortcuts`), the combat clock (`TouchCombatClock`) |
| `Previews/` | the item tooltip's preview switches (`TouchPreviewSwitches`) and the enchant preview (`TouchEnchantPreview`), with the host reads they use (`ITooltipPreviewHost`, `IEnchantPreviewHost`) |
| `NativeAdjustment/` | Screen Fill's flow (`TouchScreenFill`), its day clock and canvases, with the host read it uses (`IScreenFillHost`) |

Host services reach it through Core ports each composition binds: `ISupporterRotation` for the supporter credit, for Collection its card catalog, run reads and encounter state ([collection.md](collection.md)), and for History its `HistoryPanelDependencies` and card templates (`IHistoryCardTemplates`).

## Panels, the HUD and the frame tick

The Mobile UI has no frame driver of its own: both hosts tick it through Core's Overlay Panel Host ([panels.md](panels.md), ADR-0022), which each host feeds a frame and its scene. Each panel registers through the port's overlay registration (`MobilePanelHandle`) under one id on both hosts, `live_build`, `collection` or `history`, with no toggle hotkey: a touch screen has no keyboard. The host keeps one panel open, closes it for combat, a scene change by its policy and the back key, and ticks it every frame. History is built when the host starts, since its coordinator returns from a replay while it is closed; Collection and Ten-Win Builds build their views on the first open.

The HUD (`Hud/TouchHud`) is no panel, but it registers the same way under the id `hud` with a registration that never opens, so the host ticks it every frame and tells it of a scene change; `overlay_panels.*` log lines can name `panel_id=hud`. Nothing may call `RequestOpen` on it: the host would close the open panel as superseded and then fail the HUD's open. Each tick runs Screen Fill and the preview switches first, each catching its own failure, then the shortcuts and the combat clock. On a scene change the clock drops its plaque and the switches clear.

## Screen Fill and Native Adjustments

A Native Adjustment is a change BPP makes to the game's own UI (root `GLOSSARY.md`): its decision is Core's, its flow the Mobile UI's, and its reads and writes of game objects the host's. Screen Fill lets the game fill a landscape screen narrower than 16:10, such as an iPad's or a foldable's inner display, instead of letterboxing it: Core's `Ui/ScreenFill` decides every threshold and size (tested in `tests/SettingsDockCore.Tests/ScreenFillTests.cs`), `NativeAdjustment/TouchScreenFill` runs it from the HUD's tick on both hosts (`touch.screen_fill.*`), moves the day clock (`TouchDayClock`) and keeps canvases as wide as 16:10 (`TouchScreenFillCanvases`), and each host's `IScreenFillHost` lowers `LetterBoxManager`'s floor and its camera patch widens the field of view. The combat clock follows the lowered board through `TouchScreenFill.BoardTop`. The HUD shortcuts, the tooltip switches and History's menu entries are Native Adjustments too.

## Log ids

Mobile UI events use the `Touch` scope and `touch.<area>.<event>` ids on both hosts: `touch.live_build.*`, `touch.collection.*`, `touch.history.*`, `touch.hud.*`, `touch.combat_status.*`, `touch.preview.*`, `touch.enchant_preview.*`, `touch.screen_fill.*`, `touch.card_text.*`. A host adapter keeps its host's ids: the Android host's adapters log under the `Android` scope (`android.back_key.*`, `android.native_art.skin_loaded`, `android.ui.mounted`), the Mono host's under `Touch`.

## Differences between the hosts

Each difference below is a deliberate choice or a host constraint; anything else behaves the same on both.

- **Threads.** Android's main-thread scope is its own pump (`AndroidMainThread`), because IL2CPP installs no synchronization context; on Mono the scope is empty and Unity's context resumes awaits. Liveness reads `WasCollected` on IL2CPP and `== null` on Mono, and casts go through Il2CppInterop on Android.
- **Entries.** Collection and Ten-Win Builds open from the HUD shortcuts on both hosts. History has no shortcut: each host adds it to the game's own menus (on Android the lobby's MENU grid and the in-run menu, on the Mono host the game menu, as on the desktop) and to the settings rows.
- **Collection.** Android binds no encounter state and no day tiers, so it preselects no merchant and its Day gate filters nothing; iOS preselects the merchant and filters by tier. Each host warms its catalog before the first open itself ([collection.md](collection.md)).
- **Card rental release.** `AndroidOverlayPanels` releases the rented cards through the melon's delegate, `DesktopOverlayPanels` through `TouchCardRental`; both on a scene change, never on a plain close.
- **Back key.** Android answers the back key inside the game's escape hook and its own keyboard read, and collapses an expanded tooltip section before the game handles another Back; iOS has no back key, and a hardware keyboard's Escape closes the top-most surface as `back_key`.
- **Tooltip.** Android's switches follow the tooltip its render patch hands over, and it keeps a tap on a switch from dismissing the tooltip (`CardTooltipHidePatch`); the Mono host reads the shown tooltip each frame. The upgrade setting is per host: `[Android] UpgradePreview`, `[Touch] UpgradePreview`.
- **End-of-run screenshot.** Only the Mono host takes one: it hides the shortcuts and the clock from the frame it begins in (`TouchShortcutSuppression`, `BppUiChromeSuppression`). Android takes none.
- **Animations.** Android follows the system's Remove animations switch; the Mono host always animates.

## The shared frame

`Core/Ui/TouchMetrics` turns the screen (size, `Screen.dpi`, `Screen.safeArea`) into the overlay canvas's units. The canvas scales with the screen's height (`UiKit.CreateOverlayCanvas`), so one dp is a different number of canvas units on every screen; layouts always ask `TouchMetrics.Dp`, `Sp` and `Target`, never a constant in canvas units. A device that reports no density reads as `TouchMetrics.FallbackDpi`.

`Core/Ui/TouchChrome` is the frame every surface lays out in: the sheet (the safe area less a margin), its body (less a padding), the gap, the header row, the type scale, and the close button. Each panel's own layout (`CollectionTouchLayout`, `HistoryTouchLayout`, `LiveBuildTouchLayout`) starts from it and places only its own content. `TouchChrome.Inspect` is the tap-to-inspect sheet all three card panels share (`TouchInspectLayout`). All of it is Unity-free and tested in `tests/SettingsDockCore.Tests/TouchChromeTests.cs` on the screens below.

## Conventions

- **Targets.** Every button, tab, chip, row, and search field is at least `TouchMetrics.MinTargetDp` (48 dp) tall, and a close button is `TouchChrome.CloseWidthDp` wide. A card socket a tap picks is a target too: Ten-Win Builds keeps every socket at least 48 dp wide, and where its boards beside the overview would leave one narrower, or the overview's column too short for the metric cells (`LiveBuildTouchLayout.MinMetricCellDp`), as on a dense screen, it stacks (`LiveBuildTouchLayout.Stacked`): the final build's title band and close stay as a header and the boards, then the overview, scroll under it. The game's own settings dialog keeps its native rows and grows their hit areas instead (`TouchMetrics.MissingTargetPixels`, android-host.md).
- **Text.** No text on a BPP surface is under `TouchMetrics.MinBodySp` (12 sp); `TouchMetrics.Sp` refuses less. Text BPP adds inside the game's own tooltip follows the tooltip instead (Previews, below). The scale is `TouchChrome`'s: a title, a card name, a button or chip, body text, in falling order. A `UiKit` button's label sits `TouchChrome.LabelInsetDp` in from either side, the same dp on every screen; History's buttons keep their own palette's padding. A chip's label shrinks to fit (TMP autosize) between the button and body sizes, then ellipsizes; it never wraps. The Collection inspection measures its labels at body size first and drops chip columns until the widest shows whole (`CollectionTouchLayout.InspectChipColumnsFor`), so an enchantment name is never cut; a filter chip whose label would not fit its span widens across more columns (`TouchChrome.ChipSpan`). Text that would not fit grows its band (History's board messages) or takes a shorter touch label (Ten-Win Builds' `LiveBuildPanelText.CandidateTouchTag`). A sideways-scrolled strip holds only chips: a note in one runs past the screen's edge, so it wraps in a column with room instead (History's Ghost cloud note, in the rail column Ghost leaves empty, `HistoryTouchLayout.CloudNote`).
- **Safe area.** Everything lays out inside `TouchMetrics.SafeArea`, so a cutout or rounded corner never covers a control. The Mobile UI's `Hud/TouchShortcuts` puts the BPP icons by the game's settings button, where Core's `TouchHudLayout.Shortcut` decides (#707): a corner, Collection below the gear (`ShortcutBelow`) and Ten-Win Builds left of it (`ShortcutBeside`); in a run on a screen that gathers the HUD above the board (`ScreenFill.GathersHudAbove`, 4:3 and squarer), where the nearer board reaches up to the gear, both in a row left of it (`ShortcutInRow`, Collection next to the gear). Collection also shows by the lobby and hero-select settings button; Ten-Win Builds shows in a run only. Both hosts draw them; on iOS they replace the desktop's dock clones. History has no icon: its entries live in the game's own menus (android-host.md). Their circular artwork is drawn at the gear's own size, icon where the gear's icon sits, and each target is at least that size. They hide during combat or a replay, native card inspection, popups and BPP panels; `touch.hud.shortcuts_layout` logs each layout and `touch.hud.open_skipped` an open the Overlay Panel Host refused. `TouchHudLayoutTests` checks safe-area fit and non-overlap, including the combat clock beside the vault, or as one row centred in the band above a lowered board (or under the vault) on a nearly square screen.
- **Sheets.** A panel is a full, opaque sheet: title top-left, close top-right (`TouchChrome.Close`), content below. A dialog closes from the same corner of its own body (`TouchChrome.CloseAt`). Every close button is `UiKit.CloseButton` or, on History's own palette, its `UiKit.CloseGlyph`.
- **Back key.** Every surface closes on the back key, top-most first; the chain and how it reaches BPP before the game's escape menu are [android-host.md](android-host.md)'s.
- **No off switch.** No Mobile UI panel switches off: none sets `OverlayPanelRegistration.Enabled`, and History's settings row only opens it (`HistoryPanelSettingsDockEntry`). History closes with its X. Its More dialog keeps only the database check and the account link.
- **No hover, right-click, or hotkeys.** A tap replaces hover: tapping a card opens the inspect sheet with the card enlarged and its text beside it; a tap outside the info column, its close button, or the back key dismisses it. Every action the desktop puts behind a hotkey or a context menu is a visible button.
- **Scrolling.** Ten-Win Builds fixes the recommendation and one lower board on ordinary landscape screens; a button beside the lower board cycles current board, stash and shop without clearing candidates. Both boards have native frames with inset card and tag areas. Recommendation paging joins the board switch in the right operation column; hero identity moves into the recommendation title. A compact library row sits below the metrics and above recommendation paging: muted status on the left opens scrollable corpus details (including freshness and errors), and a native framed Update button on the right refreshes the library. Paging and the board switch expand into the remaining height, with the final switch aligned to the lower board frame rather than the scroll viewport. The board column needs no separate switch band. Empty recommendation guidance occupies the upper board itself. Its dense arrangement scrolls the selected board and overview under the header. Lists and grids scroll by drag with inertia (`UiKit.VerticalScroll`, the Collection grid's included; History's own palette has `TouchHistoryUi.Scroll`); the Mobile UI's `ScrollTracker` logs each finished gesture (`touch.history.scrolled`, `touch.collection.scrolled`) with its distance, peak speed and coast frames.
- **Columns from width.** A card grid chooses its column count from its width, never a fixed desktop count: `CollectionTouchLayout.GridColumns` keeps a small item's column and a skill's square above a readable minimum, up to the desktop's count, and never fewer columns than a large item spans. `CollectionGridLayout.Build` takes that count; the desktop overload keeps `CollectionGridConstants`.
- **Relayout.** A surface lays itself out again when the Mobile UI's `TouchScreen.Key` (size, density, safe area) changes, and renders the same state into the new tree; an open panel stays open (`touch.collection.relaid_out`). Collection closes an open inspection first (`touch.collection.inspection_closed reason=relayout`), returning its card. History reopens an open note dialog on its unsaved draft (`touch.history.relayout note_draft_kept=true`); a scene change, which keeps the view, leaves the note open on its draft (`touch.history.scene_changed note_draft_kept=true`). An open Ten-Win Builds or Collection, each of which rents its cards again on a relayout, waits for the key to hold still and for no card to be setting up (Core's `TouchRelayoutDebounce`, capped so a stuck setup cannot pin the old layout); `touch.live_build.relayout` and `touch.collection.relaid_out` log the frames it held. Opening on a changed screen lays out at once. Each panel's view goes through Core's `TouchViewSlot` (`src/BazaarPlusPlus.Core/Ui/TouchViewSlot.cs`): the old view is forgotten and dropped before the new one builds, and the key is recorded only once the build returned. So when a build fails, on a relayout, on opening, or for Collection's first tree, no panel keeps a destroyed view: the build destroys its partial tree, the panel logs `touch.collection.relayout_failed`, `touch.live_build.layout_failed` or `touch.history.layout_failed`, reads closed (a failed relayout requests the host's close, so the HUD shortcuts come back), and builds again on the next open. The recovery stays the panel's own: Collection's close ends its view state, Ten-Win Builds closes its state, History's overlays go with the view.
- **History header.** History keeps section tabs, one supporter credit that opens the sponsor page, More and Close. The run archive sizes its rows to show three complete runs in the initial viewport while keeping the touch-target floor; additional runs remain drag-scrollable. It offers no hero, outcome or day filters; the archive uses the default unfiltered coordinator state. The supporter credit shares Collection's catalog and samples once per opening, with a late catalog arrival filling the initial sponsor label.
- **Native look.** Each host's native art adapter (`GameInterop/AndroidNativeArt`, on the Mono host `GameInterop/Touch/TouchNativeArt`) borrows popup button sprites and tooltip frame/TagFrame art, which the host hands the Mobile UI's `NativeSkin` through its port; the skin applies them to Collection, History, Ten-Win Builds, the tooltip's touch previews and the combat clock without copying native callbacks. The sprites are cached process-wide: `FindObjectsOfTypeAll` runs again only for a pair that is missing or collected, and only that rescan logs `android.native_art.skin_loaded` (`touch.native_art.skin_loaded` on the Mono host); each surface keeps one skin until `NeedsRefresh`. The round shortcut frame is read, at rest, from the gear the shortcuts anchor to (each adapter's `RoundArtFor`, through the port). Panels keep opaque backing beneath transparent frame art. History's sheet, dialogs and inputs draw only the art's border (`NativeSkin.Frame` with `borderOnly`), so each fills its interior once, and History's backdrop covers only the margins around its sheet, as four bands, rather than the whole canvas under it. Decorative images take no touches, and missing sprites fall back to the host palette. Reopening a panel with missing or destroyed art rebuilds its view. History keeps its warm backing and status palette, and its dimmed actions remain tappable where the model supplies an explanation. The Mobile UI's `PortraitView` shares Collection's framed hero crop with History archive rows; rebinding a reused row invalidates its previous portrait request. The Mobile UI's `InspectionText` scrolls long History and Ten-Win Builds descriptions at body size instead of truncating them.
- **In-game previews.** The upgrade switch controls the existing next-tier projection inside the native tooltip, at the game's own text size. Its initial state follows the host's upgrade setting (`[Android] UpgradePreview`, on iOS `[Touch] UpgradePreview`, both off by default), and a card's next tooltip starts there again once its tooltip closes. The switches are the Mobile UI's `Previews/TouchPreviewSwitches` on both hosts, ticked by the HUD (`touch.preview.*` logs); each host reads and writes its tooltip through `ITooltipPreviewHost` (Host adapters, above). Only the tooltip reads and the upgrade state stay in the host (`AndroidUpgradePreview`, `TouchUpgradePreview`), which the host's own tooltip patches also read; the switches and the enchant preview are the Mobile UI's. They show only on an item tooltip, outside a fight and under no open panel, and the upgrade switch never on a replay's or recap's card. Under `[EnchantPreview] Mode` ON, or AUTO while an enchant pedestal is offered, the enchantment effects are listed expanded in the native tooltip's main text below the passive text, one line per enchantment at the current quality, where a player reads them without a tap or a scroll: the Mobile UI's `Previews/TouchEnchantPreview` on both hosts (`touch.enchant_preview.*` logs), which each host's tooltip render patches drive and which reads the tooltip through `IEnchantPreviewHost`. The upgrade switch, and the enchantment switch for an item whose main text lists none, use Collection's toggle rows inside the native right-side description scroll; those enchantment effects expand below their switch, merge current-and-higher-quality values with Collection's formatter and colour the enchantment names. Body text follows the shared touch floor. Replacing or dismissing the native tooltip collapses the enchantment section; Back collapses it before the native tooltip handles another Back. Native pedestal-owned upgrades are never disabled by BPP.
- **Combat clock.** A plaque in the native button's opaque dark-brown sits right of the vault and spans the vault frame's height, so its top and bottom edges line up with the board. The vault is the player's bank, an equipped cosmetic (`BankToyController` under `BoardManager.playerBankAnchor`); it is board meshes rather than canvas UI, so the host's vault adapter (through the port) projects its framed platform mesh (`Bank_Platform_SM`, not its slightly larger `Platform_Shadow_SM`) through the board camera, as the desktop bar reads the hero portrait, and `TouchHudLayout.Playback` places the plaque beside that box. The platform holds still while the coin pile on it changes with gold; a bank without one falls back to its hover boxes (the pot's `_bankCollider` and the income and gold plaques' colliders), which sit a few pixels up and left of the art; the stash cosmetic (`activeStorageToy`) is the box at the board's other end. As on the desktop, no vault on screen means no plaque: the main menu, which has an active run to resume but no board, shows none, and a read that is off the canvas, left of center or shorter than a touch target (`TouchHudLayout.FitsBesideVault`) hides it too. The vault is read every few frames while the clock shows; a vault or screen that moves lays the plaque out again once the new place holds still for two reads (`TouchRelayoutDebounce`), and a clock shown again after hiding lays out at once; `touch.combat_status.layout` logs the box. The clock is the Mobile UI's `Hud/TouchCombatClock` on both hosts; each host feeds it the playback state, the setting, its own run-or-replay rule (on iOS also no end-of-run screenshot) and its pause. It hides while the native card drawer shows an inspected card, and its canvas sorts just beneath that drawer. Time fills the upper row with tabular digits; a gold rule separates it from a shorter lower row split by a vertical rule into speed (left) and pause/resume (right). The two hit areas keep full touch-target size by extending below the plaque to the screen edge rather than into the time row. The default-on **Combat timer** switch in native settings controls visibility. As the desktop bar, it shows for the whole run or replay, not only during a fight: before the first fight it reads `0:00.00`, after one it keeps that fight's final time until the next starts at zero, and outside a fight the time fades to muted ink and pause/resume dims, while speed stays tappable and sets the next fight's pace. While it is hidden beneath a panel, popup or inspection it is built hidden ahead, once per scene (`touch.combat_status.layout ahead=true`), so the frame it reappears on does not build it; a plaque built before the native art loaded is built again when first shown. Tapping speed cycles the three supported speeds using the shared speed setting. It hides beneath Main Overlay Panels and native popups and clears on scene changes. **Detailed Preview** controls both quest and encounter previews through one native settings toggle. It never counts background wall time.

## Screens

The tests cover a 20:9 phone (2400x1080 at 420 dpi, with and without a cutout; Ten-Win Builds also at 480, 560 and 640 dpi, where it stacks), a 16:10 tablet (2560x1600, with and without the emulator's 91 px top inset), a 16:9 phone (1920x1080), and a device that reports no density. The device evidence covers the first two. Keep a separate landscape AVD for each ratio and select it with `BPP_ANDROID_SERIAL`; changing one emulator's `wm size` mixes device configuration with layout evidence. Before judging a panel, run `just mod::android-screen-check <run>` on that panel. It saves the screenshot and display metadata and rejects portrait screenshots, size/density overrides, or a mismatch with the last logged Unity screen. It never changes the device. `environment.json` records the last logged Unity density and safe area when available; `display.txt` keeps Android's display state. A passing check establishes the display baseline, not visual correctness: inspect the screenshot for sideways content, clipped rows and alignment.

Use `just mod::android-check` for the serial build/test gate. The build and test script entry points share a checkout-local lock because they write the same `bin/obj` outputs; run another checkout to work independently. Each gate saves full logs and a `result.json` with the revision, dirty-worktree flag and exit codes under `artifacts/validation/`. A failed step stops the sequence. After an interrupted process, the next run's lock error names the lock directory; its `owner.json` records the holder, so confirm that process has stopped before removing the directory.

## Gotchas

- The overlay canvas scales with height, so a 16:10 tablet has fewer canvas units across than a 20:9 phone of the same height: a layout that fits the phone by canvas units can overflow the tablet. Lay out in dp from `TouchMetrics`, and test both ratios.
- A rented card carries its own `Canvas`, so a `RectMask2D` does not clip it: a scrolled card list draws first and opaque bands above and below it hide the cards past its edges, and the inspect sheet is opaque under its info column.
- `RectTransform.rect` of a stretched child is valid as soon as its parent has a size, so a flow that measures wrapped text (`ChipFlow.Note`) needs its parent placed first.
